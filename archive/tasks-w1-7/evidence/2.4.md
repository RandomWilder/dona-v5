## The four decisions this slice owed

### `party`'s natural key — a generated `national_id_key`

2.1 left the table keyless deliberately and named three hazards. All three are inside one expression:

```sql
national_id_key text GENERATED ALWAYS AS (
  CASE WHEN national_id IS NULL THEN NULL
       ELSE party_kind || ':' || <separators stripped, all-digit values left-padded to 9>
  END
) STORED
```

- **Leading zeros.** `042938271` and `42938271` are one person, and every spreadsheet export produces
  the second from the first. Asserted with four spellings — as typed, as exported, as a person writes
  it with hyphens, and with stray cell whitespace — all colliding on `23505`.
- **Two registries.** A `PERSON` and a `COMPANY` may share nine digits and are two parties. Asserted.
- **Nullable.** A UNIQUE index ignores nulls, so a party with no identifier has no key. Three such
  parties insert without conflict, which is the assertion.
- A non-numeric identifier (a passport) is normalised for case and separators and **never padded**:
  `X-12345 ` → `PERSON:x12345`. Padding it would be inventing a fact about a registry we do not read.

**The register file format requires an identifier where the schema does not.** No identifier, no
idempotence — and a surrogate built from a name and a phone would be a key that disagrees with itself
in the other direction: two people with one name, or one person whose number was recycled. This is
the answer to 2.1's open question, and it is **a question put to the client**, carried into 2.5:
confirm the Priority export carries a ת.ז./ח.פ. on every party before the first row lands.

### `terms_profile` — `UNIQUE (name)`, and a blank one is a reject

What identifies a profile is not the same question as how many are in force, which stays week 5's.
**A lease naming no profile is rejected with its line number, never defaulted to `standard`**: the
column is NOT NULL precisely so the question reaches the client instead of reaching week 6's
responsibility matrix as an assumption. Carried into 2.5 beside the identifier.

### `party_contact` — `UNIQUE (party_id, channel, value, valid_from)`

Mechanical rather than domain-shaped: `ON CONFLICT` needs a unique constraint as its arbiter and 2.1's
`contact_value_resolves_to_one_party` is an `EXCLUDE` constraint, which cannot be one.

### `is_primary` — nothing, which confirms 2.1 rather than revisiting it

The register carries one contact per row and does not say which of a party's numbers is primary. As a
partial unique index the rule would fail an import that touched two rows in the wrong order.

## The register file, and what it proves

`src/register/fixtures/register.csv` — nine rows, twenty-two columns, two buildings. Ours, designed
for coverage of the cases that break things (`docs/pipeline.md` §1 principle 5, `SPEC.md` tier 3):
one person under two spellings of one ת.ז. on two tenancies in two cities; a recycled phone number
held by one party to 30 June and another from 15 July; a guarantor; two tenancies on one unit, one
`ENDED` and one `ACTIVE`; a company party whose name contains a quotation mark; a building with no
project; a `DRAFT` tenancy that has not started.

**First run — nine lines, nine accepted, zero rejects.** The row counts are not nine, and that is the
keys doing their work:

| | created | updated |
|---|---|---|
| `project` | 1 | 6 |
| `building` | 2 | 7 |
| `space` | 5 | 4 |
| `unit` | 5 | 4 |
| `terms_profile` | 2 | 7 |
| `party` | 8 | 1 |
| `party_contact` | 8 | 1 |
| `tenancy` | 6 | 3 |
| `tenancy_party` | 9 | 0 |

Nine lines produce **eight parties**, because rows 2 and 9 are the same person under the two
spellings a spreadsheet produces, in two cities, on two tenancies.

**Second run — `created: 0` on all nine tables, and every id identical.** The counts are the weak
half; the ids are the strong half. A re-import that renumbered every unit would satisfy a count and
break everything that ever pointed at one, which is 1.11's lesson asserted again here over buildings,
units, tenancies and parties.

## The broken file — a reject is a line number, and the file continues

`src/register/fixtures/broken.csv` — eleven rows, nine broken, one good first and one good last. The
last row is the assertion the file exists for.

```
accepted: 2 of 11
  line  3 validate       — national_id is required and is blank
  line  4 validate       — phone is not a number this register can normalise
  line  5 validate       — tenancy_end (`2026-01-01`) is before tenancy_start (`2027-01-01`)
  line  6 validate       — role (`LANDLORD`) is not one of PRIMARY_TENANT · CO_TENANT · GUARANTOR · OCCUPANT
  line  7 validate       — terms_profile is required and is blank
  line  8 validate       — expected 22 columns, found 21
  line  9 write   23514  — rejected by guarantor_is_never_a_service_contact
  line 10 write   23P01  — rejected by one_active_tenancy_per_unit
  line 11 write   23P01  — rejected by contact_value_resolves_to_one_party
```

Line 2 and line 12 are absent from that list, and units `1` and `9` are in the database. **The three
`write` rejects are the ones the mechanism exists for**: they reached the database and were refused by
a rule, and the import carried on.

**A reject never quotes a person.** `full_name`, `national_id` and `phone` are named as columns and
never echoed; every other column may be quoted back, because a reason reading *"role (`LANDLORD`) is
not one of…"* is worth an order of magnitude more than *"role is invalid"* and costs nothing. The set
is explicit rather than inverted, and a test asserts that no name, identifier or number from the
broken file appears in any reason.

## Three probes, and each found something review would not have

### Probe 1 — remove the savepoint

The claim was that a `SAVEPOINT` per row is what makes a rejected row a reject rather than a failed
file. Removing it, against the same broken file:

```
accepted: 1 of 11                       (with the savepoint: 2 of 11)
  line  9 write 23514 — rejected by guarantor_is_never_a_service_contact
  line 10 write 25P02 — rejected by the database
  line 11 write 25P02 — rejected by the database
  line 12 write 25P02 — rejected by the database
```

Three things go at once. Line 12 is a **good row** and is lost. Lines 10 and 11 are still rejects but
say nothing about *why*, because `25P02` is the transaction being poisoned rather than a rule being
enforced. And every constraint name disappears from the report — which is exactly the number 2.5
exists to take: *how many rows does the client's register lose to `one_active_tenancy_per_unit`.*
At nine rows this is a curiosity; at 1,500 the first sloppy end date costs the other 1,499.

### Probe 2 — can `ON CONFLICT` arbitrate at all?

`party_contact` carries an `EXCLUDE` constraint from 2.1 and a UNIQUE index from 2.4 over overlapping
territory, and the red-first run showed the exclusion constraint winning: a bare duplicate `INSERT` is
rejected as `23P01`, not `23505`. That raised a real question the plan had assumed away — whether the
new key can be an `ON CONFLICT` target when the exclusion constraint would also fire.

Measured rather than reasoned about:

```
first : { contact_id: 01a07724-…af5c, inserted: true  }
second: { contact_id: 01a07724-…af5c, inserted: false }
```

`ON CONFLICT` runs its **arbiter check before any index insertion**, so the unique index resolves the
re-run and the exclusion constraint is never reached. The test was corrected to assert both halves —
a bare duplicate is still `23P01`, and the upsert returns the same `contact_id` — rather than to
assert the SQLSTATE the plan expected.

### Probe 3 — the recycled-number case asserted the wrong thing

The case was written to show one number resolving to two different tenancies on two dates. It went
red: on a day inside the first holder's contact period, `resolveUnitsByPhone` returned **nothing**.

The first holder's tenancy is `ENDED`, and the isolation join reads `status = 'ACTIVE'`. A number
whose only tenancy has ended resolves to **nobody** — which is the property, not a gap, and is the row
2.5's *Done when* calls *"one ended tenancy reading as a vacancy"*. Asserted correctly now: nothing on
2024-06-01, exactly one unit on 2026-06-01, and it is the new holder's own (`PERSON:071500006`), with
the previous holder still present as history (R5) and their leading zero restored
(`PERSON:071500005`, from `71500005` in the file).

**Had the assertion been left as written and made to pass by moving a date, the case would have been
green for a reason that has nothing to do with recycling.**

## Two guards, and one of them was missing

**Guard three did not fire, and should have.** `national_id_key` was not on `PII_COLUMNS`, and the
guard matches names exactly rather than by pattern — on purpose, because `like '%phone%'` fires on
`telephone_policy` and teaches people to work around a guard. So the most person-shaped column this
slice adds was invisible to it. This is the list's **second miss**, after `party_contact.value` at
2.1, and the rule stayed the rule: the list learned the name it met. With `national_id_key` added and
the marker removed on purpose, the guard fires:

```
guard pii-columns-are-commented: 0009_import_natural_keys.sql — line 41: `national_id_key`
  holds personal data and carries no `-- pii` (or `-- not-pii: <why>`)
```

`national_id_key` is marked `-- pii` and not `-- not-pii`, which is where it differs from
`building.address_key`: `address_key` is an enforcement column carrying no fact, and this one *is* the
identifier, normalised.

**`AGENTS.md` has claimed since week 1 that "a CI grep guard" stops a module reaching another
module's `internal/`, and there was none.** It cost nothing while every module was a leaf. 2.4 is the
first slice where a module imports four others' contracts, so the claim became load-bearing and was
made real — `src/kernel/boundary.test.ts` now proves two boundaries instead of one. Proved red by
pointing `src/register/internal/importer.ts` at `../../parties/internal/commands.ts`:

```
+ 'register/internal/importer.ts → ../../parties/internal/commands.ts'
```

This is the move guard three made at 1.12, one slice later than it should have been: a control
written down with nothing behind it is a control about to be discovered missing.

by `src/parties/schema.test.ts` and `tests/policy/`. `node --test` runs files in parallel against one


## What is deliberately not here

- **No batching and no `COPY`.** A savepoint per row costs a round trip per row. 2.6 measures this
  path at 1,500 units and owns the decision, with a timing in front of it — the rule both index
  questions are held to.
- **No screen.** 2.4 adds no route. 2.6 is the screen slice.
- **No cross-tenancy identity resolution.** `national_id_key` deduplicates by *identifier*, which is
  a key and not a judgment. Matching a name against the register is month two's, and
  `SPEC-flows.md` A2 step 5 forbids it to the lease flow for the same reason.
- **No republish of the four documents.** `docs/data-model.html` names Party's fields at the altitude
  of *"id, full_name, national_id"*; a generated enforcement column is below it, and nothing in the
  Cadence, the Platform Brief or the Stack Map moved. The repo and the artifacts are in step.

## Staging

```
migrate: applied 1
  0009_import_natural_keys.sql
Container called exit(0).
```

`dona-staging-migrate-g7hlt` · deploy run `34040595328` · revision **`dona-staging-00028-b8n`**, 100%
of traffic · `{"ok":true,"version":"0c6177d","db":"up"}`.

The migration ran as its own Cloud Run job, from the image about to be deployed, as the **runtime**
service account, **before the revision served** ([pipeline.md](../../docs/pipeline.md) §5). The
version stamp is the check that the deploy read was this one — 2.1 reported another commit's
in-flight run as its own, and `version` is what caught it.

**This migration did carry a Cloud-SQL-specific risk, unlike 2.3's.** `national_id_key` is a
`GENERATED ALWAYS AS … STORED` column added by `ALTER TABLE`, which is a table rewrite, and its
expression has to be **IMMUTABLE** on the server that runs it — `regexp_replace`, `lpad`, and
`lower`, which is the one that is collation-adjacent and therefore the one a local container answers
for least well. `0005_estate_natural_keys.sql` established the pattern on `address_key`, and the same
question was open again for a different expression. Cloud SQL `POSTGRES_16` accepted it. The rewrite
cost nothing because all three tables hold zero rows in every environment, which is also why this is
DDL with no backfill — the same reason `0005` landed in week 1 rather than under 1,500 units.

**No register has been imported into staging, and that is the state this slice ships.**
`npm run import:register` is in no workflow, exactly as `npm run seed` is not: an import is a thing
somebody runs on purpose, having chosen the file, and the file this one will eventually be pointed at
is a register of real people. What is on staging is the *path* — the migration, the module and the
entry point. **2.6 loads the generated register through it, and 2.5 the real one**, after the two
questions this slice raises have answers.

`/estate` is still fixture-only and has no session, which is week 5's (1.11's carry, restated at 2.1,
2.3 and again here). Nothing this slice adds is in front of a user: the register module has no route.
