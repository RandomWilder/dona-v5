## Verdict is a column, not a scrape of audit_log

3.3 left the guard's result on the audit line because nothing listed yet. 3.6 made it a property of
a list, and a list cannot re-read the bytes without missing the four-second bar. `audit_log` is
who-did-what JSON and is the wrong read model for a card.

This is **not** figure 5's `state`. `refused` still writes no row. The three stored values are
`verified · unverified · unguarded`. The immutability trigger still names only `file_hash` and
`storage_uri`: 4.1 may later move `unverified` → `verified` once OCR gives a scan a text layer.

Workbook first: `verification_verdict` appended on E12 in `docs/model/build_model.py`, generator
re-run, Hebrew workbook untouched. Then `0014_document_verdict.sql` (nullable column) and
`0015_document_verdict_backfill.sql` (from the 3.3 audit lines, leftover test-helper rows
`unguarded`, then CHECK and `NOT NULL`). DDL and backfill in separate files.

Both constraints were red first against 0014 without them: inserting `refused` succeeded, inserting
with no verdict succeeded. After 0015 they are `23514` and `23502`.

`-- not-pii:` on the column: a guard outcome, never a person. Guard three did not fire; the sentence
is there anyway, 3.1's habit.

## Search is extended, not forked

Same box, same `LIMIT` 60, same LIKE-escape. Estate still finds buildings and units. Evidence adds
`searchDocuments`, injected at `app.ts` so estate never imports evidence (evidence already imports
estate). Matches type labels, a unit number, a building name or address — never a city, never a
party, never a filename, never the file's text.

A lone `%` matches nothing. That case was copied from 2.6 and would have been the defect if the
second search had forgotten it.

A unit hit now links to `/estate/units/:id`, not the building, so a 72-flat building is not the
find path.
