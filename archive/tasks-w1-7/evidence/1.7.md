## Both cases are red for the right reason, and the reason is named

`REQUIRE_POSTGRES=1 npm run test:policy` against the real local database, with no estate, parties or
tenancy tables in it:

```
▶ policy · the five-hop isolation join
  ✔ resolves a current tenant to their own unit, and to no other
  ℹ pending — relation "building" does not exist yet
  ✔ drops a contact whose validity has closed — temporal predicate one
  ℹ pending — relation "building" does not exist yet
  ✔ drops a tenancy that is not active today — temporal predicate two
  ℹ pending — relation "building" does not exist yet
  ✔ never resolves a guarantor to the unit they guarantee
  ℹ pending — relation "building" does not exist yet
▶ policy · a recycled number
  ✔ resolves to nobody once the tenancy and the contact have both closed
  ℹ pending — relation "building" does not exist yet
  ✔ stops a stranger reaching a unit whose tenancy is still running
  ℹ pending — relation "building" does not exist yet
  ✔ resolves to the new holder’s own unit and never to the previous one
  ℹ pending — relation "building" does not exist yet

ℹ tests 14 · pass 14 · fail 0 · skipped 0 · todo 0
```

The raw error underneath every one of those lines, which is what "the right reason" means:

```
error: relation "building" does not exist
  code: '42P01'
```

**Why the cases are pending rather than red in the committed state, which is the only structural
decision in this slice.** `gate` is a required check on `main` and `enforce_admins` is `true` from
1.6, so a deliberately-red required test blocks every merge including its own. A `t.skip` or a
`{ todo: true }` would clear that and cost the thing the slice exists to buy: both stay quiet after
the tables land, and have to be *remembered*.

So the case runs the real query and tolerates exactly one failure — SQLSTATE `42P01`, on a relation
the query declares it reads. A wrong column, a wrong row count, a wrong error code or a 42P01 on a
relation nobody declared all fail the build. **The branch is unreachable the moment the last table
lands**, so the case starts asserting for real with no edit and nothing on anyone's list. The rule is
written into `SPEC.md` rather than into the two files that use it.

The first run proved the tolerance is not a blanket pass: the declared list was the join's five
relations, the fixtures reach `building` and `space` as well, and the case failed —
`42P01 on a relation this case does not declare: relation "building" does not exist`. The list is now
the join's relations plus the fixtures', exported from the two files that own them rather than
restated in the cases.

## Every predicate in the join is load-bearing, and two cases were rewritten because they were not

Each predicate was deleted from `ISOLATION_JOIN_SQL` in turn and the suite re-run against
`policy_probe`. A predicate whose removal breaks nothing is a predicate the suite does not test.

```
predicate removed              cases red   which
contact validity               2           temporal predicate one · stranger on a running tenancy
tenancy start/end dates        1           temporal predicate two
tp.is_service_contact          1           the guarantor case
pc.value = $1 (the phone)      7           all of them — scope widened to everybody
```

**The first version of this suite failed that check twice, and both fixes are the interesting part
of the slice.**

- *"Drops a tenancy that is not active today"* seeded the tenancy with `status = 'ENDED'`. The join
  filters on `status = 'ACTIVE'` as well, so the row was excluded by the status filter and **both
  date comparisons could have been deleted with the case still green.** The fixture now leaves the
  status `ACTIVE` and lets the dates be expired — a lease that ended in June with a status nobody
  updated, which is the ordinary state of an operations database and the only version of the case
  that tests the predicate it is named after. A second assertion covers the lower bound: a lease
  starting next month is not a lease today.
- *The recycled-number cases* both ended the previous tenancy, so the tenancy predicate killed them
  and **the contact dating — the whole point of case 2 — was doing nothing.** A third case was added
  where the tenancy is still running: the tenant changed carrier in June and their old number was
  reassigned, the lease runs to 2027, the unit is occupied, and the closed `party_contact` row is the
  entire defence. That is the case v3 could not represent, and it is now the one that goes red when
  the predicate is removed.

Two temporal predicates asserted, as the acceptance bar asks — and asserted in the only fixtures
where each one is the thing standing in the way.

## The guards, tripped in CI rather than described

Both are steps of `gate`, not a job of their own: `gate` is the required context on `main`, and a
guard nothing requires is a guard nobody obeys.

**Guard one — a migration naming `current_tenant`.** Commit `8c67318` added
`0004_deliberate_violation.sql`. Run `33965072969`:

```

  ALTER TABLE unit ADD COLUMN current_tenant uuid;

```

**Guard two — a second copy of the join.** Commit `f9eb13a` wrote the join's own text into
`src/channel/lookup.ts`, reindented the way a copy that drifts would be, so what is proved is that
the guard matches the *predicate* and not the layout. Run `33965119613`:

```

  belongs to src/scope and nowhere else
guard isolation-join-lives-in-src-scope: src/channel/lookup.ts — the tenancy-active predicate
  belongs to src/scope and nowhere else

PR #10   mergeStateStatus BLOCKED   gate FAILURE
```

Both reverted (`f225a24`, `ab961c7`), `gate` green again, and the guards also have unit tests of
their own so a later refactor of `scripts/guards.ts` cannot quietly defang them.

**Guard one greps `src/kernel/migrations/*.sql`, and both guards fail when they scanned zero files.**
`docs/pipeline.md` §6, `tasks/todo.md` and `tasks/roadmap.md` all wrote this guard against
`migrations/*.sql`, which has never existed in this repository. A guard pointed at a path that
matches nothing passes forever and reads like diligence — it is 1.3's silent-glob finding arriving in
CI instead of in a test runner. The count is the part that catches it, it is asserted by a case, and
§6 was corrected in this change rather than left disagreeing with the code.

**Guard two matches the predicates, not the table names.** Naming `party_contact` is ordinary —
`tests/policy/fixtures.ts` inserts into it — while re-deciding *when* a contact or a tenancy counts is
what only one file may do. It fired on its very first repository-wide run, on two comments in this
change that quoted a predicate in prose to explain the mutation testing. The comments were reworded.
The guard was not weakened, and the cost is now known and small: you cannot quote the predicate in a
comment outside `src/scope/`.

## `src/scope/` landed at 1.7 rather than 2.3

The consequence of the decision above: the case has to run the join, so the join has to exist. A case
that writes its own copy proves that copy — and puts a second copy outside `src/scope/`, which is the
exact drift guard two exists to stop.

What landed is the join and nothing else: `internal/isolation-join.ts` and `contract.ts`, no tables,
no view, no command surface. It is written against the workbook's E1–E8 field names, which are a
specification and not a description, so if 1.9's DDL drifts from them the policy cases go red — the
gate working, not the gate breaking.

**One predicate in it is not in the acceptance bar and is there on purpose.** `tp.is_service_contact`
is not temporal; it is foundation rule 7 — a guarantor (ערב) never receives service information — at
the point where the constraint is actually *spent*. The flag is forced false for `role = GUARANTOR`
by a database constraint at 2.2, and a flag nothing reads protects nobody. The constraint itself is
policy case 3 and is not this slice's.

## Observations, which are not assertions

**`scripts/` joined `tsconfig.json` and `biome.json`.** The guards are CI-critical code that decides

and is 32 after; the guards line replaced a line rather than adding one. Carried, not fixed here.

## What this slice carried, and to where

`tasks/roadmap.md` — not only here.
