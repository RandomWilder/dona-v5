## Four structural calls

**1. Four scripts were lifted, not one.** The slice names `bootstrap.sh`. `set-secret.sh`,
`smoke.sh` and `rollback.sh` came with it because lifting one of the four leaves the repository
pointing at three files that do not exist: `rollback.sh` ends by invoking `smoke.sh`, `bootstrap.sh`
prints a `set-secret.sh` command in its own output when the model key is absent, and `AGENTS.md`
already told every agent "secrets only through `infra/set-secret.sh`". All four are byte-identical to
v3 apart from the changes listed below. Only `bootstrap.sh` was *run* in this slice; the other three
are consumed at 1.6 and 1.10, which now lift nothing.

The complete diff against v3, and there is nothing else in it:

**2. R8 is not satisfied, and no slice this week can satisfy it.** The requirement is that the
project is created **under an organisation**. `dona-v5` was created org-less on 2026-09-04, and
`gcloud organizations list` returns **0 items** for the owning account — there is no organisation to
create it under. Making one means a Cloud Identity Free tenancy on a domain we control plus DNS
verification: a signup, not a script. `roseberry.media` is a different company's tenancy and is not a
candidate for holding a Dona Dom project.

Provisioned org-less on purpose. A project move preserves project id, resources, data and IAM
whenever it happens, so the cost of doing it in three weeks is the same as the cost of doing it
today, and nothing in week 1 depends on it. What is **not** deferrable is the ordering, and the
ordering is what gets lost:

- an identity on the destination domain must exist **before** the move, because most organisations
  enforce `constraints/iam.allowedPolicyMemberDomains`, which blocks IAM grants to an external
  `gmail.com` address outright — the likeliest single way to be locked out of this project;
- the move must happen **before real tenant data lands**, so it stays an admin task rather than a
  data-custody event. The real corpus arrives at **slice 1.12, this week.**

That ordering is now **fuse F7**, it is carried into 1.12's entry in both `tasks/todo.md` and
`tasks/roadmap.md`, and `bootstrap.sh` prints it on every run against an org-less project:

```
▸ Environment: staging (project dona-v5, region me-west1)

  !! dona-v5 has no organisation. R8 is not satisfied -- see fuse F7.
     Move it before real tenant data lands, and not before an identity
     on the destination domain exists.
```

A warning in the output beats a line in a document, for the same reason the bash guard exists: the
document is read when someone remembers to read it, and the output is read every time.

**3. The four staff seed secrets were dropped from the lift.** v3's bootstrap creates

## The three proofs

### (a) A second run is a no-op

A normalised inventory — service accounts, project IAM bindings for our accounts, every secret with
its IAM policy and version list, the Artifact Registry repository, the WIF pool and the provider's
attribute condition, both buckets with their three controls and their IAM, and both SQL instances
with their settings — captured after the first `bootstrap.sh staging`, then again after a second.

```
$ diff inv-01-after-first.txt inv-02-after-second.txt
$ echo $?
0                                        # 49 lines, byte identical
```

The interesting line in the second run is the one that proves the password is not rotated by a
re-run, which is what makes bootstrap safe to run against a live environment:

```
▸ Database user and connection secret
  secret already exists — leaving password untouched
```

Prod's run is a second, independent no-op proof for the resources the two environments share: it
created its own instance, secret, service accounts and bucket, and reported nothing for the Artifact
Registry repository or the Workload Identity pool, because staging had already made them.

### (b) No user-managed service-account key exists

A user-managed key is a long-lived credential that can be copied out of a laptop; Workload Identity
Federation exists so that none is needed. `--managed-by=user` excludes Google's own rotating
system keys, which are not ours to have an opinion about.

```

app-prod@dona-v5.iam.gserviceaccount.com             user-managed keys: 0
app-staging@dona-v5.iam.gserviceaccount.com          user-managed keys: 0
deploy-prod@dona-v5.iam.gserviceaccount.com          user-managed keys: 0
deploy-staging@dona-v5.iam.gserviceaccount.com       user-managed keys: 0
```

Five accounts, including the default compute account this slice did not create, all zero.

### (c) Staging cannot read prod's connection URL

Read **as `app-staging` itself**, by impersonation, rather than by reading an IAM policy and calling
that proof. A policy says what was granted; an impersonated call says what is enforced. The human
account was granted `roles/iam.serviceAccountTokenCreator` on `app-staging` for the duration of the
proof and it was removed immediately afterwards — the account's IAM policy is empty again, confirmed
after the fact.

No secret value is printed anywhere in this proof. The positive control is piped to `wc -c`.

```
== negative: app-staging -> prod-database-url (expect PERMISSION_DENIED)
PERMISSION_DENIED
Permission 'secretmanager.versions.access' denied
   denied ✓
== positive control: app-staging -> staging-database-url (expect a value, never printed)
   staging-database-url readable by app-staging: 99 bytes
```

**The positive control earned its place on the first attempt, and this is the part worth keeping.**
Run thirty seconds after the grant, the negative leg produced a textbook-looking denial:

```
PERMISSION_DENIED
Permission 'iam.serviceAccounts.getAccessToken' denied
```

That is not the isolation being enforced. It is the impersonation grant not yet propagated — the
call never reached Secret Manager at all. On its own it is indistinguishable from a pass, and it
would have been recorded as one. The positive control failed in the same run (`0 bytes`), which is
what exposed it; ninety seconds later both legs behaved, and the denial names
`secretmanager.versions.access` on the right resource. A denial is only evidence when the same
mechanism can be shown to allow something.

## Two observations, which are not assertions

**A project editor can still delete a document object.** The runtime account has `objectViewer` and
`objectCreator` and deliberately not `objectAdmin`, so the *application* cannot destroy a signed
contract. The bucket's IAM policy also carries the default `projectEditor` / `projectOwner` legacy
roles, including `legacyObjectOwner`, which do carry delete. That is inherent to a GCS bucket in a
project with basic roles, not something bootstrap chose, but it means "the contract cannot be
deleted" is true of the app and not of a human with project editor. Slice 1.12 owns the deletion
path and the retention rule; this is the fact it starts from.

**Soft delete is on by default at 7 days**, which was not asked for and is not harmful — it is a
recovery window, not a retention obligation. 1.12 should decide whether it stays once a real
retention rule exists, because a "permanently removed" claim and a seven-day recovery window are not
the same statement.

## Cost, and the lever on it

Both instances are the smallest shape that works: `db-f1-micro`, `ENTERPRISE` (me-west1 defaults new
instances to `ENTERPRISE_PLUS`, which rejects shared-core tiers — two hours of v3's discovery in one
flag), zonal, 10 GB. Staging runs `--no-backup` because it is disposable; prod keeps seven daily
backups. Cloud Run scales to zero and does not exist yet. The steady-state bill is two always-on
micro instances and their storage.

Two controls were put in place rather than promised:

1. **A monthly budget on the project.** `dona-v5 — monthly`, **₪250**, filtered to project
   `681282581055` alone, with alerts at 50%, 90% and 100% of current spend and at 100% of
   *forecasted* spend — the forecast rule is the one that fires before the month ends rather than
   after. The billing account is denominated in ILS, which is why the figure is not in dollars.
2. **Prod's database is idle from 1.10 until week 12** and should be stopped for that stretch.
   Pipeline §8 is explicit that prod tagging starts at week 12; between 1.10's deliberate round trip
   and the pilot there is nothing in prod to serve and nobody to serve it. `gcloud sql instances
   patch dona-prod --activation-policy=NEVER` stops compute billing while keeping storage, the
   instance and its data, and one command reverses it. Carried into 1.10's entry, which is the slice
   that finishes with prod and knows when it is safe.

Also noticed while doing this, and belonging to whoever owns the billing account rather than to this
slice: the existing budget on this billing account is named **`dona-v1 — monthly`** but its filter is
`projects/149055978002`, which is **dona-v3**. The alert does not cover what its name says it covers.
