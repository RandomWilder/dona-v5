## The ruling, and why it is a refusal

The week-6 demo filed one file twice. `ON CONFLICT (file_hash)` returned the document filed on 8 Sep,
a second `SUBJECT` link went in, and `unitIdOf`'s unordered `LIMIT 1` then decided which of the two
flats the confirm screen was about — *"the address does not match"*, said about an apartment the
director had never opened. That document now carries three links.

**Decided: a document is anchored to one place, and it is the place its own `storage_uri` names** —
written once, immutable since 3.1, and already unique. Filing bytes already on file **against a
different place is refused**, naming the flat they are anchored to. The same place is unchanged: a
no-op on the row plus whatever link the caller came to add. The four reasons are in
`SPEC-evidence.md` (*The same bytes are one document, and one anchor*); the shortest is 6.11's
standing form — **a confident wrong anchor is the dangerous failure and a refusal is the safe one** —
and re-anchoring is the demo's own defect with a different winner.

**R13 is untouched at the table.** The guard is in `fileDocument`, not the DDL: one document still
binds to a letting and to two signatories, and `schema.test.ts` still proves it.

## Two unordered `LIMIT 1`s became one read

`anchorOf` (`documents.ts`) is the place a document is about, off `storage_uri`. Both callers use it:
`unitIdOf` (the lease confirm screen) and `GET /documents/:id/read`, each of which could return either
row. Deterministic by construction rather than by an `ORDER BY` — and **right for the rows already in
the wild**, which resolve to the flat their bytes are filed under. The parse takes no bucket, on
purpose: *which flat* does not depend on which bucket holds the copy. Reading the **bytes** still goes
through `parseStorageUri` and still refuses a foreign bucket.

## Raised, and owned elsewhere

- **Nothing can move an anchor.** A document filed against the wrong flat stays filed against it; the
  operator is told which one and can open it. Correcting one is a deliberate act with its own line and
  its own screen, and it does not exist. Ruled in `SPEC-evidence.md`, carried in `todo.md`.
- **`cap.test.ts` deletes another suite's rows.** Its cleanup is
  `storage_uri LIKE 'gs://dona-v5-test-docs/%'` and `routes.test.ts` commits under the same bucket;
  `node --test` runs files concurrently. Seen twice in this session — an FK violation in cap's own
  teardown, and routes losing its filed document mid-run. Both passed on a re-run, which is the
  problem. Not fixed here: it is a test-harness slice, not this ruling.
- **A document's *tenancy* link is stable but arbitrary.** `tenancyLinkOf` and `promote.ts` order by
  `entity_id`, so they never reshuffle — but no rule says a document has one letting, and if one ever
  has two the lowest id wins for no reason. Worth a rule, not worth a guess.
- **The CSS carry rides on.** `.form-grid` / `.form-row` / `.hint` / `.form-actions` are still **two
  files each** (`src/estate/internal/views.ts`, `src/evidence/internal/views.ts`); this slice wrote no
  third file. Carried into week 7.
