## How many buildings had a placeholder handover date

The register carries no handover date. `src/register/internal/importer.ts` writes
`handoverDate: row.tenancyStart` and `warrantyEndDate: row.tenancyEnd`, and says so in the comment
that has been there since 2.4.

| Source | Buildings | Placeholders | Why |
|---|---|---|---|
| Shoham fixture | 1 | **0** | `2025-03-01` / `2027-03-01` were authored with the plan |
| 2.4 nine-row register | 2 | **2** | every building is a last-row lease start |
| 2.6 generated register, 1,500 units | 37 | **37** | the same importer, at volume |

**Every building that arrived through the register importer had a placeholder. The one that did not
arrive that way did not.** Staging's two flats of בניין האלון 12 are register-shaped and sit in the
37 once that register is loaded.

A6 is what turns a placeholder into a fact: a confirmed `building_handover_protocol` writes
`building.handover_date` and `building.warranty_end_date` (two calendar years later, matching the
fixture). A unit-level protocol writes `unit.warranty_end_date` — R14's override, the only place a
per-flat handover can land, because E4 has no `handover_date` of its own.

## Two protocols, because there are two handovers

The corpus specimen is operator-to-tenant (`מסירת החזקה במושכר לשוכר`). `building.handover_date` is
developer-to-operator. They are not the same act and they are not the same form.

`building_handover_protocol` is the tenth seed type — a row, not a migration, which is A8's open
half used for real rather than demonstrated in a test. 3.1's bar (a type with four fields of its
own costs no DDL) still holds and is still proved on a type that is not in the seed.

The unit-level specimen was enriched with a date (`2024-06-01`), an apartment number (`12`), an
appliance list and meter readings. A second specimen, `docs/corpus/building-handover-protocol.md`,
is the developer handover (`2024-03-01`). Both stay inside the tier-1 bars.

## Flow A6 — propose, confirm, no staging table

The reader is deterministic over the same `documentText` the 3.3 guard already produces. It maps
Hebrew names onto the governed `asset_type` list. It proposes; it does not write.
`handover_date` drives `warranty_end_date` drives the ternary responsibility answer, which is
invariant 5 applied to a date.

**The confirm page recomputes the proposal from the stored bytes.** The document is immutable and
the reader is a pure function, so a staging table would be a second copy of a fact the document
already is. A2's model-based proposals still owe their own answer; this is the deterministic case
only.

Evidence owns the reader and the screen. Estate owns the writes (`applyProtocolSeed`), because a
document module that updated `building.handover_date` would be writing through the wall. A
`building_handover_protocol` is filed under the building (`PlaceKind = BUILDING`).

Confirming the same document twice restates the dates and writes no second water heater.

## Schema

`0012_assets.sql` — `provider` first (three columns, unique on `name`), then `asset` with the
FIELDS sheet's fourteen columns and no others. `space_id` is `NOT NULL` (R3). The class/type pair
is a composite CHECK. `serial_no` carries `-- not-pii:`. Index `asset (space_id)`. The
inspection-date index is deferred to a measurement.

`0013_asset_natural_key.sql` — `UNIQUE (space_id, asset_type)` as an idempotent index. The red that
forced it was `42P10` (`ON CONFLICT` with no matching unique): `CREATE TABLE IF NOT EXISTS` had
left a table from an earlier draft of 0012 without the table-level UNIQUE. The importer's second
run and A6's second confirm both need the key.

Workbook pass first: `asset_type` enumerated on the FIELDS sheet. Against the committed `.xlsx`
baseline (which regenerates cell for cell from `build_model.py`), **exactly two cells changed**,
both on E11 `asset_type` — meaning and note. R1–R18, E1–E16 and every other FIELDS row unchanged.
