**And the half that is new.** 1.6 flipped `enforce_admins: true` as its last act and no slice had

```
$ gh pr merge 15 --squash --admin
```

## Leg 3 — `v0.1.0`, and the first execution of a workflow written three slices ago

`release.yml` was written at 1.6 and had never run. Nor had the two lines 1.8 added to it. The tag
was pushed at 16:00:17Z and prod was serving at 16:02:37Z — **2 m 20 s**, first run included.

```
gate / gate    success   16:00:30 → 16:01:01   31 s
gate / evals   success   16:00:23 → 16:01:00   37 s   ← needs OPENAI_API_KEY, which a called
prod           success   16:01:03 → 16:02:37   1 m 34 s   workflow inherits only via `secrets: inherit`
```

Both halves of the gate ran against the tagged commit through `workflow_call`, which is what makes a
release something other than a redeploy of whatever CI last happened to bless. A red `evals` would
have stopped the release before prod, and that path had never been executed until this tag.

**The migration ran as `app-prod` against a virgin production database, before the revision served:**

```
2026-09-05T16:02:11Z  migrate: applied 4
                        0001_init.sql
                        0002_kernel_durability.sql
                        0003_kernel_settings.sql
                        0004_estate.sql          ← the estate spine, landed at 1.9
                      Container called exit(0).
```

Four, not 1.6's three: prod's first migration run is the first time `0004_estate.sql` has been
applied anywhere but staging and a laptop. The job `dona-prod-migrate` and the service `dona-prod`
were both **created by this run** — bootstrap deliberately creates neither.

```
https://dona-prod-r44j24yuaa-zf.a.run.app/health → {"ok":true,"version":"v0.1.0","db":"up"}
dona-prod-00001-ldz   100%   VERSION=v0.1.0
```

`VERSION` is the tag on prod and the short commit on staging, which is the distinction the two
workflows draw deliberately: a release is named by what was released, a staging revision by what
happened to merge.

## Leg 4 — `v0.1.1`, and the second run is where "repeatable" stops being an assumption

```
run 33976739648  success  16:04:50 → 16:07:15   (2 m 25 s)
  gate / evals   success  30 s
  gate / gate    success  38 s
  prod           success  1 m 35 s
```

```
2026-09-05T16:06:48Z  migrate: nothing to apply — schema is current
```

```
dona-prod-00002-ssd   100%   VERSION=v0.1.1   {"ok":true,"version":"v0.1.1","db":"up"}
dona-prod-00001-ldz     0%   VERSION=v0.1.0
```

The second tag exists because of how `infra/rollback.sh` finds its target: it walks the ready
revisions newest-first and takes the one *after* whichever is serving traffic. Against a service with
a single revision it prints `no previous ready revision to roll dona-prod back to` and exits 1 —
correct, and not the thing this slice is asked to prove. One tag cannot demonstrate a rollback.

## Leg 5 — the rollback, proved by the script's exit code and not by a percentage

`./infra/rollback.sh prod`, no revision argument, so the script derives the target itself:

```
▸ dona-prod: dona-prod-00002-ssd → dona-prod-00001-ldz
Updating traffic...
Routing traffic..............................................................done
Traffic:
  100% dona-prod-00001-ldz
smoke ok — https://dona-prod-r44j24yuaa-zf.a.run.app/health → {"ok":true,"version":"v0.1.0","db":"up"}

▸ dona-prod is now serving dona-prod-00001-ldz, and traffic is PINNED to it.
  The next tag deploy un-pins it automatically (release.yml ends with --to-latest). To roll
  forward by hand:

    gcloud run services update-traffic dona-prod --to-latest --region me-west1 --project dona-v5
```

`EXIT=0`, and the exit code is the proof rather than the traffic line above it. The script ends by
calling `infra/smoke.sh` against the service URL, so a rollback that lands on a revision which boots
but cannot reach Postgres fails **closed**: the `db:up` assertion is inside the same script both
deploy workflows use. Rolling back onto a broken revision is the failure mode that turns an incident
into two incidents, and it is the one thing a traffic percentage cannot tell you.

**And the pinning is visible in the service, not just in the message.** The traffic entry loses its
`latestRevision` flag and starts naming a revision outright:

```
before the rollback   {'latestRevision': True, 'percent': 100, 'revisionName': 'dona-prod-00002-ssd'}
after  the rollback   {                        'percent': 100, 'revisionName': 'dona-prod-00001-ldz'}
```

That missing flag is the whole hazard `docs/pipeline.md` §5 names: the service is no longer following
latest, so the *next* deploy would create a revision serving 0% — a green pipeline that changed
nothing — if `release.yml` did not end with `--to-latest`. Leg 6 is that claim, tested.

## Leg 6 — the post-rollback deploy takes 100%, which is the acceptance bar

`v0.1.2` was cut and pushed while prod was pinned to `dona-prod-00001-ldz`.

```
run 33977045147  success  16:10:42 → 16:13:12   (2 m 30 s)
  gate / evals   success  26 s
  gate / gate    success  28 s
  prod           success  1 m 56 s
```

```
dona-prod-00002-ssd     0%   VERSION=v0.1.1
dona-prod-00001-ldz     0%   VERSION=v0.1.0
```

The `latestRevision` flag is **back**, which is the whole claim. Without `release.yml`'s closing
`--to-latest` step the deploy would have built an image, migrated a database, created a healthy
revision and served none of it — the failure mode `docs/pipeline.md` §5 describes and the only one in
this chain that reports success while doing nothing.

## Leg 7 — prod is parked, deliberately and visibly

Prod's database is idle from here until week 12, when prod tagging starts. Between this round trip
and the pilot there is nothing in prod to serve and nobody to serve it, so it is stopped rather than
left billing for eleven weeks:

```
$ gcloud run services update dona-prod --min-instances 0 --region me-west1
$ gcloud sql instances patch dona-prod --activation-policy=NEVER

dona-prod     STOPPED    NEVER      ← the instance, its storage and its data are all retained
dona-staging  RUNNABLE   ALWAYS     ← untouched: staging is the delivered artifact every week
```

**Two commands, not the one `tasks/todo.md` named.** `release.yml` deploys prod with
`--min-instances 1`, which is right for a live production service and wrong for a parked one: an
always-warm instance would have billed for eleven weeks in front of a stopped database. The workflow
keeps `--min-instances 1` and week 12's first tag re-applies it automatically — so of the two, only
the database restart is a manual act, and it is carried as one.

Setting the minimum to zero is a configuration change, so Cloud Run made a revision of it:
`dona-prod-00004-nkm`, same image and same `VERSION=v0.1.2` as 00003, serving 100%.

**And the parked service is honest about being parked:**

```
$ curl https://dona-prod-r44j24yuaa-zf.a.run.app/health
HTTP 503  {"ok":false,"version":"v0.1.2","code":"unavailable","message":"database unreachable"}
```

That is `/health` doing exactly what 1.3 built it to do. A parked prod that answered `ok:true` would
be the "deployed but silently broken" state the smoke script exists to make impossible — here the
same assertion says, correctly, that the service is up and its database is not.

## Observations, which are not assertions

**`environment: production` currently buys nothing, and this slice is how that was found.**
`release.yml` names a `production` environment; no such environment existed in the repository until
this tag, and GitHub created it implicitly on first use — **with no protection rules at all**:

```
$ gh api repos/RandomWilder/dona-v5/environments
{"name":"production","rules":[],"branch_policy":null}
```

So today a `v*` tag is the only thing standing between a commit and production. That is the correct
design for this week, when the point is to exercise the path unattended. It is the wrong one from
week 12, when a tag reaches real tenants: the environment wants a required reviewer and a deployment
tag policy limited to `v*`. Carried, below, rather than fixed here — turning on a reviewer gate in
the same slice that needs six unattended releases would have proved neither.

**Release timings, three runs, first one included.** 2 m 20 s · 2 m 25 s · 2 m 30 s end to end, of
which the gate is ~30 s and the prod job 1 m 34 s – 1 m 56 s. Prod releases cost roughly 35 s more
than a staging deploy, all of it in the extra gate run against the tagged commit — which is the price
of not shipping whatever CI last happened to bless, and it is cheap.

**`release.yml` does not print the image size and `deploy.yml` does.** Trivial today because both
build the same Dockerfile, and worth a line in the workflow-hygiene pass rather than a change now.

**The prod database holds the schema and nothing else.** Four migrations, zero rows. The estate
tables exist in production before any tenant data does, which is the order R4 asks for.
