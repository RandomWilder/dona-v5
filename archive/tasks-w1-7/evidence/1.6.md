## The acceptance proof, and it is a sequence rather than a check

**A red commit pushed straight to `main` did not reach staging.** Commit `ed92f87` added a test that
asserts `'red' === 'green'` and was pushed directly to `main` — no PR, no review — which is possible
only while `enforce_admins` is `false`, and that flag was `false` for exactly this reason.

```
CI      33963619478   failure   25 s   ed92f87
Deploy  33963639747   skipped    7 s   ← if: github.event.workflow_run.conclusion == 'success'
```

Staging, before the red push and after it, unchanged:

```
dona-staging-00002-jst  100%   {"ok":true,"version":"958f8b9","db":"up"}
```

`958f8b9` is the *previous* commit. The red one never became a revision, never became an image tag
and never ran a migration.

**What actually enforces this is the trigger, not the branch protection.** Protection blocks a merge;
an admin can push past it, and it says nothing at all about deployment. `deploy.yml` fires on
`workflow_run` — the CI *result* — and its one job is gated on `conclusion == 'success'`, so the
failing gate leaves the previous revision serving whether the commit arrived by merge, by admin push,
or by anything else that moves `main`.

**And the recovery leg, which is the half that proves the first half was not just an outage.** The
revert `84ebd92` went green and staging moved on its own:

```
CI      33963662163   success   30 s   84ebd92
Deploy  33963686519   success   1 m 42 s  → dona-staging-00003-247, 100%, version 84ebd92
```

## The migration entry point, and where it runs

`kernel/migrate.ts` had no caller outside the test run. The schema existed in the repository and
nowhere else, so the first deploy would have served `/health` against an empty database — `/health`
would even have said `db:up`, because `SELECT 1` does not need a table.

`src/migrate.ts` is the entry point and `npm run migrate` is the command. Proved locally against a
throwaway database before it was ever pointed at Cloud SQL, both branches:

```
$ DATABASE_URL=…/migrate_probe npm run migrate     $ npm run migrate            (already current)
migrate: applied 3                                 migrate: nothing to apply — schema is current
  0001_init.sql
  0002_kernel_durability.sql
  0003_kernel_settings.sql
```

Then the same code against the real Cloud SQL instance, from the deploy — the job log, which is the
record anyone reads afterwards:

```
2026-09-05T11:26:49Z  migrate: applied 3           ← first deploy, virgin database
                        0001_init.sql
                        0002_kernel_durability.sql
                        0003_kernel_settings.sql
                      Container called exit(0).
2026-09-05T11:31:45Z  migrate: nothing to apply — schema is current    ← second deploy
2026-09-05T11:35:31Z  migrate: nothing to apply — schema is current    ← third
```

**It runs as a Cloud Run job, as the runtime service account, before the new revision serves.** Three
decisions in that sentence, and the middle one is the important one.

**Not from the CI runner.** `staging-database-url` is a unix-socket URL (`?host=/cloudsql/…`) and
1.5 bound it to `app-staging` alone. Migrating from the runner would have needed the deploy identity
granted `secretmanager.secretAccessor` on the database URL plus `cloudsql.client` plus a proxy — in
other words, making the CI identity able to read prod's connection string, and connecting to the
database from outside the perimeter, in exchange for a build step. The job reuses the runtime
account, the same per-secret binding and the same `/cloudsql` mount the service gets, so **the runner
orchestrates and never holds the credential.** No IAM change was needed: `run.admin` and
`iam.serviceAccountUser` on the deploy account already cover deploying and executing a job.

**Before the deploy, not after.** `docs/pipeline.md` §5 read `deploy → migrations → smoke`, which
puts new code in front of the old schema for the length of a migration. Migrations are append-only,
so old code against the new schema is the safe direction; the arrow was corrected in §5 in the same
change as the workflows, rather than the workflows quietly disagreeing with the document. `--wait`
makes the job's exit code the deploy's, and `--max-retries 0` means a bad migration fails once rather
than being retried three times against a database it has already half-changed.

**Two more values worth naming.** `VERSION`, not v3's `APP_VERSION` — `src/serve.ts` reads `VERSION`,
and a verbatim lift would have shipped `0.0.0-dev` on a live URL, which is exactly the "the injection
did not happen" signal that would then have gone unnoticed. And `--set-secrets` mounts
`DATABASE_URL` alone: v3 mounts four staff seed secrets and an OpenAI key, none of which exist in
this project (1.5 dropped the first four deliberately, and `staging-openai-api-key` has no value
yet). Mounting a secret that does not exist fails the deploy, so copying that line would have failed
the first deploy for a reason unrelated to anything this slice is about.

## What `evals` is still not

`ci.yml` has one job. v3's has two, and the second is not lifted, because a job that exits 0 on an
empty suite is a green check that proves nothing — which is precisely what made 1.1's `evals`
context a permanently failing promise. 1.8 writes the harness, watches the job go red with the
database URL unset, and re-arms the context then.

## Observations, which are not assertions

**The image is 330 MiB and the build is most of the deploy.** `docker build` plus two pushes is
~35 s of a 1 m 53 s first deploy; `pdfjs-dist` is ~35 MB unpacked and `google-auth-library` brings
its own tree. Nothing is wrong with it — Cloud Run pulls from Artifact Registry in-region — but it is
the number to watch when the deploy starts feeling slow, and the reason the Dockerfile's comment
about "pg and fastify are the only runtime dependencies" was corrected rather than left as a
pleasant memory of 1.3.

**GitHub is deprecating Node 20 actions.** Every run annotates: `actions/checkout@v4`,
`actions/setup-node@v4`, `google-github-actions/auth@v2` and `setup-gcloud@v2` target Node 20 and are
being forced onto Node 24. Nothing fails today. It becomes a broken pipeline on someone else's
timetable, so it is carried rather than noted.

**`strict: true` on the required check** (1.1's setting, kept) means a PR must be up to date with
`main` before it merges. With one developer that costs nothing; it will cost a rebase the first time
two branches are open at once.
