## Red first, twice, and one of the reds was a surprise

### The natural keys

The claim `0005_` exists to make true is that an import can be run twice. So the defect was measured
against `0004` alone before it was fixed, with a plain-`INSERT` importer over the same fixture:

```
after run 1: { project: '1', building: '1', space: '184', unit: '72'  }
after run 2: { project: '2', building: '2', space: '368', unit: '144' }
```

Two buildings at one address, and 144 apartments in a 72-apartment building. With the keys in place
the same plan twice is `created: 0` on every table, and — the half that matters more — every
`building_id` and `unit_id` is identical across the two runs. A re-import that renumbered its units
would satisfy a count and break everything that ever pointed at one.

The five schema cases were run against the pre-`0005` schema in a rolled-back transaction with the
three indexes dropped and `address_key` removed. Every duplicate was accepted:

```
 same_tender_code | same_address | same_space_name
------------------+--------------+-----------------
                2 |            4 |               2
```

`same_address` is four because the four rows are `Rakefet 12`, `Rakefet 12`, `  Rakefet  12 ` and
`RAKEFET 12` — the whitespace and case variants a second export brings, which is the whole reason
`address_key` is a generated column rather than a normaliser the importer has to remember to call.

Also asserted: nothing may write `address_key` (`428C9`), and a space name may repeat across kinds
and across buildings — the half of a natural key that stops it being a global lock.

### The token guard, and the defect it was carrying

Owed by 1.4. v3's `kernel/ui/tokens.test.ts` was tripped on purpose, four ways:

```
hex colour           #1d2d3d                     ✖ caught
font-family          font-family: Heebo          ✖ caught
physical property    padding-left: …             ✔ PASSED    ← should have failed
physical property    border-left-width: …        ✔ PASSED    ← should have failed
physical value       text-align: left            ✔ PASSED    ← should have failed
```

v3's pattern is `(?:^|[\s;{])(?:left|right)\s*:`. The character before `left` in `padding-left` is a
hyphen, which is not in that class — so the guard caught a bare `left:`, which nobody writes, and let
through every property anyone does. It has been decoration for its most common case for a year, in
the file whose comment says the discipline erodes in the screens.

Found by tripping it rather than by reading it, which is exactly why the ritual is *trip it*. v5's
`tests/ui/tokens.test.ts` matches the hyphen-separated segment (`(?:[a-z]+-)*(?:left|right)(?:-[a-z]+)*`)
plus a second pattern for the physical *value*, and `--color-bright` and `copyright` stay out of it.
All five forms above now fail. Recorded in [docs/from-v3.md](../../docs/from-v3.md) beside the
`kernel/db.ts` defect, for the same reason: a lifted file is inherited, not trusted.

## Structural calls

**`address_key` is a generated column, not a unique constraint over `(city, address_line)`.** The
constraint would have been one line and no new column, and it would have treated `Rakefet 12` and
`  Rakefet  12 ` as two buildings. Normalising in the database rather than in the importer means
every writer gets it, including the week-2 Priority import and whatever writes after that; an
application-level normaliser is one the next caller has to remember. The column carries no fact — it
is `GENERATED ALWAYS`, nothing writes it, and it is derived from the two columns that do — which is
the same standing `unit`'s three constant discriminators have had since 1.9.

**`unit` gets no natural key.** R2 made a unit's identity its space's (`Unit.unit_id =
Space.space_id`). A second key on `(building_id, unit_number)` could only ever disagree with the
first, and the disagreement would surface as two rows for one door.

**The screens are server-rendered, with no client JavaScript at all.** v3's were static shells that
fetched JSON. Rendering on the server means there is no JSON API to scope before the screens can be
shown to anyone — which matters this week specifically, because there is no authentication yet. The
kernel's `h` template, lifted at 1.4 and never called until now, escapes every interpolation and has
no raw escape hatch; `tests/ui/tokens.test.ts` asserts a building name of `<script>alert(1)</script>`
comes back as text.

**`npm run seed` is wired into no workflow, and that is the point.** `deploy.yml` and `release.yml`
are untouched. A fixture that seeds itself on every deploy reaches production the next time a `v*`
tag is cut, and prod is exactly where mock buildings must never appear. Staging is seeded by hand,
once, as a Cloud Run job from the deployed image running as `app-staging` — the same pattern and the
same reasoning as the migrate job: the CI runner orchestrates and never holds the database URL.

**`src/estate/test-support.ts` exists because a passing suite went red on a seeded machine.** The
importer cases count rows, and `inRolledBackTransaction` gives a case a database it cannot dirty, not
an empty one. After `npm run seed` the importer suite reported that its first run created nothing —
a failure with no defect behind it, on a machine that did what `AGENTS.md` says. `inEmptyEstate`
empties the four estate tables at the top of the transaction that is about to be rolled back, so
nothing is lost and the case starts where it can reason from. It is in `src/estate/` and not in
`kernel/pg-support.ts` because it names domain tables.

## The fixture, and what it is not

**Nothing in it is real, by decision.** The director's call this week: functionality is established
against mock addresses and example leases, and real data is applied to it afterwards — which is
[pipeline.md](../../docs/pipeline.md) §1 principle 5, mock data as the development substrate by
design and not by shortage. The week-1 demo line in `tasks/todo.md` and `tasks/roadmap.md` read
"real names, real addresses"; both were corrected in this slice rather than in the room.

What is deliberate is the coverage. 72 units over 12 floors, asserted in `importer.test.ts` rather
than described, because a fixture that quietly became 72 identical apartments would still satisfy a

## The defect this slice shipped, and what CI did with it

Recorded here because it is the most useful thing in the file. `ImportReport` was a `count(*)` over
each table before the import and after it, with `created` as the difference. It passed locally, it
passed on the slice's own PR, and it **failed `gate` on the documentation-only PR that closes this
slice** — nothing between the two commits but markdown.

```
✖ counts the units rather than reading a column
  AssertionError: 2 !== 1
```

`node --test` runs test files in parallel, and `src/estate/routes.test.ts` **commits** — it has to,
because the routes read through the pool and a rolled-back transaction is invisible to them. So a
second suite's building was visible to a case that had asserted the table held one.

**The flake was the symptom; the count was the defect.** A whole-table count is not a fact about
*this* import. Another suite moves it, another environment moves it, and a developer's own
`npm run seed` moves it — so an import reporting `created: 0` because somebody else's row happened to
be there would be reporting the wrong thing while looking exactly right. That is the failure a green
number hides, and it would have reached the week-2 import of 1,500 real units.

`ImportReport` is now `{ created, updated }` per table, counted from the statements themselves:
`(xmax = 0)` on the row an `ON CONFLICT DO UPDATE` returns is true when the row was inserted and
false when it was updated. It says strictly more than the version it replaces — a second run of the
Shoham plan is `created: 0, updated: 184`, and the update count is the proof the rows were *reached*
rather than skipped by a conflict target that matched nothing.

Every estate suite now carries a city of its own, none of them the seed fixture's, and every query is
scoped to the building it is about. The last assertion that could see another suite's rows —
`listBuildings` returning exactly one — finds its own building instead: `listBuildings` returns the
whole table because that is what the screen shows, and a case that asserts on rows it did not create
fails for someone else's reason. `src/estate/test-support.ts`, which emptied the four estate tables
at the top of each rolled-back transaction, is deleted with it. It was the wrong answer to the right
question, and it would have wiped a developer's seed on every test run.

Six consecutive clean `npm test` runs against a seeded database, and twelve of the estate suites
alone, before it went back up.

`{"ok":true,"version":"8feced2","db":"up"}`. `0005_` was applied by the migrate job before the

Then `dona-staging-seed`, created here from the same image as the revision and running as
**`app-staging`** — the runtime account, not the deploy one, for the reason §5 of the pipeline gives
about the migrate job: `staging-database-url` is readable only by `app-staging`, so seeding from a
runner would mean handing a CI identity the database URL. Executed twice, on purpose:

```
dona-staging-seed-dc44f     project 0 → 1     building 0 → 1     space 0 → 184     unit 0 → 72
dona-staging-seed-x5qfd     project 1 → 1     building 1 → 1     space 184 → 184   unit 72 → 72
```

and not only in a transaction that was going to be rolled back anyway.
