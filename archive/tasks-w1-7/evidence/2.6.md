# Slice 2.6 — Browse at portfolio scale

**Closed 2026-09-06.** Week 2's last slice and the week's demo: the same URL as week 1, now at
1,500-unit volume from a generated register, with the query timings that volume exists to produce.

Four things were owed to this slice by earlier ones, and all four are decisions that were
deliberately deferred until there was a row count and a timing in front of them. Two of them are
index questions and **they were answered in opposite directions**, which is the part of this slice
worth reading.

---

## The generated register — 1,500 units, 2,908 rows, zero rejects

Volume and realness are different facts, and an index decision needs only the first. The real
register belongs to step 4 of the method ([SPEC-flows.md](../../SPEC-flows.md)) and is 2.5's; what
2.6 needed was 1,500 units in the same twenty-two columns, loaded through
`npm run import:register`, so that the path under measurement is the path that ships.

`src/register/fixtures/generate.ts` produces it. Same seed and same day, same bytes — `today` is a
parameter and never a clock reading, and here it has a second job, because "leases ending in the next
60 days" is a question about a day and a fixed one would answer it emptily.

```
generate: buildings — 37          generate: occupiedToday — 1218
generate: units — 1500            generate: expiringWithin60 — 144
generate: tenancies — 1674        generate: recycledNumbers — 174
generate: parties — 2871          generate: splitIdentifiers — 37
generate: rows — 2908             generate: guarantors — 338
                                  generate: companies — 56
                                  generate: buildingsWithoutProject — 5
```

**It is the nine-row fixture at volume rather than fifteen hundred copies of one household**, and
every case that breaks an importer is counted above: a recycled number, one person under two
spellings of one ת.ז., a guarantor, a company whose name carries a quotation mark, a unit let twice,
a lease that has not started, a building with no project.

**Zero rejects, by construction, and that is a deliberate limit on what this file can prove.** A
generated register that loses rows measures the generator. How many rows a real register loses to
`one_active_tenancy_per_unit` is a fact about the client's data, and it stays with 2.5.

Two numbers cross-check the generator against the application rather than against itself: the
buildings list renders **1218 מאוכלסות היום** and the expiring screen renders **144 חוזים**, which are
the generator's own `occupiedToday` and `expiringWithin60` arrived at by an entirely different route —
through the CSV, the importer, the database, `src/scope/` and two screens.

### The import, timed — and the batching question answered

| | wall | per row | created |
|---|---|---|---|
| first run | **6.481 s** | 2.23 ms | 1,500 units · 1,674 tenancies · 2,871 parties · 2,908 tenancy_party |
| second run, same file | **5.989 s** | 2.06 ms | **0 in all nine tables** |

`SPEC-register.md` said 2.6 was the slice that measured the savepoint-per-row cost and decided
whether to batch. Nine upserts and two savepoint statements a row is about **32,000 round trips** for
this file, and it takes six and a half seconds. **The savepoint stays.** A register is loaded by a
person who chose the file; six seconds is not a number worth trading a line number for, and batching
would coarsen the reject boundary to buy something nobody is waiting on. Reopened if a register
arrives an order of magnitude larger.

`created: 0` on the second run is the weak half of idempotence and the counts show the strong half:
`party` created 2,871 and updated 37 on the *first* run, which is the 37 split identifiers converging
on parties already written — `national_id_key` doing at volume exactly what 2.4 built it for.

## The two index decisions, and they went opposite ways

`npm run measure:scale` (`scripts/measure-scale.ts`) is the instrument, beside `npm run measure` and
gating nothing. It explains and times **the strings the screens run** — `MEASURED_QUERIES`,
`ISOLATION_JOIN_SQL` — never a copy typed into a script, because a measurement of a query the
application does not run is worth less than no measurement at all: it is believed.

**No number here is asserted anywhere**, for the reason `docs/pipeline.md` §7 gives about embedding
distances. A timing is weather. The whole-query medians below moved by 30% between two runs of the
same code on the same laptop, which is exactly why the two decisions rest on isolated A/B pairs taken
in one session instead.

### Added — `tenancy (end_date) WHERE status = 'ACTIVE'`

2.2 left it out on the record. The tenancy access alone, three runs each, the index dropped inside a
transaction that was rolled back:

| | plan | buffers | time |
|---|---|---|---|
| without | Seq Scan on tenancy, 1,530 rows discarded | 53 | 0.080 – 0.086 ms |
| with | Bitmap Index Scan | 2 on the index, 51 on the heap | 0.032 – 0.043 ms |

Whole-Q5 medians were 0.82 ms and 0.69 ms, and those two are within this laptop's noise of each
other — which is why the isolated pair is what the decision rests on.

**Twice the speed is not the argument.** Nothing here is slow at 1,674 tenancies. The argument is the
shape: the scan reads every tenancy the company has ever signed and a tenancy table only grows, while
the index reads two pages to find the answer. **Partial on `ACTIVE`**, which is
`one_active_tenancy_per_unit`'s move at 2.2 and for the same reason — `ACTIVE` is exactly the set the
question asks about, so the index holds 144 rows of 1,674 and only an `ACTIVE` row pays on write.

### Not added — a btree on `party_contact (channel, value)`

2.1's reasoning was right on the facts. The same lookup, three values, one session, over 2,871
contacts:

| index | buffers | time |
|---|---|---|
| GiST — `contact_value_resolves_to_one_party` | 4 – 6 | 0.031 – 0.062 ms |
| btree — `(channel, value)` | 2 – 3 | 0.009 – 0.017 ms |

Three times the time and twice the pages, on the first hop of the hottest query in the system once
the agent is live. Which reads like a case for adding it, and is not:

> **With both indexes present the planner chose the GiST one every time.** Its estimated startup cost
> is lower (0.14 against 0.28) and so is its total (8.16 against 8.30) — inside the join and
> standalone, warm and cold.

So the btree would be maintained on every insert into a table the register writes 2,871 rows into,
and read by nothing. **An index the planner will not choose is not an optimisation, it is a write
cost with a comment.** This is 2.1's question answered rather than deferred a second time: the gain
is real, it is 0.04 ms a lookup today, and it is unreachable while the exclusion constraint's index
is the cheaper plan. What reopens it is carried into week 12 in [roadmap.md](../roadmap.md), and the
fix then is not "add the btree" — that was tried here — it is changing what the exclusion
constraint's index looks like to the cost model.

## The occupancy chip did not call the function the plan named

`tasks/todo.md` said the chip would call `resolvePartiesInUnit`. At portfolio scale that is the wrong
call, and the table above says why: the grid asks it of every card, so a sixty-unit building is
**29.68 ms and sixty audit rows for one page load** against **0.94 ms and one**.

The round trips are the smaller half. **An access log in which one browse is indistinguishable from
sixty lookups is worse than useless in the review it is kept for**, and every scoped read is logged
by design (`SPEC.md`, security defaults). So `src/scope/` gained `resolveOccupiedUnits(db, unitIds,
today)` — the units a caller is about to draw, or `null` for the portfolio; one query, one audit line,
and the tenancy-active predicate still in the one file guard two protects.

Three properties came with it and each is a case in `src/scope/scope.test.ts`:

- **a vacancy is an absent row**, so an ended lease reads as a vacancy and never as the last
  household (R5, from the grid's side);
- **a guarantor is not counted as a resident** — on the lease, not in the apartment (foundation rule
  7, and E8's own note) — while the tenancy still counts as let;
- **a party is counted once however many numbers they are reachable on**, because the view fans a
  party out over their contact rows and a count that forgot to be `DISTINCT` would report a
  two-phone household as two people. A chip that lies quietly is worse than one that is absent.

## Three screens, and the rule all five now keep

`GET /` stopped being a 302 (1.11's carry). `GET /estate/search?q=` and `GET /estate/expiring` are
new. The occupancy chip is on the unit grid and the totals are on both list screens.

**The root index runs no query.** A portfolio headline belongs on the buildings list, where those
numbers are already being read for the cards; an index that ran three portfolio queries to render
three links would be a worse root than the redirect was. It moves to the composition root the week a
second *module* has a screen — week 5's — because an index of screens is not estate's fact.

**No name and no number reaches any of the five screens**, and it is a rule rather than a discipline
the views remember: they are never handed the data. Search covers buildings and units and never
`party`; the chip is a state and a count. `/estate` has no session until week 5, and the week the
register arrives is the week that stops being an abstraction. `tests/ui/tokens.test.ts` now asserts it
from outside as well — every screen, no `05x` number, no `+972`.

**A city matches buildings and not units.** A city holds hundreds of apartments and sixty arbitrary
ones is a worse answer than the buildings that contain them; a building name or an address narrows to
one building and matches both.

**The search term's LIKE metacharacters are escaped**, and that is the one genuinely hostile input
these views have ever been handed. A bound parameter is not the same thing as a safe pattern:
unescaped, a lone `%` matches the whole portfolio and `%%%` scans it three times. Asserted at three
levels — the read model, the route, and the rendered page.

Every new screen is in `tests/ui/tokens.test.ts`'s `SCREENS` registry, which is the file's own rule
(*"adding a screen means adding it to SCREENS"*), and the chip is asserted in both states because a
card that is let and a card that is not are different markup.

## What the volume found that review would not have

**Three suites went red on `terms_profile_natural_key` the moment a generated register sat in the
development database.** `src/tenancy/schema.test.ts` and 2.4's own nine-row fixture both name a
profile *נספח תחזוקה — תקן*, and `terms_profile.name` is globally unique — a profile is identified by
its name and by nothing else (0009).

This is the third time this repository has met the same lesson and the first time on a key nobody had
thought of: 1.11 met it on addresses, 2.4 met it on phone numbers and identifiers and namespaced its
cities, its phone block and its ת.ז. block — and then named its maintenance annexes something a real
register will also name them. Every fixture profile now carries the suffix its cities do, and
`fixtures/load.ts` records why. **The suites had been passing because the fixture that would collide
with them had always been rolled back.**

**The scope suite's own fixture could only ever seed one household.** `seed()` hardcoded
`national_id = '040000001'` and a profile called `standard`, so the first case in this repository to
seed two parties in one transaction hit `party_natural_key` — and would have hit
`terms_profile_natural_key` immediately after. Both are the same class as above and neither had been
noticed, because until 2.6 nothing had needed two.

**The generated register wrote a second contact for two parties, and the count said so.** The first
1,500-unit import reported `party_contact created 2873` against 2,871 parties. `recycles()` was
building the new holder with `{...party, phone}` — a copy — so the register's own memory held a
number the file never wrote, and the next row to re-use that person gave them a second one. Fixed by
handing the inherited number to the party's constructor rather than pasting it onto the result; the
counts now read 2,871 and 37, which are the parties and the split identifiers exactly.

**The required gate had a latent `40P01` in it, and this slice made it fire.** After the new scope
cases landed, `npm test` failed roughly one run in three — always in `tests/policy/`, always
*"resolves to the new holder's own unit and never to the previous one"*, always **deadlock
detected**. Nothing about that case was wrong. `tests/policy/recycled-number.test.ts`,
`src/parties/schema.test.ts` and `src/scope/scope.test.ts` had all been seeding
**`+972521234567`**, and `tests/policy/guarantor.test.ts` and `tests/policy/isolation.test.ts` had
both been seeding `+972501112233`. `node --test` runs files in parallel against one database, so two
transactions inserting one contact value on overlapping days each wait on the other's speculative
insertion inside `contact_value_resolves_to_one_party`.

**2.4 diagnosed this exact failure and fixed it for register fixtures**, which is why the rule
"every fixture owns a phone block" is written in `fixtures/load.ts`. It was never applied to the
suites, which had been sharing numbers since week 2 and had been getting away with it because their
transactions were short. Widening one suite's window by four cases was enough. Each suite now owns a
block — `0522…` for parties, `0523…` for scope, and the two policy files no longer share one — and
the suite ran clean **six times consecutively** afterwards, where before it failed one in three. A
flake in a required gate is worse than a red one: it teaches people to re-run.

**The measurement measured the wrong building first.** The busiest building in the database is the
week-1 Shoham fixture, which carries 72 units and no tenancy at all, so the occupancy probe reported
zero occupied units and the N+1 comparison compared two ways of finding nothing. The probe now picks
the busiest building **that has leases on it**.

## Carried

- **A register-created building's `handover_date` and `warranty_end_date` are a lease's dates**, and
  at volume it is visible on screen: 2.4's `upsertUnitRow` writes `tenancyStart`/`tenancyEnd` into
  them because a register carries no handover date and both columns are `NOT NULL`, so the last row
  of a building wins. It was invisible at nine rows and it is a date on a card at 1,500. **Not fixed
  here on purpose** — week 3's handover protocol (slice 3.5) is what brings the real fact, and
  inventing a better-shaped guess in week 2 is work week 3 deletes. Owned by **3.5** in
  [roadmap.md](../roadmap.md) and [todo.md](../todo.md).
- **The btree on `party_contact (channel, value)`**, above — reopened at **week 12**, when the agent
  is live on the pilot and this table stops being 2,871 rows.
- **The root index moves to the composition root at week 5**, when the staff console gives a second
  module a screen. Recorded in `SPEC-estate.md` with its trigger.
- **A register cannot express a vacant unit.** The file is one row per party on a tenancy, so a unit
  with no lease at all has no row and does not exist. The generated register shows vacancies through
  ended and draft tenancies, which is what a real register does too; if the client's export carries
  empty apartments, that is a format question for **2.5**.

### The register is on staging — 1,500 units, through a Cloud Run job

`npm run seed:register` as `dona-staging-seed-register`, from the image about to serve, as the
**runtime** service account, with the same flags the migrate job uses. It is deliberately not in any
workflow, for `npm run seed`'s reason and `npm run import:register`'s: loading data is something
somebody runs on purpose.

Every count is identical to the local run, which is the generator being deterministic across two
machines from a seed and a day: 37 buildings, 1,500 units, 1,674 tenancies, 2,871 parties, 2,908
rows, **0 rejected**.

**The one number that is not identical is the one worth having.**

| | wall | per row |
|---|---|---|
| local, docker Postgres on the same machine | 6,481 ms | 2.23 ms |
| staging, Cloud SQL over a unix socket | **98,713 ms** | **33.95 ms** |

**Fifteen times slower, and it is round trips rather than work.** The importer issues nine upserts
and two savepoint statements a row — about 32,000 round trips for this file — and on staging each one
crosses a socket to a shared-core instance instead of to a container on the same kernel. This does not
change the batching decision, and it does sharpen it: 99 seconds for the whole register is still a
person watching a script they chose to run. **The threshold to revisit is stated rather than left to
feel: a register that takes more than about ten minutes**, which on these numbers is roughly 18,000
rows. Dona Dom's 1,500 units are not close to it, and neither decision should be taken again without
a timing.

Whole-page HTTP from a laptop to `me-west1`, five requests each, seconds:

|---|---|
| `/` — the index, **which runs no query at all** | 0.175 · 0.174 · 0.179 · 0.202 · 0.232 |
| `/estate` — 38 buildings, portfolio occupancy over 1,500 units | 0.244 · 0.263 · 0.244 · 0.254 · 0.233 |
| `/estate/expiring` — Q5, 144 leases | 0.294 · 0.213 · 0.257 · 0.226 · 0.273 |
| `/estate/search?q=רקפת` — 65 results | 0.173 · 0.172 · 0.244 · 0.176 · 0.235 |

**Search is a quarter of a second against a bar of one second, on the machine the demo runs on.**

The root index turned out to be the control the measurement needed: it runs no query, so its ~0.175 s
*is* the TLS-and-network floor from here, and every other screen's own work is the 0.02–0.09 s on top
of it. That was not why the root was left query-free, but it is what made these four numbers readable.

### One thing staging showed that local did not

**«בעוד 1 ימים».** The expiring screen special-cased "today" and nothing else, so a lease ending
tomorrow rendered a plural Hebrew count — the first thing a Hebrew speaker reads on that screen, and
it was on staging before it was noticed. Hebrew counts in three: היום · מחר · יומיים · N ימים.
Fixed, and `tests/ui/tokens.test.ts` now renders all four and fails on the plural one, because the
next screen with a countdown on it will be written by somebody who did not read this file.
