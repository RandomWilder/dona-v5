00 — METHOD

How to describe a data model so it survives

The notebook sketch was drawn in attribute mode — what does each thing have. That mode produces boxes that grow until they hold everything and explain nothing. Two habits fix it, and they are worth more than any single correction below.

Habit one — sort every field into one of three planes

A box becomes unwieldy the moment it holds more than one kind of statement. The notebook Apartment held all three at once, which is exactly why it felt tangled: equipment is a fact about the world, liabilities is a rule about what should happen, and neither belongs beside the other.

PlaneAnswersTestIn the sketch
Record What is true, and during what period Could a court establish it from the world? Building, Apartment, Tenant, equipment
Evidence Where a value came from, and how sure we are If disputed in a year, what do I put on screen? Document, Schema, validated
Policy What should happen, given the facts Could ops change it without a release? liabilities, dependencies docs

Policy stored as a fact is the costliest mistake of the three. Freeze “who pays for a broken oven” onto the apartment row and you can no longer answer what did the rule say last March — which is the only question a dispute ever asks.

Habit two — run every field through five tests

These are the whole method. They are cheap to apply at the moment a field is proposed and expensive to apply after it has been in production for six months.

TEST 01 — IDENTITY

What makes this row this row, forever?

If a human can type it, edit it, or reformat it, it is an attribute — never a key. Identity is always a surrogate id the system mints and nobody ever sees or quotes.

Sketch failed at Apartment.Building Address. Addresses get corrected by the municipality, transliterated three ways, and typed with and without a comma.

TEST 02 — TIME

True forever, or true during an interval?

If during an interval, it is a row with dates, not a column. Tenancy, warranty, rent amount, terms profile, provider assignment — all intervals.

Sketch nearly passed at Current tenant (+past +upcoming). Those are not three fields; they are one table and a date comparison.

TEST 03 — DERIVATION

Can this be computed from other facts?

If yes, it is a view, not a stored column. Stored derivations rot silently — nothing throws an error, the value is simply wrong, and you learn about it from a tenant.

Sketch failed at Apartment.Current tenant. This is the tenant-isolation guarantee, and it should not depend on anyone remembering to update a column on move-out day.

TEST 04 — PROVENANCE

If disputed in a year, what do I show?

Any value read off paper carries (document_id, page, bbox, confidence, promoted_by, promoted_at). That is the difference between the system says ₪4,800 and here is the clause it read.

Sketch reached for it with Document.validated — but a boolean discards the trail instead of keeping it.

TEST 05 — ISOLATION

Can I draw a line from a phone number to this row?

If a table cannot be scoped by tenancy, the agent may not read it. Run this at the moment a table is added — it is free then and a migration later.

Applies to every table. The client constraint is absolute: a tenant only ever receives information derived from their own documents and the global knowledge base.

02 — ISOLATION

Why the hard constraint is a schema decision

“A tenant must never receive another tenant's information” cannot be enforced in a prompt. It is enforced by the shape of the join — and specifically by whether tenancy is stored or derived. This is test 05 drawn out.

View two

The Lifecycles

What changes, and what makes it change. Three things in this system have a life: a tenancy, a document, and a service call. None of them is visible on an entity diagram, which is why an ERD alone always feels like it is missing the hard part — it is.

NOTATION — STATE MACHINE · SOLID ORANGE = A DOCUMENT CAUSED IT · DASHED BLUE = A DATE CAUSED IT

03 — TENANCY

Occupancy changes for two different reasons

Some transitions happen because a piece of paper arrived. Others happen because a date passed and nobody did anything at all. Confusing the two is how a system ends up believing a tenancy is still active nine months after the tenant moved out.

The row is mutable; the log is not. Tenancy is a normal row that reads fast, and every transition appends a TenancyEvent with (field, old→new, actor, source_document_id). Deliberately not event-sourced — state is never replayed from the log. The log exists to answer questions, not to serve reads.

04 — DOCUMENT

Paper is immutable; the reading of it is not

A document never changes after it lands. Everything that looks like an edit — a correction, a newer lease, a re-scan — is a new row that supersedes the old one. That is what makes the archive worth anything in a dispute.

05 — SERVICE CALL

The half the agents actually live in

The notebook modelled who lives where and what paper exists. This is the other half — and where the engineering difficulty really sits.

Break-glass is a state, not a feature. An ops user must be able to seize any conversation mid-sentence; the agent then goes silent on that thread and stays silent until explicitly released. Model it as a flag on Conversation checked before every outbound message — not as a UI affordance bolted on later.

06 — RESPONSIBILITY

Who pays is a function, not a property

The notebook put liabilities on the apartment. It is not a fact about a flat — it is a lookup over four dimensions, two of which change over time. Illustrative rows below, keyed on a single terms profile.

The two highlighted rows are why תקופת הבדק is not an afterthought. Same fault, same lease, same building — and a different payer depending only on whether the appliance is still inside its defect period. A binary tenant-or-landlord model cannot express that row pair, which is why responsibility here is ternary. Note the last row: a rule that changed in April 2026 does not overwrite its predecessor, it supersedes it by date, so a ticket opened in March still resolves against the March rule.

Every decision snapshots the rule that produced it. When a ticket resolves responsibility, it writes both responsible_resolved and policy_version_id. Without the second field the matrix is only useful for the present, and the one question a dispute asks is about the past.

08 — INGESTION

Getting Dona Dom's Drive into the model

The documents are already being organised per building and per apartment on Google Drive. That is close to the best case — the backfill is an ingestion problem with a known source, not an expedition. Two structural rules keep it from becoming a liability.

Rule one — Drive is a source, not the system of record. Copy every file into Cloud Storage at ingest, hash it there, and keep drive_file_id as provenance. Do not read live from Drive at request time: you would inherit its permission model, its latency and its mutability directly into your isolation boundary, and a file moved to a different folder would silently change who can see it.

Rule two — the path is evidence of intent, not of fact. Store it on the document as drive_path_hint so an operator can see what the filing implied and so a mis-binding can be traced. Bind on surrogate ids only.

The intake screen is not a throwaway. It is the tool you will personally live in for several weeks, and then hand to trained crew — so it should be built for repetitive speed, not as a generic entity form: page image on one side, extracted fields on the other, keyboard-driven, accept / correct / reject, next. Every correction an operator makes is also labelled training data for the confidence gate, which means the review queue shrinks as you work rather than staying constant.

10 — ACCEPTANCE

Eleven queries the schema must answer

Design top-down from these, build bottom-up from the tables. If the model answers all eleven cleanly, the agents are a thin layer of tool definitions on top. If it doesn't, no prompting rescues it.

  1. Who is the verified occupant of unit X today, and which phone numbers may speak for them? Party · TenancyParty · Tenancy · Unit
  2. Which unit or units may this WhatsApp number ask about, and for which date range? Party.phones · Tenancy bounds
  3. For issue category C in unit X, who is responsible — tenant, operator, or contractor? ResponsibilityPolicy · Asset.warranty_until
  4. Is the asset involved still under warranty, and held by whom? Asset · Building.handover_date
  5. Which tenancies end within 90 days and have no renewal recorded? Tenancy.end_date · status
  6. Which active tenancies are missing a required document, or hold one expiring within 30 days? DocumentRequirement ⟕ Document
  7. Which providers cover category C at building B, and are they retainer or per-job? Provider · coverage
  8. What is the open ticket count and SLA state per building right now? ServiceCall.state · SlaPolicy
  9. What has broken in this unit before, and what fixed it? ServiceCall · Visit · Asset
  10. Show every message ever exchanged about ticket T, in both original language and Hebrew. Conversation · Message
  11. What did we believe the rent on unit X was on 12 March, who changed it, and which document says so? TenancyEvent · Document · ExtractedField
11 — UNRESOLVED

Open questions on the model

Each of these changes a table. None can be answered from outside Dona Dom.

Where does the data live today? — answered

Google Drive, organised per building and per apartment, with the organising work already under way. Backfill is an ingestion problem against a known source, run first by the head of development personally and then by trained crew. The Workspace integration that was considered does not cover tenant-facing service, which is what this platform is for.

Can one party hold two tenancies at once?

A storage unit alongside an apartment, or an overlap while moving between units. If yes, “the tenant's apartment” is ambiguous and the agent needs a disambiguation turn on the very first message — a conversation-design problem, not a schema one, but it is the schema that reveals it.

Is equipment inventoried today, or only known when it breaks?

If the Drive holds handover protocols with appliance lists and serials, Asset and its warranty windows are backfillable and תקופת הבדק attribution works from day one. If not, the asset table fills lazily from service calls and warranty-based responsibility only becomes reliable months in.

How many terms profiles actually exist?

The matrix is keyed on what a tenancy obliges, never on how the paper looks. If Ashdod and Shoham share one maintenance annex, this collapses to a single value and the matrix loses a whole dimension. Still the highest-leverage unknown in the model.

Who owns the unit register — us or Priority?

We own the tenancy. But if Priority already holds units and customers, one of the two must be master and the other a mirror. Two masters is the worst outcome.

How is a phone number bound to a party the first time?

The entire isolation model rests on this one step. It needs a real enrolment flow, an answer for shared numbers, and a policy for numbers that change mid-tenancy.

Where does the on-site crew's calendar live?

The in-house crew is the deterministic happy path for dispatch. If their availability is in someone's head, the state machine has no calendar to book against.

What is the emergency bypass?

A burst pipe at 02:00 must reach a human without passing through triage. That is a policy row and a routing rule, and it should exist before the agent takes its first real message.
