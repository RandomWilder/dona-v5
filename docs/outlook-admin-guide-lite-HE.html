למה חשוב לעשות את זה נכון

דונה דום בונה פלטפורמה חדשה לניהול הנכסים. המייל הוא הערוץ הראשון שבו דיירים פונים, ולכן החיבור הזה הוא הבסיס של כל המערכת: ממנו נפתחות קריאות שירות, ועליו יישענו בהמשך גם סוכני ה-AI שיטפלו בפניות.

ההגדרה נעשית פעם אחת. כשהיא נכונה, הגישה מוגבלת לתיבה אחת, מתועדת, ואפשר לבטל אותה בכל רגע. כשהיא שגויה, האפליקציה מקבלת גישה רחבה מדי או לא עובדת בכלל. לכן כל שלב כאן מפורט, ויש בדיקה בסוף שמוכיחה את התוצאה.

כל הרחבה עתידית, כמו תיבה נוספת או הרשאה נוספת, תהיה בקשה נפרדת ומפורשת. שום דבר לא מתרחב מעצמו.

מה המערכת עושה עם הגישה

  • קוראת מיילים חדשים בתיבה הנכנסת, כל כ-90 שניות, מיום החיבור והלאה.
  • שולחת דבר אחד: תשובה קבועה עם מספר התורן כשמייל מסומן כחירום. היא נשמרת ב-Sent Items.
  • לא מוחקת, לא מעבירה ולא מסמנת כנקרא.
  • תיבה אחת בלבד. אין גישה לתיבות אחרות או לרשימת המשתמשים.
1

Entra: זהות למערכת

מה זה Entra, ולמה אי אפשר לדלג

  • Entra (לשעבר Azure AD) הוא המקום שבו Microsoft 365 מחזיק את כל הזהויות בארגון: משתמשים, וגם אפליקציות.
  • המערכת ניגשת לתיבה בלי שאדם מחובר. Microsoft מאפשרת גישה כזו רק לאפליקציה שיש לה זהות וסיסמה ב-Entra.
  • Exchange לא יכול ליצור זהות כזו. הוא רק מחליט לאיזו תיבה זהות קיימת רשאית לגשת (שלב 2).
  • בקיצור: Entra קובע מי האפליקציה, Exchange קובע לאן היא נכנסת. בלי Entra אין למי לתת את ההרשאה.
אל תוסיפו שום הרשאה במסך API permissions, ואל תלחצו Grant admin consent. הרשאת דואר שם חלה על כל התיבות בארגון. ההרשאה ניתנת רק ב-Exchange, בשלב 2. (‏User.Read שמופיע שם כברירת מחדל לא מזיק ואפשר להשאיר אותו.)

entra.microsoft.com ← Applications ← App registrations ← New registration

  1. Name: Dona Platform - Staging
  2. Supported account types: Single tenant (ברירת המחדל).
  3. Redirect URI: ריק. ← Register.
  4. במסך Overview להעתיק: Application (client) ID ו-Directory (tenant) ID.
  5. באותו מסך, ללחוץ על הקישור Managed application in local directory ← להעתיק את ה-Object ID שמופיע שם.
  6. חזרה לאפליקציה ← Certificates & secrets ← New client secret ← Expires: Custom, 24 חודשים ← Add.
  7. להעתיק מיד את עמודת Value (לא Secret ID), ולרשום את תאריך התפוגה. הערך מוצג פעם אחת בלבד.
ה-Object ID שצריך הוא זה שבסעיף 5 (של ה-Enterprise application), לא זה שמופיע ב-Overview של ה-App registration. הם שונים, וזו הטעות הנפוצה ביותר.
2

Exchange: הרשאה לתיבה אחת

מציגים את האפליקציה ל-Exchange, מגדירים תחום שכולל רק את תיבת הפיילוט, ונותנים הרשאת קריאה ושליחה על התחום הזה בלבד. נדרש תפקיד Exchange Administrator.

למה כאן אין מסכים בממשק הניהול

  • ההגבלה של אפליקציה לתיבה אחת (RBAC for Applications) קיימת ב-Exchange רק כפקודות PowerShell. ב-Exchange admin center אין לה מסך.
  • המסכים שכן קיימים (API permissions ב-Entra) נותנים גישה לכל התיבות בארגון. בדיוק מה שלא רוצים.
  • זה נעשה פעם אחת: חלון אחד, חמש פקודות להדבקה. אחרי כל פקודה כתוב מה אמור להופיע.

2א. בדיקת התיבה בממשק הניהול

admin.exchange.microsoft.com ← Recipients ← Mailboxes

  1. לחפש asafv ולפתוח את התיבה.
  2. לוודא ש-Primary email address הוא בדיוק asafv@dona.co.il. אם מופיעה כתובת אחרת, להשתמש בה במקום בכל הפקודות.

2ב. פתיחת PowerShell

  1. במחשב Windows: תפריט התחל ← לחפש PowerShell ← לפתוח.
  2. אם זו הפעם הראשונה, להתקין את מודול Exchange. אם מופיעה שאלה, לענות Y או A:
Install-Module ExchangeOnlineManagement -Scope CurrentUser

2ג. חמש פקודות, אחת-אחת

להדביק כל פקודה, ללחוץ Enter, ולוודא את התוצאה לפני שממשיכים. טקסט אדום = שגיאה, ראו טבלה בסוף.

  1. התחברות. נפתח חלון התחברות רגיל של Microsoft. להתחבר עם חשבון המנהל.
Connect-ExchangeOnline
  1. הצגת האפליקציה ל-Exchange. מופיעה שורה עם Dona Platform - Staging.
New-ServicePrincipal -AppId <APP_ID> -ObjectId <ENTERPRISE_APP_OBJECT_ID> -DisplayName "Dona Platform - Staging"
  1. תחום של תיבה אחת. מופיעה שורה עם Dona-Staging-Mailbox והכתובת.
New-ManagementScope -Name "Dona-Staging-Mailbox" -RecipientRestrictionFilter "PrimarySmtpAddress -eq 'asafv@dona.co.il'"
  1. הרשאת קריאה על התחום. מופיעה שורה עם Application Mail.Read.
New-ManagementRoleAssignment -App <APP_ID> -Role "Application Mail.Read" -CustomResourceScope "Dona-Staging-Mailbox"
  1. הרשאת שליחה על התחום (לתשובת החירום בלבד). מופיעה שורה עם Application Mail.Send.
New-ManagementRoleAssignment -App <APP_ID> -Role "Application Mail.Send" -CustomResourceScope "Dona-Staging-Mailbox"

להשאיר את החלון פתוח: שלב 3 רץ באותו חלון.

3

בדיקה

מוכיחים שהגישה היא לתיבת הפיילוט ורק לה. להריץ אחרי 30 דקות עד שעתיים: לפני כן התשובה יכולה להיות False גם כשהכל תקין.

  1. תיבת הפיילוט. InScope צריך להיות True בשתי השורות:
Test-ServicePrincipalAuthorization -Identity <APP_ID> -Resource asafv@dona.co.il
  1. תיבה אחרת כלשהי. InScope צריך להיות False:
Test-ServicePrincipalAuthorization -Identity <APP_ID> -Resource <OTHER_MAILBOX>
  1. צילום מסך של שתי התוצאות.

מסירה

חמישה ערכים וצילום מסך. רק הסוד רגיש, והוא עובר בנפרד.

  • Directory (tenant) ID
  • Application (client) ID
  • תאריך תפוגת הסוד

את כל אלה אפשר לשלוח במייל.

Client secret (Value): לא במייל ולא בוואטסאפ. בטלפון, או בקישור חד-פעמי (מנהל סיסמאות או OneTimeSecret).

אחרי המסירה: מהתיבה לטאב קריאות

כך מייל של דייר הופך לקריאת שירות במערכת. אותו מסלול בדיוק בבדיקות ובייצור, רק התיבה משתנה.

המסלול של כל מייל

  1. קריאה. כל כ-90 שניות המערכת שואלת את Microsoft מה חדש בתיבה הנכנסת מאז הפעם הקודמת. נקודת הקריאה נשמרת, כך שגם אחרי הפעלה מחדש שום מייל לא נקרא פעמיים ולא מדולג.
  2. שמירה. המייל נשמר במערכת כפי שהוא, עם הקבצים המצורפים. בתיבה עצמה לא משתנה דבר.
  3. בדיקת חירום. לפי רשימת ביטויים קבועה, בלי AI. מייל חירום מסומן ומוצמד לראש הרשימה, ויוצאת ממנו תשובה קבועה אחת עם מספר התורן, על אותו שרשור.
  4. שרשור. תשובה על מייל קיים מצטרפת לקריאה הפתוחה שלו, ולא פותחת קריאה חדשה.
  5. מיון. מודל AI (OpenAI) מציע אם זו קריאת שירות, קטגוריה וסיכום בעברית, ומתרגם מייל שלא נכתב בעברית. הוא רק מציע; הצוות מחליט. מייל שאינו פנייה (פרסומת, התראה) עובר ל"מסוננות" ונמחק אחרי 6 חודשים.
  6. זיהוי. כתובת השולח מושווית לאנשי הקשר של הדיירים. התאמה אחת מסמנת את הקריאה כ"זוהתה".
  7. בטאב. הקריאה מופיעה בטאב קריאות, עם המייל, הקבצים והסיכום.

שמירה על החיבור

  • שעה בלי קריאה מוצלחת מהתיבה: הטאב מציג אזהרה. קריאה מוצלחת מנקה אותה.
  • 30 יום לפני שהסוד פג: הטאב מציג אזהרה לחדש אותו.
