## Four structural calls

**1. The kernel's own migrations come with the kernel.** The slice entry says v3's migrations do not
come, and that is right about the **domain** ones — 0003–0011, 0013, 0015, 0016 encode the three
shapes v5 examined and rejected (from-v3.md Tier 3), and the estate spine is written fresh at 1.9.
But seven kernel suites go through `migratedPoolOrNull()`, which migrates and then queries
`audit_log`, `outbox`, `scheduled_work`, `idempotency_keys` and `config_settings`. With no
migrations at all they skip locally and **fail in CI from 1.6**, which sets `REQUIRE_POSTGRES=1`.

This was measured rather than reasoned about. The lift was landed first, with an empty
`migrations/`, and run against the real database:

```
$ REQUIRE_POSTGRES=1 npm run test:code       # kernel lifted, no migrations
ℹ tests 104 · pass 83 · fail 21

✖ audit.test.ts · config.test.ts · events.test.ts
✖ idempotency.test.ts · migrate.test.ts · work.test.ts
  Error: ENOENT: no such file or directory, scandir 'src/kernel/migrations'
```

Six files, 21 cases. Three migrations then close all 21:

| | |
|---|---|
| `0001_init.sql` | the `vector` extension — v3's, verbatim |
| `0002_kernel_durability.sql` | `idempotency_keys` · `audit_log` · `outbox` · `scheduled_work` · `config_settings` |
| `0003_kernel_settings.sql` | the embedding and extraction settings rows |

Three departures from a byte copy, each stated in the file that makes it. v3's later
`ALTER TABLE audit_log ADD COLUMN actor_role` is **inline in 0002**, because an ALTER correcting a
column this repository never shipped is theatre. The **seeds are their own file**, because `SPEC.md`
says DDL and backfill never share one and v3 had them together. And `occupancy_chunk_embeddings`
does **not** come: it is an occupancy table, and nothing in the kernel reads it.

The result is a database holding the kernel and nothing else:

```
$ psql -c "SELECT filename FROM schema_migrations ORDER BY filename" -c "\dt"
```

Six tables, no domain table among them. Estate appends from `0004_` — carried into 1.9.

**2. `kernel/db.ts` is the one file deliberately not v3's, and it was red first.** 1.3 found that a
`pg` Pool with no `'error'` listener takes the *process* down when an idle client's backend goes
away, and wrote the listener into `src/db.ts` — a file this slice deletes. The case moved into
`src/kernel/db.test.ts` and was run against the verbatim v3 file before the listener was added:

```
$ node --test src/kernel/db.test.ts          # v3's db.ts, no listener
✖ stays alive to answer instead of taking the process down with it
  error: terminating connection due to administrator command
ℹ tests 3 · pass 2 · fail 1

$ node --test src/kernel/db.test.ts          # listener added
pg pool: idle client dropped — terminating connection due to administrator command
✔ the pool survives the database going away (277.242ms)
ℹ tests 3 · pass 3 · fail 0
```

v3's signature is kept over 1.3's — `createPool(env)` raises `invalid` when `DATABASE_URL` is
absent rather than defaulting to a developer's laptop, and `src/serve.ts` no longer passes a
fallback. A production service that quietly boots against the wrong database is worse than one that
refuses to boot:

```
$ node -e "createPool({})"
KernelError: invalid — DATABASE_URL is required
```

**3. The boundary is a test, not a grep run once.** The Verify asks for a grep, and the grep was run

specifier naming a module from `SPEC.md`'s map. It runs on `npm test` today and inside `gate` from

## The defect this slice found by running it

**`migrate.test.ts` skipped green under `REQUIRE_POSTGRES=1`.** v3's copy connects through a private
`connectOrNull()` that ignores the flag entirely, so with an unreachable database it reports:

```
$ REQUIRE_POSTGRES=1 DATABASE_URL=…:1/dona node --test --test-reporter=tap 'src/**/*.test.ts'
ok 1 - applies in order, records files, and is safe to run twice # SKIP postgres not running
# skipped 1
```

That is precisely the failure `docs/pipeline.md` §7 names — and it is the *migration* suite, the one
case whose whole job is to prove the schema applies at all. In CI at 1.6 with a misconfigured
database URL, it would have gone green having applied nothing.

Routed through `pg-support.ts`, which is the single place that decision belongs. `migratedPoolOrNull()`
migrates the pool it hands back, so the suite's two `migrate()` calls are now the second and third
runs rather than the first and second — a stronger idempotency assertion, not a weaker one.

```
before: fail 22 · skipped 1        after: fail 23 · skipped 0
```

Every one of the other seventeen kernel suites already used `pg-support`; this was the only one.

## The live round trip

The same four states 1.3 proved, now through the kernel's error shape rather than a literal, and
with an unknown route added because `setNotFoundHandler` is new here:

```
--- up ---                {"ok":true,"version":"0.0.0-dev","db":"up"}                    HTTP 200
--- unknown route ---     {"code":"not_found","message":"route not found"}               HTTP 404
--- database stopped ---  {"ok":false,…,"code":"unavailable","message":"database unreachable"}  HTTP 503

```

One log line, no stack trace, no connection parameters, and a process that is still there to answer.
The 404 body carries no path: Fastify's default echoes the request back into it, which is a small
reflection of user input into a response, and the handler exists so that never reaches the wire.

## Two runtime dependencies, with their reasons

- **`pdfjs-dist`** — `kernel/pdf.ts`. Positions rather than a flat string: a lease's facts live in a
  two-column label/value annex, and flattened text binds every value to the label on the line above.
  Imported lazily, so a process that never reads a PDF never pays for it.
- **`google-auth-library`** — `kernel/objects.ts`. Token acquisition differs between Cloud Run's
  metadata server and a laptop's ADC, and hand-rolling an OAuth refresh for a bucket holding signed
  contracts is the wrong economy, while the transfer itself is two HTTP calls that need no SDK.

Four total. v3 shipped a production service on five; `@fastify/multipart` is the one not taken,
because nothing in the kernel imports it. **`pdfjs-dist` is 35 MB unpacked** and
`npm ci --omit=dev` will install it — carried into 1.6 as an image-size note rather than a surprise.

## Smaller decisions, recorded so they are not rediscovered

- **`SPEC-kernel.md` was written before the code**, from v3's 281-line spec, trimmed to what actually
  lands and re-pointed at v5's slices. The sections v3 wrote about `identity`/`portfolio` validators
  are restated against v5's module map.
- **The seed values are v3's *final* ones**, not its first: `gpt-5.6-luna` at `reasoning_effort:
  none` is what v3 arrived at after a staging press timed out at Cloud Run's 300 seconds. Seeding the
  first value and then "migrating" to the second would be re-enacting history the repository does not
  have. `config.test.ts` asserts the final values verbatim, which is how this was noticed.
- **`now()` appears in `0003`, and it is the one place `SPEC.md` allows it.** A seed inside a
  migration is not a domain write and there is no injected clock at migration time; the ban exists so
  a *business* timestamp is never written by a source the tests cannot control. Said in the file.
- **The `after-write` hook now runs 19 kernel test files on any write under `src/kernel/`** and
  returns in 0.57s, silent. Checked rather than assumed, because 1.3's session-start hook is the
  cautionary tale about what a hook can do to a machine.
