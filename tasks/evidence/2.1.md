## The acceptance bar is an exclusion constraint, not application code

"At most one party on any given day, and different parties over different days" is a statement about
**overlap**, so it is declared as one:

```sql
CONSTRAINT contact_value_resolves_to_one_party EXCLUDE USING gist (
  channel WITH =, value WITH =, daterange(valid_from, valid_to, '[]') WITH &&
)
```

Four semantics were measured in a throwaway database **before** the line was written, not after:

| Case | Outcome |
|---|---|
| Two parties, `…–2026-06-30` then `2026-07-01–NULL` | accepted |
| A second row overlapping by one day (`2026-06-30`) | rejected `23P01` |
| A later row while an open-ended one is current | rejected `23P01` |
| The same string on `PHONE` and on `EMAIL` | accepted |

`'[]'` is inclusive at both ends, which is the same day-grained reading
`src/scope/internal/isolation-join.ts` already uses. A `NULL` upper bound is unbounded, which is what
*"null = still current"* means — so closing the old contact is a step somebody takes rather than one
the schema forgives.

`btree_gist` is required for the `=` operators. It was confirmed present in the local
`pgvector/pgvector:pg16` container (`1.7`, not installed) before the `CREATE EXTENSION` line existed,
which is `0001_init.sql`'s own lesson: a migration needing a permission or an extension the database
lacks is a deployed revision that will not start.

## Every rejection, red first

Run by a probe that rebuilds `0006_`'s own DDL with **only the constraint under test removed**, in
`pg_temp` on a connection of its own. Output in full:

```

         → accepted without the constraint
RED      exclusion · an open-ended contact blocks every later one
         → accepted without the constraint
RED      phone_is_e164 · a locally-formatted number
         → accepted without the constraint
RED      validity_is_ordered · an inverted period
         → rejected as an unnamed 22000 instead of the named 23514 the case asserts
RED      party_kind · a value outside the closed set
         → accepted without the constraint
RED      preferred_language · a value outside the closed set
         → accepted without the constraint
RED      party_contact.party_id · a reference to a party that does not exist
         → accepted without the constraint

all probes red
```

**The fourth line is the useful one, and the probe found it rather than the commit message claiming
it.** `validity_is_ordered` is the one constraint whose removal does *not* let the row through: an
inverted period still fails, inside the exclusion constraint's `daterange()` constructor, as a bare
`22000` — *"range lower bound must be less than or equal to range upper bound"* — with no constraint
name and nothing an importer can report against a line number. The CHECK's entire value is turning
that into a named `23514`, and Postgres evaluating CHECKs before index constraints is what makes the
named error the one that surfaces. The case is therefore red on the **SQLSTATE** and not on
acceptance, and the probe was rewritten to say so instead of being marked as a pass.

The probe itself was written the wrong way twice, and the second time mattered: it first wanted to
tear down its schemas with a statement **`.claude/hooks/guard-bash.mjs` blocks with exit 2**. That is
the guard doing its job, and the fix was `pg_temp` rather than a way around it — a probe that needs
to destroy things is a probe written the wrong way.

## Both remaining grep guards fired, and neither was worked around

**Guard three could not see the column that most needed it.** `party_contact.value` holds a phone
number or an email address and is the most person-shaped column in the system; `scripts/guards.ts`
matches bare column names, and adding `value` to the list would have fired on `config_settings.value`
in `0002_kernel_durability.sql`. A guard with a false positive is one people learn to work around,
which is worse than the gap. So the guard learned to track the enclosing `CREATE TABLE` / `ALTER
TABLE`, and its list can now carry **qualified** entries — `party_contact.value` — beside bare ones.
Its own comment already had the rule: *"a column this list misses is added to it when it is met."*
Four cases, written red first, assert both directions: the qualified name fires on an unmarked
`party_contact.value`, stays silent on `config_settings.value`, and the table name is forgotten at
the end of its statement so a later `value` in the same file does not inherit it.

**Guard two fired on `0006_`, and it was its first firing on work that was not a violation.**

```
guard isolation-join-lives-in-src-scope: src/kernel/migrations/0006_parties.sql
  — the contact-validity predicate belongs to src/scope and nowhere else
```

`validity_is_ordered` is a null-guarded comparison of `valid_to`, and so is the join's
contact-validity predicate; the pattern could not tell them apart. They are different questions: the
join asks *is this contact valid on the day being asked about* and compares `valid_to` to a
parameter, while the CHECK asks *is this row's period ordered* and compares it to the other column of
the same row.

The resolution was to make the pattern say which it means, and **not** to rephrase the CHECK to slip
past it — pipeline §6 is explicit that the constraint is revisited on the record or not at all. The
exception is safe by construction rather than by judgement: `valid_to >= valid_from` is true of every
well-formed row, so it cannot express "valid on day D" no matter who writes it or where. Two cases
hold the pair — the ordering check is allowed outside `src/scope/`, and a copy comparing `valid_to`
to a parameter, a literal, `CURRENT_DATE` or another column still trips the guard.

**Fixing it surfaced two bugs of its own**, both caught by the tests rather than by review:

1. `>=\s*(?!valid_from\b)` does not do what it reads like. `\s*` backtracks to zero width, the
   lookahead then examines `" valid_from"`, which does not begin with `valid_from`, and the guard
   matches anyway. The whitespace has to be **inside** the lookahead: `>=(?!\s*valid_from\b)`.
2. The new test file became the second copy the guard exists to catch — both in a fixture string and
   in a comment quoting the predicate. Fixed the way the neighbouring cases already were: derive the
   violating text from `ISOLATION_JOIN_SQL` itself, and describe the predicate in prose rather than
   quoting it. A guard that scans this repository scans its own tests.

**Proved on the real migration, not only on a fixture.** With the marker deleted from `0006_`
itself, guard three fires on the qualified name — the check the plan owed, and the one that makes
"the guard can see it" a fact rather than a unit test agreeing with itself:

```
guard pii-columns-are-commented: src/kernel/migrations/0006_parties.sql
  — line 53: `party_contact.value` holds personal data and carries no `-- pii`
    (or `-- not-pii: <why>`)
```

## Three calls made in the DDL, and what decided each

- **`phone_is_e164`** — `channel <> 'PHONE' OR value ~ '^\+[1-9][0-9]{7,14}$'`. The workbook's note
  is *"One format, always. Mixed formats break the inbound lookup silently."* A number stored as
  `052-123-4567` and asked for as `+972521234567` resolves to nobody, and **that is
  indistinguishable from correct isolation** — the failure mode where nothing looks wrong. The CHECK
  makes it loud. It is a backstop and not a normaliser; converting at the edge stays 2.3's, where 1.7
  carried it, and the two together are what close the workbook's warning.
- **`preferred_language` is `NOT NULL DEFAULT 'he'`** where the sheet marks the column optional. The
  sheet's own note is "Default he", and a null language is not a behaviour the agent can have — it
  opens in *some* language on the first message. A literal default is not a clock and does not breach
  the `DEFAULT now()` rule.
- **No natural key on `party`**, deliberately, and carried into **2.4**. The obvious candidate is
  `national_id` and it is the same trap `address_key` was at 1.9: a ת.ז. is nine digits **with
  leading zeros that every spreadsheet export drops**, so `042…` and `42…` are one person and a naive
  `UNIQUE` disagrees with itself the first time the register arrives. It also has to be
  `(party_kind, national_id)` at minimum — a ת.ז. and a ח.פ. are different registries and can be the
  same nine digits — and it is nullable, a third decision. 1.9 waited and 1.11 chose against real
  addresses; 2.4 chooses this one against the real export.
