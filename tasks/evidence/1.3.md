# Evidence — Slice 1.3 · Toolchain and a walking skeleton

**Date:** 2026-09-04 · **Week 1** (built ahead of Sunday 6 Sep) · **Size:** M

> **Done when:** a clean clone reaches a running server in under five minutes; `/health` returns
> `ok:true` **and** `db:up`.
> **Verify:** time it from `git clone` on a second checkout; record the number.

## The number

A genuine second checkout: `git clone` from this repository into an empty directory, its own compose
project, its own volume, its own container. Nothing reused but the machine.

```
git clone            0s
npm ci               1s      (warm npm cache)
docker compose up    0s
server answering     1s
----------------------------------------
TOTAL                2s
GET /health          {"ok":true,"version":"0.0.0-dev","db":"up"}
```

**Both halves of the bar in one line**: `ok:true` is the process, `db:up` is the claim it can only
make by reaching Postgres. The endpoint exists so that "deployed but silently broken" is not a state
the pipeline can report as green (pipeline §5).

**Two seconds is a flattering number, so here is what it does not include.** The npm cache was warm
and the database image was already on disk. Measured against an empty npm cache and a real network,
`npm ci` takes **2s** rather than 1 — 70 packages, five of them direct. The one leg not measured is
the first-ever `docker pull` of `pgvector/pgvector:pg16`, **147 MB**, which on a new machine is a
minute or two of someone else's bandwidth. Even taking that at its worst the total sits an order of
magnitude inside the five-minute bar, and the bar is not at risk from anything this slice added.

Proof it was a real clone and not a warm directory:

```
$ ls node_modules | wc -l          # in the clone
      59
$ cat compose.log
 Volume checkout_dona5_pg Creating
 Network checkout_default Created
 Container checkout-db-1 Started
```

The clone, its volume and its container were destroyed afterwards.

## Six structural calls, and what they cost

**1. The skeleton lives at the root of `src/`, not in `src/kernel/`.** Slice 1.4 lifts all of v3's
`src/kernel/` verbatim, renaming nothing. Anything written there now is a conflict against a file
the plan says arrives untouched, so `src/` contains no module at all and 1.4 lands in clean space.
The cost is four hand-written stand-ins the kernel takes back, all four carried into 1.4's entry in
`todo.md` and `roadmap.md`.

**2. No kernel imports, so the 503 body is a literal.** v3's `app.ts` gets `KernelError` /
`httpStatus` / `toErrorBody` from `kernel/errors.ts`. Those arrive in 1.4, so `src/app.ts` writes
`SPEC.md`'s shape by hand with a comment naming its future owner — and deliberately does **not**
write `setNotFoundHandler` / `setErrorHandler`, because writing them twice is how two copies drift.

**3. Fastify and `pg`, not `node:http`.** `plan.md` A2 inherits the stack whole. `google-auth-library`,
`pdfjs-dist` and `@fastify/multipart` are v3's other three and are not here: they arrive with the
kernel modules that use them.

**4. Postgres stays on 5434**, v3's port, so `kernel/pg-support.ts`'s default connection string is
still a genuinely verbatim lift in 1.4. The cost is that v3's compose stack and this one cannot both
be up; v3 is a reference to read, not a service to run. Written into 1.4's entry as *do not
renumber*.

**5. Biome's scope is application code, not `.claude/`.** The three hook `.mjs` files are Node
scripts on a 120-column style Biome would rewrite wholesale. Excluding them is what made it possible
to turn the format step on today rather than after a reformatting argument.

**6. One entry point, not two.** v3 has `serve.ts` *and* a `dev.ts` that hand-rolls a `.env` loader
whose distinguishing feature is that it never overrides a variable already set in the shell. Node
24's `--env-file-if-exists` was checked here and has that same property, so `dev.ts` is not lifted:

```
$ FOO=fromshell node --env-file-if-exists=.env.example -e 'console.log(process.env.FOO)'
fromshell
```

## The two items 1.2 owed this slice

### 1. `npm test` runs the hook suite — and wiring alone would not have done it

The finding that made this more than a script line. Bare `node --test` **does not descend into
dot-directories**, so `.claude/hooks/hooks.test.mjs` is invisible to default discovery. Measured in
a scratch fixture holding one test in each place:

```
$ node --test                                   # default discovery
✔ module (0.24ms)        ← src/estate/x.test.ts
ℹ tests 1                ← .claude/hooks/hooks.test.mjs was never found

$ node --test '.claude/hooks/**/*.test.mjs' 'src/**/*.test.ts'
ℹ tests 2
```

The path has to be named. A glob matching nothing was checked in the same fixture and is a silent
no-op, so `tests/**` and `evals/**` are named now and start reporting when 1.7 and 1.8 create them —
which is also why both of those slices are carrying an instruction to confirm the count rather than
trust the glob. **A suite the runner never found is indistinguishable from a suite that passed.**

### 2. `after-write.mjs` gains the Biome step — and §4's two rules stop being one

Pipeline §4 states two separate rules. Slice 1.2 collapsed them into one `^src/<module>/` gate, so
`src/app.ts` and `src/serve.ts` — the entirety of this slice's code — would have been formatted by
nothing. The hook now runs Biome for any file inside Biome's own scope, read out of `biome.json` so
the two cannot drift, and runs the module's tests only for `src/<module>/`.

Both directions, live in this session, through the real Edit tool:

```
$ (Edit src/app.ts — introduces double quotes and a missing semicolon)
   → no hook output at all; the file came back as
     return { ok: true, version: deps.version, db: 'up' };

$ (Edit src/app.ts — introduces `const started = Date.now();`)
PostToolUse:Edit hook blocking error:
  src/app.ts:25:11 lint/correctness/noUnusedVariables  FIXABLE
  ! This variable started is unused.
  i Unsafe fix: If this is intentional, prepend started with an underscore.
  × Some warnings were emitted while running checks.
  Biome could not clean src/app.ts on its own.
```

Silent when it can fix it; exit 2 with Biome's own words when it cannot. Four new cases in
`hooks.test.mjs` pin both, and two of them were red against the committed hook first:

```
✖ formats a src file that belongs to no module
  + actual   'export function serve() {\n    return "up";\n}\n'
  - expected "export function serve() {\n  return 'up';\n}\n"
✖ exits 2 with Biome's own output when it cannot clean the file
```

## Four defects, every one found by running it rather than reading it

### 1. `SessionStart` fork-bombed the machine

The sharpest thing in the slice. `session-start.mjs` ran `npm test` whenever a test script existed.
`npm test` ran the hook suite. The hook suite spawns `session-start.mjs`. There is no bound on that.

The first `npm test` after `package.json` appeared:

```
$ time npm test
✖ prints the current branch (120358.640917ms)      ← spawn timeout, not an assertion
✖ names the loaded guardrails …  (121733.625958ms)
✖ blocks with exit 2: force push — git push --force origin main (60.12ms)
ℹ tests 34 · pass 31 · fail 3
npm test  0.97s user 1.69s system 1% cpu  4:06.89 total
```

Three things in that block are worth separating. Two failures are the recursion timing out. **The
third is a guard-bash case that has nothing to do with any of this and went red anyway** — the
machine had no room left to fork, so a `spawnSync` returned in 60ms with the wrong status. It passed
in isolation immediately afterwards. That is a gate failing for weather, which is the failure mode
`SPEC.md` bans committed embedding distances for; here it arrived from the other direction.

And it did not stop when the command did. Twenty minutes later:

```
$ ps -Ao pid,etime,command | grep -E "npm test|node --test"
 1774    11:11 /bin/sh -c npm test --silent 2>&1
10451    21:16 node --test .claude/hooks/**/*.test.mjs …
81186    21:29 /bin/sh -c npm test --silent 2>&1        (… eleven of them)
```

**Fixed structurally, not by a flag.** `npm test` is now `test:code && test:hooks`; `SessionStart`
runs `test:code`, which cannot reach the hook suite that spawns it. `DONA_SESSION_START=1` is set on
the child as a second line of defence for the day someone points that line back at `npm test`, and
the banner names the narrower script rather than implying it ran everything:

```
$ node .claude/hooks/session-start.mjs
## slice/1.3-toolchain

tests: green — src · tests · evals (`npm test` adds the hooks suite)
guardrails: armed — guard-bash · after-write
```

Five new `session-start` cases, all five red against the committed hook — including the recursion
itself, which shows up in the red run exactly as it did in the wild:

```
$ git show HEAD:.claude/hooks/session-start.mjs > .claude/hooks/session-start.mjs
✖ prints the current branch (120033.737583ms)
✖ says nothing is there to run rather than printing an npm error
✖ runs the code tests and reports green
✖ reports FAILING with the tail of the output when the code tests are red
✖ does not run the suite again when it is already inside one
✖ names the loaded guardrails … (120169.629833ms)
ℹ tests 41 · pass 35 · fail 6
```

### 2. The server died when the database went away — and v3's does too

Found by stopping the container while `npm run dev` was up, which is what a Cloud SQL restart, a
failover or a maintenance window looks like from the process's side.

```
$ docker compose stop db
$ curl -s http://127.0.0.1:3000/health
                                        ← nothing. HTTP 000. The server was gone.

# in the server log:
node:events:487  throw er; // Unhandled 'error' event
error: terminating connection due to administrator command
Emitted 'error' event on BoundPool instance
```

`pg` emits `'error'` on an idle client whose backend disappears, and Node throws on an unhandled
`'error'` event. So the process **exits** instead of degrading, and `/health`'s 503 branch — the
whole reason the endpoint reports `db` separately from `ok` — never runs, because nothing is left to
serve it. The unit test could not have caught it: its dead pool never connects, so it never has an
idle client to lose.

**v3 has no listener either.** `src/kernel/db.ts` builds the pool and attaches nothing, and a grep
over all of `src/` finds no `pool.on('error')` anywhere in the repository. That file is Tier 1,
"take verbatim", and 1.4 lifts it — so a clean lift would reintroduce this. It is now written into
[from-v3.md](../../docs/from-v3.md) beside the kernel's own paragraph and into 1.4's entry in both
plan files.

`src/db.ts` has the listener; `src/db.test.ts` proves it by terminating its own backend, and it was
red first:

```
$ node --test src/db.test.ts          # with the listener removed
✖ reports 503 instead of taking the process down with it
  error: terminating connection due to administrator command
ℹ tests 1 · pass 0 · fail 1

$ node --test src/db.test.ts          # with it restored
pg pool: idle client dropped — terminating connection due to administrator command
✔ reports 503 instead of taking the process down with it (333.549ms)
```

The case terminates **only its own** backends, matched by `application_name`. `node --test` runs
files in parallel, and a blanket `pg_terminate_backend` would take `src/app.test.ts`'s connections
down with it and call the result a flake.

The full round trip, live, after the fix — which is precisely what `infra/smoke.sh` will assert in
1.6:

```
--- up ---                 {"ok":true,"version":"0.0.0-dev","db":"up"}                    HTTP 200
--- database stopped ---   {"ok":false,…,"code":"unavailable","message":"database unreachable"}  HTTP 503
--- database back ---      {"ok":true,"version":"0.0.0-dev","db":"up"}                    HTTP 200

server log: pg pool: idle client dropped — terminating connection due to administrator command
```

One log line, no stack trace, no connection parameters. The error object carries the full connection
string and `SPEC.md`'s rule is that internals reach a log no more readily than they reach the wire.

### 3. Biome, handed an absolute path into a symlinked checkout, processes nothing and exits non-zero

The hook originally passed the payload's absolute path. Every macOS temp directory reaches its
contents through a symlink (`/var` → `/private/var`), and Biome resolves its project root through
symlinks before matching `includes` against the path it was handed:

```
× No files were processed in the specified paths.
i These paths were provided but ignored:
  - /var/folders/…/T/dona-v5-hook-o7zTAW/src/app.ts

Biome could not clean src/app.ts on its own.
```

The hook would then report a file as unclean that Biome never opened. It passes the repo-relative
path now. Caught because the fixtures live in `/var/folders` — a case written for one reason finding
a defect of a different kind.

It also produced a **false green**, which is the more instructive half: the "exit 2 when Biome
cannot clean it" case asserted `/noUnusedVariables|could not clean/` and passed on the second
alternative while Biome had examined nothing. The case now names the rule, so "processed no files"
can never again read as "found a lint error".

### 4. Biome's default for an unused variable is a warning, and a warning exits 0

```
$ npx biome check --write src/a.ts
lint/correctness/noUnusedVariables  ! This variable unused is unused.
Found 1 warning.
exit=0
```

A hook that notices and stays silent is decoration — the exact defect slice 1.2 found in this same
file's exit code, arriving a second time by a different route. Both `npm run lint` and the hook
carry `--error-on-warnings`, which makes that case exit 1 while still applying the formatting.

## Smaller decisions, recorded so they are not rediscovered

- **`npm run format` is `biome check --write`, not `biome format --write`.** The same command the
  hook runs, so the two can never disagree about what a clean file is. It formats, organises imports
  and applies safe lint fixes.
- **`biome migrate` was run.** `linter.rules.recommended` is deprecated in Biome 2.5.12 in favour of
  `preset`, and a deprecation notice printed on every lint run is a notice you stop reading.
- **`npm test` does not run typecheck or lint.** Three separate scripts, because CI runs them as
  three steps and the Definition of Done lists all three.
- **The version string is `process.env.VERSION ?? '0.0.0-dev'`.** The deploy stamps the commit it
  built (1.6). Locally the honest answer is that this is a working copy, not a release.
- **`.claude/settings.json` gained four entries** — `test:code`, `test:hooks`, `npm run dev`, and
  nothing else. `npm install` stays behind a prompt: it writes a lockfile, which is exactly the kind
  of change that should be noticed.
- **`node --test` was verified not to error on a glob matching nothing**, which is what makes naming
  `tests/**` and `evals/**` a year early safe rather than a trap.

## Raised and settled

- **No `SPEC-<module>.md` was touched.** This slice creates no module and changes no module
  behaviour — not applicable rather than skipped, as in 1.2. `SPEC.md`'s status section does change,
  because where the skeleton lives and why is a shared convention.
- **Most of the standing Definition of Done now runs.** `typecheck`, `lint` and `npm test` are green
  locally for the first time in this repository. Still absent by sequence, not by omission:
  `tests/policy/` (1.7), `npm run evals` (1.8), staging and `infra/smoke.sh` (1.6).
- **Two runtime dependencies, with reasons in the commit body** — `fastify` and `pg`. v3 shipped a
  production service on five; v5 is at two.

## Where it stands

PR to `main` from `slice/1.3-toolchain`, and it will report `BLOCKED` for the same reason 1.2 did:
`gate` and `evals` are required check contexts and no workflow reports them until 1.6. The merge is
the director's call, not this slice's to assume.

## What this cost

One session. The toolchain itself was an hour of copying v3's proven files and would have been the
whole slice if it had been read rather than run. **Everything of value in this file came from the
running**: a recursion that fork-bombed the machine, a server that died instead of degrading, a
formatter that reported on files it never opened, and a warning that exited 0. Three of those four
were invisible in the source and all four were invisible in v3, which has been deployed with the
second one for a month.
