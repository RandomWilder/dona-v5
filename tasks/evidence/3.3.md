## What the slice ships

```
POST /documents
  sniff the bytes  → pdf · jpg · png · tif, or invalid
  hash the bytes   → sha256, lowercase, 64 chars
  verify           → verified · refused · unverified · unguarded
  refused?         → audit line, and return. No row, no object.
  look the hash up → an existing document, or none
  put              → only when no document already holds these bytes
  ingest           → document row, clock injected
  link             → UNIT:SUBJECT always, TENANCY:EVIDENCE when one was chosen
  audit            → ok
```

The order is 3.2's carried rule, unchanged: hash first so the path is computable before anything is
written, look up before putting so the same bytes filed against a second place do not write a second
copy. What 3.3 added to it is the **verify step, and its position** — before the lookup and before
the put, because "caught before it is filed" is a claim about writes and a refusal that had already
uploaded the object would be a refusal in the UI only.

## Four decisions, and why each went the way it did

### 1. A refused upload leaves no row — the question 3.1 left open

3.1 gave E12 no `state` column and handed this slice the disagreement: figure 4 of the published Data
Model says *"REJECTED is a state, not a deletion — the wrong file is evidence too, of what someone
tried to file and when"*, while this slice's own bar says the ארנונה bill is caught **before** it is
filed.

Decided: **the caption binds the bulk queue, not the interactive path.** A drive full of scans
arrives with no human present, so a rejection there has to become a row somebody can review later —
that is 3.4, deferred. Here an administrator is looking at the screen when the refusal happens, and
the whole failure mode is *you picked the wrong file*, which they fix in the next five seconds.
Storing a rejected upload would cost a `state` column, a migration, a lifecycle for rows nobody will
revisit, and an object in the bucket the application cannot delete.

The attempt is still recorded, because the caption's *what someone tried to file and when* is the
part worth keeping: every call writes an `audit_log` line, refusals included, carrying the digest,
the declared type, the verdict and the missing terms. Not the filename, and there is nowhere for one
to come from — the intake is never told it.

### 2. Every marker term must be present, not any one of them

The lease specimen contains the word ארנונה, in the clause about who pays the utilities. A guard
that accepted a single matching term would therefore have filed a lease as an ארנונה bill and called
it verified. So the verdict is `verified` only when **all** of a type's `verification_terms` are
found, and a refusal lists exactly the ones that were not — an operator who cannot see what was
missing works around the guard instead of fixing the upload.

Observed on the real files rather than argued: filing the lease into the ארנונה slot fails on
`המחזיק` and `הרשות המקומית` and **not** on `ארנונה`.

Comparison is over normalised text — NFKC, niqqud stripped, bidi controls and soft hyphens removed,
all whitespace removed, lowercased. Whitespace goes entirely rather than being collapsed because a
PDF text layer breaks a line wherever the typesetter did, and `חוזה\nשכירות` is the same phrase as
`חוזה שכירות` to every reader except a naive `includes`.

### 3. A file with no text layer is filed `unverified`, not refused

A scan and a photograph carry no text, OCR is 4.1's, and refusing them would refuse most real leases.
Filing them silently would make `verified` mean nothing. The third verdict keeps both honest: it is
on the audit line, and the confirmation screen says in words that the file was not checked and will
be at the automatic-reading step. `unguarded` is the fourth, for a type whose `verification_terms`
are null — nullable on purpose, so a type added as a row is never unfileable just because nobody has
written its marker terms yet.

### 4. The kind of a file is read from the file

`sniffExtension` matches magic bytes and the filename never reaches the path, the row or the screen.
A `.pdf` that is a PNG is filed as a PNG; a `.jpg` that is a Windows executable is refused with
`invalid`. This is the same reasoning as 3.2's *validated, never sanitised*: the extension is a
segment of an object path, and taking it from a string the caller chose is taking a path segment
from the caller.

## The first write route in this system, and it has no session

Every route before this one was a read. `GET /documents/new` and `POST /documents` are reachable by
anybody until staff auth lands in week 5, and the bounds that stand in for a session are:

| | |
|---|---|
| files per request | 1 |
| bytes per file | 20 MB, enforced by the plugin and re-checked for truncation |
| kinds accepted | four, from the bytes |
| fields | 8, 200 bytes each |
| filename | discarded |
| what the response can say | a flat, a type, dates, a digest — never a name |

**There is no CSRF token, and that is not an omission.** A CSRF token defends a session's authority;
there is no session, and an anonymous caller can already post directly. Week 5's login is the slice
that owes one, in the same change that gives this route something worth riding.

`@fastify/multipart` is the one runtime dependency added, and the reason is in the commit body: an
HTML file input posts `multipart/form-data`, and hand-writing a parser for a boundary-delimited
stream of untrusted bytes is exactly the work a maintained plugin exists to save. It is Fastify's
own, over busboy. Parts are iterated rather than taken from `request.file()`, whose `fields` carry
only what arrived *before* the file and would have made the handler depend silently on the order of
inputs in the form.

## Three things that moved while this was written

**The page shell moved to `src/kernel/ui/page.ts`.** Doctype, `noindex`, RTL, the token stylesheet,
the brand bar and the common CSS were estate's, and evidence would have been the second copy. The
first copy of a rule is a rule; the second is a divergence with a date on it. Estate keeps its own
nav and its own styles and lost nothing else.

**`.facts` moved to `src/kernel/ui/tokens.css`.** A list of label-and-value pairs is now drawn by two
modules, so it sits beside `.chip` and `.btn` rather than in whichever module happened to draw it
first. Estate keeps only its narrow override for a unit card; the filed screen overrides to a single
column, because three pairs one of which is a 64-character digest wrap into an unreadable block in
two.

**Tenancy exports its first query.** `listUnitTenancies` returns the lettings of one flat as dates
and a status — no person, no isolation predicate, no join that belongs to `src/scope/`. The upload
screen has to offer *which letting is this lease for*, and answering it from anywhere else would
have meant a second module reading tenancy's tables.

## Two seeded types had the wrong marker terms, and the red-first case is what found them

`handover_protocol` and `bank_guarantee` were seeded at 3.1 with terms taken from the **name** of the
form rather than from its printed language, and the policy case refused both specimens in their own
slots on the first run. The terms are now the phrases the tier-1 specimens actually carry:

| type | before (3.1) | after (3.3) |
|---|---|---|
| `handover_protocol` | `פרוטוקול מסירה` … | `פרוטוקול` · `מצב המושכר` · `מונה מים` |
| `bank_guarantee` | `ערבות בנקאית` … | `כתב ערבות` · `אוטונומית` · `בלתי מותנית` |

This is what a guard reading the catalogue buys: the fix was a seed row, not a release. It also says
something about the seed — marker terms written from the title of a form are a guess, and the corpus
is the only thing that can tell a guess from a fact.

## The policy case, and how it was made red

`tests/policy/document-verification.test.ts`, seven cases over the tier-1 specimens and the seed. Red
first, per `docs/pipeline.md` §6 — the case existed before `verifyDeclaredType` did, and the first

✔ accepts every specimen in its own slot            → ✖ handover-protocol.md as handover_protocol

`document-path.test.ts`'s coverage case at 3.2.

## The Verify step — the wrong file, both directions, against tier-1 specimens

Run locally against the running application (`npm run dev`, Postgres 16 on compose, the in-memory
object store), because the acceptance bar is about the interactive path and `app.inject` is not it.

**The specimens were made into real PDFs.** `docs/corpus/` is markdown, and `src/kernel/pdf-sample.ts`
builds Latin-only fixtures on purpose — carrying Hebrew there would need an embedded font and a CMap.
So the two specimens were printed to PDF by headless Chrome, giving a genuine Hebrew text layer with
embedded fonts, and read back through the real `pdfjs` adapter rather than a fake. That is the whole
point of this step: the contract tests inject the reader, and this is the one run where nothing is
injected.

| what was posted | declared as | HTTP | outcome |
|---|---|---|---|
| lease specimen, 34,319 B, filename `שכירות כהן.pdf` | `lease` | 200 | filed, `verified` |
| ארנונה specimen, 20,586 B | `lease` | **422** | refused: `חוזה שכירות` · `המושכר` · `תקופת השכירות` |
| lease specimen | `arnona` | **422** | refused: `המחזיק` · `הרשות המקומית` |
| ארנונה specimen | `arnona` | 200 | filed, `verified` |
| the same lease bytes, second flat | `lease` | 200 | filed, **one document, second link** |
| a PNG with no text layer | `handover_protocol` | 200 | filed, `unverified` |
| a zip | `lease` | 400 | `file is not one of the kinds we store` |

422 and not 400 for a refusal: the request was well formed and the file was wrong, and an operator
who sees a 400 in a log goes looking for a bug in the form.

**What the database held afterwards** — three documents, four links, and the lease counted once:

```
lease              gs://dona-v5-dev-docs/unit/01a0774c-3cc4-…/lease/1e688b5e…415e.pdf
arnona             gs://dona-v5-dev-docs/unit/01a0774c-3cc4-…/arnona/3e952d93…cef9.pdf
handover_protocol  gs://dona-v5-dev-docs/unit/01a0774c-3cc4-…/handover_protocol/518f3980…0b00.png

UNIT:SUBJECT → 1e688b5e   UNIT:SUBJECT → 3e952d93
UNIT:SUBJECT → 1e688b5e   UNIT:SUBJECT → 518f3980
```

**Six audit lines, two of them refusals**, and the filename that was posted appears in none of them:

```
ok     lease              verified    missingTerms []
error  lease              refused     missingTerms ["חוזה שכירות","המושכר","תקופת השכירות"]
error  arnona             refused     missingTerms ["המחזיק","הרשות המקומית"]

ok     lease              verified    (second flat, same documentId)
ok     handover_protocol  unverified
```

The zip wrote **no** audit line, and that is worth stating rather than hiding: the sniffer refuses
before the intake has a type, a place or a digest to record, so a file of no known kind is turned
away at the edge like a malformed request. If that turns out to be the interesting refusal to count,
it is a line in `routes.ts`, not a redesign.

### The screens

The upload form, the refusal and the confirmation, on the dev fixture. Nothing on any of them is a
person: a flat, a building, a type, a date range, a status and a digest is the entire vocabulary, and
`tests/ui/tokens.test.ts` asserts it on the rendered bytes for all five new registry entries.

The refusal returns the form with the declared type still selected and the missing terms as chips —
the form's own printed words, never anything the file said. The confirmation shows the verdict in
words and the digest, and **no `gs://` uri and no link to the bytes**: nothing in this system mints a
signed URL, which is 3.2's carry and stays 3.6's to answer.

## A test that passed on a clean laptop and would have failed on a used one

Worth recording because it was found by using the application rather than by running the suite. The
intake contract tests counted `audit_log` and `document` rows **over the whole table**. Their
transaction is rolled back, so they leave nothing behind — but they can still *see* what a developer
filed through `npm run dev` an hour earlier against the same database, and the manual Verify run
above turned four green cases red. Both counts are now scoped to the place the case invented. Same
lesson as 1.11's two suites racing over one database, in a new disguise: a count that is not about
*this* run is not a fact about it.

## Not in this slice

Said plainly so none of it reads as an oversight.

- **The content cross-check — does the address on the document match the unit it was filed against —
  is week 4's.** It needs extraction; the guard here reads marker terms, which is a statement about
  the *form*, not about the *flat*. `tasks/todo.md` said so before the slice started and it is still
  true after it.
- **No draft tenancy from the upload screen.** 3.3's entry allows binding to an existing letting *or
  a new draft*. A draft is never an empty shell — it needs unit, dates and at least one tenant — so
  declaring one on this screen means three more fields on an unauthenticated form, and at least one
  tenant means **a person's name typed into a page anybody can reach**. The screen binds to an
  existing letting or to the flat alone, and creating a tenancy from a lease is A2's, where the dates
  and the parties come out of the document instead of out of a stranger's keyboard.
- **No OCR.** A file with no text layer is filed `unverified` and says so. 4.1.
- **No documents panel.** What is filed against a flat is not on any screen yet; that is 3.6.
- **No migration**, and no `state` column — see decision 1.
- **`evals/` not run as a gate** — nothing here touches a prompt, a model id, a retrieval config or a
  tool definition (`docs/pipeline.md` §7). Run anyway, unchanged: 1 passed, 0 failed, 2 skipped.

## `infra/docs-delete.sh` — the half 3.2 left to a human, written down

Added while reviewing this slice before it merged, because 3.3 is the slice that starts putting bytes
in the bucket and the question *how does mock data leave again* had no answer in this repository.

The rule is unchanged and is not weakened by this: **the application has no `delete` and the runtime
account has no `objectAdmin`.** Both stay true. What was never in question is whether a person with
owner credentials can remove an object — 3.2's staging verification proved they can, by hand, and
measured what survives afterwards. All this script does is make that act reviewed rather than
improvised.

It is the **inverse of `infra/corpus-delete.sh`** and asserts the opposite thing, which is the part
worth recording because the two files look alike. That one proves a tier-2 document is gone
*permanently*, so it fails while anything is still recoverable and the corpus bucket's soft-delete
window is zeroed at 1.12 to make that reachable. Here the seven-day window is a control chosen on
purpose at 3.2, and clearing mock data by widening the blast radius on a bucket that will hold real
contracts would be trading a control for tidiness. So this script removes the live objects and their
noncurrent versions, **leaves the window alone**, and *reports* what remains restorable rather than
failing on it.

Three refusals, all of which run before `gcloud` is reached, and all four exits were exercised:

```
$ ENV=prod ./infra/docs-delete.sh --all
refusing: dona-v5-prod-docs is the production document store.
  This script does not delete real tenant documents, with any flag.          exit 2

$ DOCS_BUCKET=some-other-bucket ./infra/docs-delete.sh --all
refusing: some-other-bucket is not a dona-v5 docs bucket.                    exit 2

$ ./infra/docs-delete.sh
usage: ./infra/docs-delete.sh <path-prefix|--all>                            exit 2

$ echo yes | ./infra/docs-delete.sh --all
✖ not confirmed — nothing was removed                                        exit 1
```

The confirmation takes the **bucket's own name** and not a `y`. A y/n on a destructive command is a
reflex; typing the bucket is reading it.

Two things it deliberately is not. It is **not wired into any workflow** — `seed:doctypes` and
`docs:probe`'s reason, and more so here. And it has **no prod path at all**, with any flag: the day
a real tenant document genuinely has to be destroyed, that is an act somebody performs with their own
hands and their own reason, and the retention rules that govern it are week 8's IAM pass and F6's,
not a script that happened to exist.
