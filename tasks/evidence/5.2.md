## The structural decision, and the argument for it

**The stance is declared at the route; the guard runs once; a route that declares neither a
permission nor `public` stops the process from starting.**

The obvious implementation was sixteen `await requireStaff(...)` call sites. It was rejected because
it leaves the default for route number seventeen **open**, which is precisely the failure this slice
exists to end: the seven routes were not open because anybody decided they should stay open, they
were open because being open is what happened when nobody said otherwise. Declared-stance inverts
that. `src/app.ts`'s `onRoute` hook throws with the method and the path in the message; `onRequest`
calls `requireStaff` with whatever the route declared; and `public` is a word somebody wrote rather
than the absence of one.

`src/guard.test.ts` asserts the inversion three ways — an undeclared route throws, a **misspelt
permission** throws (`estate.reed` would otherwise boot and refuse every request at run time, which
reads as a broken session rather than a broken route), and a bare Fastify instance is shown
accepting the same route, which is the control.

**`onRequest` and not `preHandler`** for the guard: it runs before the body is parsed, so an
unauthenticated 20 MB upload is refused before a byte of it is read.

**An unmatched path answers the same redirect as a guarded one.** A 404 for the paths that do not
exist and a login redirect for the ones that do would tell a stranger which is which. This changed
`src/app.test.ts`'s 404-shape case, which now signs in first — and the change is the finding rather
than a chore.

## The CSRF token: derived, never stored

`sha256('csrf:' + <session token>)`, computed from the `HttpOnly` cookie the request already
carries. No column, no second secret, and `tests/policy/staff-session.test.ts` — *no column in this
database whose name contains `token` may be anything but a `_hash`* — stays green **by construction**
rather than by anybody remembering it.

**The domain separator is not decoration.** Hashing the bare session token would make the CSRF value
equal to `staff_session.token_hash`, so anyone who could read one row would hold a valid CSRF token
for that session — a database read turned into half a forged write. *Renders the token into the form
the screen serves, and the same token verifies* asserts the rendered value both equals
`csrfTokenFor(token)` and **differs from the `token_hash` the row holds**.

Scope is every write route in the application. The two `GET /staff/auth/*` routes are outside it on
purpose: they change no row of ours, and `state` is the anti-forgery value that flow carries by
construction. `POST /staff/logout` is `public` and still token-checked, because the hook keys on the
**presence of a session cookie** rather than on the route's stance — an operator whose role was
withdrawn holds a live session with no permission at all, and a logout behind a permission would
leave them unable to sign out of a system that will not let them do anything.

**`POST /documents` verifies its own token**, declared as `csrf: 'in-body'`, because its body is a
multipart stream a `preHandler` would consume. It calls the same `verifyCsrf` — one comparison, a
second call site, not a second implementation — and *marks exactly one route as verifying its own
token* asserts that the exemption has not spread.

`sameValue` moved from `src/staff/internal/routes.ts` to `src/kernel/compare.ts` in the same change,
because a four-line constant-time compare with two callers is exactly the size of thing that gets
copied and then diverges.

## The defect this slice's own Verify step found

**`renderIncompletePage` served an empty token, and every gate was green.**

The view took `csrf` as a parameter with a default of `''`. That type-checks at every call site, so
the estate route that never passed one compiled, rendered, and served a form whose hidden input was
`value=""` — a form that would be refused on every submit. `tests/ui/tokens.test.ts` could not see
it: that guard renders the **view** with a token, and the bug was in the **caller**.

It was found by clicking `/estate/incomplete` on `:3000` before merge, which is what
[docs/pipeline.md](../../docs/pipeline.md) §8's restart-and-click step is for, and it is the second
time that step has caught something no suite could have (the first was the Hebrew day counts at
2.6).

Two things changed, not one. The default is gone, so a route that forgets now fails to compile. And
because a fix for one screen is not a rule, `src/guard.test.ts` gained *never serves a form with an
empty token*, which signs in, GETs the screens, and asserts every rendered `name="csrf"` value equals
this session's token. Proved red by restoring both halves of the defect:

```
✖ never serves a form with an empty token
  AssertionError: /estate/incomplete served a bad token
```

### And then CI found that this new case was asserting a fixture

**The first push failed the gate, on the test written above.**

```
✖ never serves a form with an empty token
  AssertionError: /estate/incomplete renders no token at all
```

`/estate/incomplete` renders **one form per incomplete tenancy**. The developer database it was
written against had two; CI's is clean and has none, so the screen rendered no form, and
`assert.ok(values.length > 0)` was asserting the *fixture* rather than the property. It is the
failure `src/kernel/boundary.test.ts` names in its own words — *a guard over an empty set is a guard
that passes because it looked at nothing* — arrived at from the other side: the guard did not pass,
it failed, and it failed for a reason that had nothing to do with the code under test.

The fix moves the assertion to where the fixture is. `src/guard.test.ts` keeps `/` and `/staff`,
which render the sign-out form whatever the database holds, so their floor is real. The screen that
carried the defect is asserted inside `src/estate/routes.test.ts`'s *a document-backed draft with no
ערב is in the incomplete queue* — the case that **builds** the tenancy that makes the form exist.

That relocation was then proved red the same way, and it caught a second version of the same
mistake in the first attempt at it: `assert.equal(tokens.length, 1)` failed locally with `actual: 2`,
because a developer's database holds whatever `npm run seed:register` left. The assertion that
survives is a floor of `> 0` — guaranteed by the row the case creates — plus **every** token
checked, which is the property rather than the count.

**Nothing about the production defect changed**; what changed is that the test proving it is fixed no
longer depends on which database it runs against. Cost: one red CI run, which is where that class of
thing is supposed to be found.

## The never-a-name rule: **KEPT**, and that is the decision

`tasks/todo.md` says this slice may lift the rule that every screen shows a state and a count and
never a name, that lifting it is a decision it records, that keeping it is equally an answer, and
that what is not allowed is the rule lapsing because a session arrived.

**It is kept.** A session says who is asking; it does not by itself make a household's name lawful
to show. The two things that would are not true yet: `national_id` is not unreachable by an agent
tool until **5.3**, and SPEC.md's *"every scoped read of tenant data is logged"* has no screen-level
reader. **5.5** is also about to change what these screens show, and relaxing a rule against screens
that are about to change shape is how a relaxation outlives its argument.

The wording was **tightened** rather than relaxed: *never a **tenant's** name*. The staff board has
shown the **operator's own** email since 5.1, and that was never the rule's subject. **Reconsidered
at 5.4**, which is already deciding what a session unlocks in evidence.

Recorded in `SPEC.md` (the UI paragraph), `SPEC-estate.md`, `SPEC-evidence.md`, `SPEC-scope.md`,
`SPEC-flows.md` and in `tests/ui/tokens.test.ts`'s *shows a state and a count, and never a person*,
whose comment now says the rule survived the slice entitled to lift it rather than that week 5 will
decide.

## The per-caller cap: the number, and why it needed a migration after all

**Fifty filed documents per operator per rolling 24 hours**, counted from `audit_log` rather than
from a new counter column. The log already records exactly the event being bounded; a counter column
would be a second place the same fact lives, and it would drift the first time a write path forgot
it. `evidence.file_document` lines gained `actor_id` in this slice — **which is not `uploaded_by`**,
still 5.4's: a log line records that a person did a thing at a time, a column asserts a fact about a
row that other code may join on.

Fifty is chosen as a bound on a runaway rather than as a budget, which is 3.3's own reasoning for its
twenty megabytes. A person filing paper for 1,500 units files a handful in a day; bulk arrives
through the register importer and 3.4's Drive ingestion and goes nowhere near this route. If an
operator ever legitimately reaches it, the number is wrong and moving it is one line and one evidence
file — a better failure than discovering the bucket has been full for a week.

**The plan said no migration and that was wrong**, corrected during the work. `audit_log` has had two
indexes since 0002_ — `(at DESC)` and `(subject_id, at DESC)` — and neither answers "how many times
did this actor do this thing". Without `0023_audit_actor_index.sql` the cap turns every upload into a
scan whose cost grows with the age of the system: invisible for six weeks, then the incident. It runs
on the hot path of the one route in this system allowed to be slow for a legitimate reason, and a
slow route that is slow for two reasons is a route nobody can measure. One index, no table, no
column.

**`too_many` → 429 was added to `ErrorCode`**, the sixth. A cap refusal answering `not_allowed`/403
tells an operator "you may not do this" when the truth is "not this many, not today", and sends
somebody to read the role matrix for an answer that is not in it.

## Raised here, and where each is owned

- **`request.staff` is set for every guarded route and read by exactly one handler.** `POST
  /documents` names the operator; every other write route still records a **user-typed** name in
  `confirmed_by`, `promoted_by` and the exception's `actor: 'console'`, which is now a snapshot
  string beside a known identity. → **5.4**, with `uploaded_by`, which is the slice that owns
  provenance. Carried into `tasks/todo.md` and `tasks/roadmap.md` § 5.4.
- **The role mapping is a first cut and one entry is arguable.** `/documents/:id/promote`, `seed` and
  `tenancy` ask for `tenancy.write` because that names what changes, not the screen it changed from.
  A VIEWER can therefore read a document and not promote a field from it, which is right, and an
  OPERATOR can do both. Nothing tests that the mapping is the *intended* one — only that each route
  has one. → **5.8**, the settings screen, which is the first slice with an operator looking at the
  matrix. Carried.
- **`tests/support/session.ts` is the first shared test helper in this repository.** Eight suites now
  drive routes as an operator, and the three lines that mint a session would otherwise be copied into
  each. Nothing enforces that a new suite uses it. → noted here; it earns a guard the first time a
  ninth suite copies the lines instead.
- **The consent screen and the shared identity configuration are unchanged** and remain **week 12**'s,
  exactly as 5.1 and 5.1b left them. This slice did not touch either.
