## The convention

```
gs://<bucket>/<place kind>/<place id>/<type key>/<file hash>.<ext>

gs://dona-v5-staging-docs/unit/019a4c7e-2b31-7f0c-8d55-6f1a0d3e9b42/lease/3f9c…8a1.pdf
```

`document.storage_uri` has been `NOT NULL` since 3.1 with nothing to fill it. This is the rule that
fills it, and it lives in `src/evidence/internal/storage-path.ts` rather than in the kernel because
the object store is handed paths and never invents one (SPEC-kernel.md).

### Four calls, and why each went the way it did

**1. The path is rooted at a place, and the rule is enforced by type rather than by care.**
`DocumentLink` carries eight `entity_type` values; `PlaceKind` carries four — `PROJECT · BUILDING ·
SPACE · UNIT`. `TENANCY`, `PARTY`, `ASSET` and `OBLIGATION` are simply not expressible, so *the path
carries the place and never the people* is a compile error rather than a review comment. The
alternative — one union with a runtime check — is the same rule written where somebody can be
talked out of it.

The interesting exclusion is `TENANCY`, not `PARTY`. [SPEC-flows.md](../../SPEC-flows.md) invariant 1
says the *upload's* primary binding is the tenancy, so rooting the path there would have looked
correct. It is not: a tenancy is temporal, and a path rooted at one scatters a single flat's papers
across its lettings — the filing cabinet stops answering *what is filed against unit 14*, which is
the question week 3 exists to answer in four seconds. The tenancy stays a `document_link` row, which
is where a temporal fact belongs.

**2. Validated, never sanitised.** A builder that cleans a street name into a path segment **is** the
failure this convention was written against, wearing a helmet: two streets that transliterate alike
would file one flat's lease under another's, the caller would get a plausible path, and nothing about
the row would look wrong afterwards. So a uuid, a `type_key`-shaped word, a 64-character lowercase
digest and an extension from a four-item list are the only things that reach the string, and
everything else is `invalid` at the edge. The refusals are half the test file.

**3. The leaf is the `file_hash`, not the `document_id`.** `document.file_hash` is `UNIQUE` and
`ingestDocument` upserts on it, so a `document_id` leaf would have stranded an object every time a
re-ingest returned the existing row rather than the fresh uuid the caller had already written under.
Hashing first makes the whole path computable before anything is written, which is also what the
ingest ordering rule carried to 3.3 depends on.

**4. `storage_uri` names its bucket, and a read refuses a bucket that is not the configured one.**
The column could have held a bare path. A database cloned from staging to a laptop carries staging's
rows, so a self-describing uri turns *this row belongs to another environment* from invisible into
refusable. The path is re-validated on the way out as well, so a hand-edited row cannot point a read
at an arbitrary object in the bucket — the rule holds in both directions, which is the whole content
of the fourth test in the policy case.

## The delete refusal, which holds twice

The bar is *the app can write and read a contract and cannot delete one*, and it is met by two
independent controls rather than one:

- **`ObjectStore` has no `delete` method**, and `src/kernel/objects.test.ts` asserts the key set is
  exactly `describe · put · read`. This is the control a reader can check without a cloud console.
- **The runtime account has `objectViewer` + `objectCreator` and not `objectAdmin`**, re-applied on
  every `bootstrap.sh` run since 1.5.

Proving only the first would be proving our own politeness, so `src/docs-probe.ts` **goes around the
missing method on purpose** — a raw `DELETE` against the JSON API carrying the store's own bearer
token. Worth noting that the OAuth scope the store requests, `devstorage.read_write`, *does* permit
deletion; what refuses it is the IAM grant, which is the thing under test.

## The bucket, and a control nobody had chosen

`bootstrap.sh` created the docs bucket closed at 1.5 and re-applied uniform bucket-level access,
public-access prevention and versioning on every run. Three controls. The fourth was a Cloud Storage
default: **soft delete, seven days**, which slice 1.5 recorded as an open observation — *a
"permanently removed" claim and a seven-day recovery window are not the same statement* — and which
1.12 answered for the corpus bucket and not for this one.

Decided here, and deliberately in the **opposite direction** from the corpus bucket:

| | docs bucket | corpus bucket (1.12) |
|---|---|---|
| versioning | **on** | off |
| soft delete | **7 days, explicit** | cleared (`retentionDurationSeconds: 0`) |
| lifecycle | none | delete at 90 days |
| why | the object is the only copy of a signed contract, and there is no removal date | the exposure has an end date, and recoverability would make `corpus-delete.sh` a lie |

The value did not change — it was 604800 seconds before and after. **What changed is that it is
chosen.** A control that exists only because a vendor defaulted to it is a control nobody decided,
and the next default change is a silent policy change. `bootstrap.sh` now also reads the four
controls back and prints them, for the same reason 1.5 prints the organisation warning: the output is
read every time, and the document is read when somebody remembers to.

```
▸ Private document store gs://dona-v5-staging-docs
  uniform=True  public_access_prevention=enforced  versioning=True  soft_delete=604800
  app-staging: objectViewer + objectCreator, and NOT objectAdmin
```

**Both environments, and the second run of each was a no-op.** A normalised inventory — the four
controls plus the bucket's full IAM policy — captured after the first `bootstrap.sh staging` and
again after the second:

```
$ diff bucket-01.txt bucket-02.txt
$ echo $?
0
```

## Four things found while reading, all in files this slice owns

**1. `DOCS_BUCKET` was injected by the deploy and read by no code in this repository.**
`SPEC-kernel.md` has said since the 1.4 lift that *which store is running is reported at boot*, and
`deploy.yml` has set `DOCS_BUCKET=dona-v5-staging-docs` since 1.6. Nothing read it. So a revision
serving off the in-memory store — every document written into a container that scales to zero — would
have looked exactly like a revision serving off the bucket, and the sentence that existed to make
that visible was a claim. `src/serve.ts` now builds the store and prints `describe()`, and
`createConfiguredStore` is where the memory fallback lives so the boot line and the probe cannot
disagree about which store this process has.

This is the same shape as the guard-one defect at 1.7 — a control written against a path that
matched no files, passing forever and reading like diligence. A spec sentence with no code behind it
is that, one layer up.

**2. `src/kernel/objects.ts` cited `SPEC-occupancy.md`**, a v3 filename that has never existed in
this repository: the 1.4 lift brought the comment along with the code. Repointed at
`src/evidence/internal/storage-path.ts` and `SPEC-evidence.md`, which now exist and are what it
meant. `objects.test.ts` asserted on `dona-v3-staging-docs` for the same reason.

**3. The soft-delete window above.**

**4. `bootstrap.sh prod` had stopped working entirely, and this slice is why anyone noticed.**

A STOPPED Cloud SQL instance answers `Invalid request since instance is not running` to **both**
`gcloud sql databases describe` and `gcloud sql databases create`, so the describe-or-create pair
failed outright rather than being a no-op, and `set -e` killed the run:

```
▸ Cloud SQL dona-prod (first run takes several minutes)
ERROR: (gcloud.sql.databases.create) HTTPError 400: Invalid request since instance is not running.
```

Everything after that line — the service accounts, the secret grants, **the bucket and its four
controls**, and the Workload Identity binding — works perfectly well against a stopped instance and
never ran. And the reason the instance is stopped is slice 1.5's own cost lever: 1.5 recommended
`--activation-policy=NEVER` on `dona-prod` until week 12, because prod has nothing to serve and
nobody to serve it. **A saving in one slice quietly made another slice's headline claim —
"Idempotent — safe to re-run" — false for prod, and it stayed false until a slice needed to reapply a
control there.**

The state is checked now rather than inferred from an error, and a stopped instance skips the
database step **loudly** and lets the rest of the run finish. Skipping quietly would have been the
worse fix: the database step is the one that *creates* something, and "it was already there" and "we
never looked" must not print the same way.

```
▸ Cloud SQL dona-prod (first run takes several minutes)
  !! dona-prod is STOPPED, not RUNNABLE — skipping the database step.
     Everything after this point does not need the instance. To finish it:
     gcloud sql instances patch dona-prod --activation-policy=ALWAYS --project dona-v5
…
▸ Private document store gs://dona-v5-prod-docs
  uniform=True  public_access_prevention=enforced  versioning=True  soft_delete=604800
  app-prod: objectViewer + objectCreator, and NOT objectAdmin
```

Prod's docs bucket now carries the same four controls as staging's. This is closed here, not carried:
the script prints the one command that finishes the job, which is the level of memory a person should
need.

## The policy case, and how it was made red

`tests/policy/document-path.test.ts`. The constraint is deterministic — no model ever proposes a path
— and the failure has isolation flavour, which is what puts it in this suite rather than only in the
module's own tests. `tests/policy/guards.test.ts` is the precedent for a case here that asserts
against TypeScript rather than against SQL.

**Red first**, per `docs/pipeline.md` §6. The `PlaceKind` lookup in `documentObjectPath` and the
reverse lookup in `parseObjectPath` were both replaced with a `String(kind).toLowerCase()` fallback,
so all eight `LinkEntityType` values built a path:

```
✔ accepts the four place kinds
✖ refuses the four E13 kinds that are not places
    AssertionError: Missing expected exception: TENANCY must not be a path root
✖ refuses them on the way back out as well as on the way in
    AssertionError: Missing expected exception: TENANCY must not parse as a path root
✔ covers every value E13 allows, so a ninth kind cannot arrive unclassified
ℹ tests 4  ℹ pass 2  ℹ fail 2
```

Two of the four, and not four of the four, because `assert.throws` stops at the first kind in the
loop and that kind is `TENANCY`. The checks were restored and all four passed. The fourth case is
the one that will matter later: it asserts the two lists cover all eight `entity_type` values, so a
ninth kind added to `DocumentLink` fails this case until somebody decides which side of the line it
falls on. That decision *is* the constraint.

## Not in this slice

Said plainly so none of it reads as an oversight.

- **No upload screen, no verification guard, no `document` row written by this code.** 3.3 owns flow
  A1's interactive path; what this slice ships is the convention it will call and the bucket it will
  call it against. `ingestDocument` and `linkDocument` landed at 3.1 and are untouched.
- **No signed URLs.** A signed URL is a bearer token for one object — whoever holds the string reads
  the document, isolation join or not — so issuing one is a decision that belongs behind a session,
  and sessions are week 5's. Carried to 3.6, which is the first slice that would want one.
- **No retention rule and no deletion path for the docs bucket.** 1.12 built both for the corpus
  bucket, where an exposure has an end date. A signed contract does not, and inventing a retention
  period for one is a legal question rather than an engineering call.
- **`evals/` not run locally** — nothing here touches a prompt, a model id, a retrieval config or a
  tool definition (`docs/pipeline.md` §7). CI runs it.

## What this slice carried, and to where

Per `docs/pipeline.md` §8 step 7, every item is in the entry of the slice that closes it, in
`tasks/todo.md` **and** `tasks/roadmap.md` — not only here.

- **→ 3.3 — the ingest order, and it is not the obvious one.** Hash the bytes → look the hash up →
  `put` the object **only when no document already holds it** → `ingestDocument`. Hashing first is
  what makes the path computable before anything is written; looking up before putting is what stops
  the same bytes filed against a second place writing a second copy of one file. `ingestDocument`
  excludes `storage_uri` from its update path, so the first path filed stays authoritative whatever a
  later caller computes. The path is built by `documentObjectPath` and **never by string
  concatenation**, and the accepted file types are `documentExtensions` and not a second list in the
  upload handler.
- **→ 3.6 — the documents panel shows a path, never a link to the bytes.** See *No signed URLs*
  above.
- **→ week 8 — the docs buckets' legacy `projectEditor` / `projectOwner` bindings carry
  `legacyObjectOwner`, which includes delete.** 1.5 raised it, 1.12 answered it for the corpus bucket
  only, and it has had no owner for the docs buckets since. This slice proved the *application*
  cannot destroy a signed contract; a human with project editor still can. It is inherent to a GCS
  bucket in a project with basic roles rather than something `bootstrap.sh` chose, so it belongs in
  the same IAM pass as 1.5's `run.admin` scoping — week 8, whose demo is *try to break isolation*.
