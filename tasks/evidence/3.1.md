## The acceptance bar, measured rather than read

> **Done when:** adding a ninth document type with four fields of its own is a seed row and a
> re-deploy of data — **no migration**.

3.0 raised that the seed is **nine** types and not eight, which makes the bar the **tenth**. It is
proved inside a test, on `applyDocumentTypeCatalogue` — the same function `npm run seed:doctypes`
calls, not a parallel path written to pass:

```
before = SELECT table_name||'.'||column_name||':'||data_type||':'||is_nullable
           FROM information_schema.columns
          WHERE table_name IN (document, document_link, document_type, document_type_field)
          ORDER BY table_name, ordinal_position

  applyDocumentTypeCatalogue(db, [ ועד בית agreement, 4 fields ])
    → { types: {created: 1, updated: 0}, fields: {created: 4, updated: 0} }

after  = <same query>
assert after === before          ✔  adding a document type moved no column of DDL
listDocumentTypes()              ✔  the tenth type is in the picker
documentTypeFields(tenth, today) ✔  agreement_date · notice_period_days · renews_automatically · scope
ingestDocument(… tenth …)        ✔  and a document can be filed against it immediately
```

*No DDL was needed* is a claim a reading eye supplies for itself, which is why it is a snapshot
comparison and not an inspection. **Extract nothing** — the slice's own words — is the point: the
declaration costs no schema change today, and filling it is week 4's.

The seed itself, run twice:

```
$ npm run seed:doctypes
seed:doctypes: types  — created 9, updated 0
seed:doctypes: fields — created 11, updated 0
$ npm run seed:doctypes
seed:doctypes: types  — created 0, updated 9
seed:doctypes: fields — created 0, updated 11
```

Counted from the upserts (`xmax = 0`) and never from the tables, for 1.11's reason: a count that is
not about *this* run is not a fact about it.

### Why the seed is data and not a backfill migration

`SPEC.md` says DDL and backfill go in separate files, so a `0012_document_types.sql` would have been
in-convention and would have been **wrong**. If the nine arrived in a migration, the tenth would be a
migration too, and the acceptance bar would have been false the day it was written. The catalogue is
`src/evidence/fixtures/document-types.ts` applied by `npm run seed:doctypes`, wired into no workflow,
which is `src/seed.ts`'s and `npm run seed:register`'s shape and reasoning both.

## Nine types, and the ninth is the one a demonstration would have dropped

`lease · lease_amendment · termination_notice · arnona · insurance · id · bank_guarantee ·
handover_protocol · inspection_certificate`. The first eight are the published Data Model's;
`inspection_certificate` has been in the workbook since 3 Sep because SAFETY assets and the
compliance tab need it, and **3.5 needs it this week**. Seeding eight so the demonstration could land
on "the ninth" would have been a knowingly incomplete seed dressed as a proof. `seedDocumentTypes.length === 9`
is asserted, because a decision nothing asserts is a decision somebody helpfully undoes.

**Eleven field declarations across three types, and that asymmetry is deliberate.** `lease` (6),
`lease_amendment` (3) and `handover_protocol` (2) are the types week 4's comprehension reads first —
A2 and A3 make the first two certain, and the third is 3.5's source. The other six carry their guard
terms and no fields: **a type with no declaration is fileable, citable and searchable**, which is the
open half working, and its fields are appended as a new `effective_from` row when the concept work
reaches it (`SPEC-flows.md`: three to five types with a handful of specimens each is the working unit).

Two of the six are empty by **rule** rather than by schedule, and both are recorded on the fixture:

- **`id`** — a declared `id_number` field would put `national_id` on the capture path, where it is
  citable and searchable by design. `SPEC.md` says it is admin-only, unreachable by any agent tool
  and access-logged. If that type ever declares fields, the policy suite decides which.
- **`arnona` and `bank_guarantee`** — the two documents where an amount is printed and the temptation
  is sharpest. `value_type` has no `MONEY` member to declare one with, and the test asserts the
  rejection rather than trusting the absence.

`handover_protocol` declares **`handover_date`**, which is the fact that discharges week 2's carried
item at 3.5: every building card's מסירה date is currently one of its leases' start dates, and
תקופת הבדק starts at handover, so `warranty_end_date` and a ternary responsibility decision are
resting on a guess until this field is filled from this document.

## E12 against the published Data Model — four columns, four reasons, four owners

3.0 raised it and left it: *a column is either in the first DDL or it costs a migration later.* The
published Data Model is the authority on what the system is (`docs/README.md`), so omitting four of
its columns is a deviation that has to be argued rather than assumed. **All four are omitted.** Each
is a nullable `ADD COLUMN` when it comes, which is the cost being accepted rather than hidden.

**`state` → carried to 3.3.** Figure 5's `RECEIVED → EXTRACTED → ACCEPTED / REJECTED` is the *review
queue's* state machine, and the review queue is 3.4, deferred 6 Sep with F4. With type declared
rather than detected, nothing in this week branches on a document state, and a state column nothing
reads is a second state machine invented ahead of its flow, standing beside `calls`' real one
(foundation rule 3). **But figure 4's caption is not covered by that**: *"REJECTED is a state, not a
deletion — the wrong file is evidence too, of what someone tried to file and when"*, while 3.3's own
bar says the ארנונה bill is *caught before it is filed*. Those two disagree. Deciding it here would
have been deciding it away from the slice that meets it, so 3.3 carries the question with both halves
stated.

**`superseded_by` → carried to week 5.** It looks urgent because of A3 and is not, because
`SPEC-flows.md` invariant 2 already relocated it: *an addendum is not patching a document, it is
contributing a value to a tenancy*. Supersession is a fact about **values**, and values carry their
own provenance (4.2, 4.3) — A3's "the later document wins and the earlier value is retained, visibly"
is a statement about two provenances, not about a pointer between two rows. The remaining case is a
genuinely re-issued document — a corrected ארנונה bill, a renewed certificate — and E12 already
answers it: the current one is the one whose `valid_from`/`valid_to` window covers today, which is a
**fact** rather than a pointer somebody has to remember to set. Week 5 is the amendment week and is
where that ruling gets tested against real promotion.

**`tenant_visible` → carried to week 9.** The sharpest of the four. A per-row boolean deciding what a
tenant may see is a **second access control standing beside the isolation join**, and foundation rule
1 is that the scope is a view and never a column. The rule's own justification is that *a model that
misbehaves cannot widen a scope it never held* — but it can be handed a row whose boolean somebody
flipped, and a boolean is exactly the artefact that gets flipped at 16:00 on a Thursday by someone
trying to be helpful. What a tenant may see is derived from `document_link` through `src/scope/`. If
week 9 finds a class of document that must stay admin-only *inside its own tenancy*, that is a
property of the **type** — one row, one rule, readable in a dispute — and never of each document.

**`uploaded_by` → carried to week 5.** There is no authenticated actor in this system: the five
screens have been unauthenticated since week 1, deliberately, and staff auth is week 5's. The column
could only have held a placeholder, and a provenance column holding a placeholder for six weeks is
worse than one that arrives with the identity it names — it reads as an answer.

**Flagged to the director and owned by no slice:** the published Data Model is now out of step with
the schema in those four columns *and* in the name (`DocumentSchema` is E15 `DocumentType`). The
repository is not out of step with itself — every difference is recorded here and in
`SPEC-evidence.md`. Whether the **artifact** is republished is a promise to the client and therefore
not a slice's to make, which is the treatment 3.0 gave the "Monday" wording.

## Two calls beyond the acceptance bar

### 1. `document_is_immutable` — the first trigger in this repository

"`file_hash` at ingest; immutable thereafter" was a sentence in `todo.md` with nothing behind it, and
this repo had no triggers, so adding one is a structural call rather than a detail. It is here
because 2.1's principle is that the claim is what **the database** refuses, not what the application
declines to offer: a hash that can be updated proves nothing, since the whole value of the column is
that the row cannot later be made to describe a different file. `storage_uri` travels with it —
repointing the URI achieves the same substitution without touching the hash.

The rest of the row is not frozen. A document re-filed with a corrected validity window is the same
evidence, better described, and the test asserts that `UPDATE document SET valid_to = …` still works.
Deletion is not blocked here either: retention and the deletion path are the bucket's (1.12), and a
document withdrawn is a different decision from a document rewritten.

It raises `restrict_violation` (`23001`) rather than the default `P0001`, so a caller can tell this
rule from any other `RAISE` somebody adds later.

`ingestDocument`'s update path deliberately excludes both protected columns, so a re-ingest is a
no-op on them rather than an `UPDATE … SET file_hash = file_hash` that trips the trigger it obeys.

### 2. `UNIQUE (file_hash)` carries the criterion, not the caller

*The same file ingested twice is one document with two links* is a statement about repetition, so it
belongs where repetition is decided. `ON CONFLICT (file_hash)` means the second ingest **finds** the
row — whoever calls it, however many times, and including a second caller written next month that
knows nothing about this criterion. The proof that it is load-bearing is in the red-first pass below:
without the unique key the upsert cannot even be expressed.

## Every rejection proved red first

Nine constraints. For each: remove it from the live schema, run the case that asserts it, watch it
fail, put it back. A case that was green before and after the change it was written for tested
nothing (`docs/pipeline.md` §10).

| # | Constraint | Case | Red without it |
|---|---|---|---|
| 1 | `document.document_type_id` FK → `document_type` | *is deactivated, never deleted* | `DELETE` succeeded — expected `23503` |
| 2 | `document.document_type_id NOT NULL` | *refuses a document with no type at all* | insert succeeded — expected `23502` |
| 3 | `document_type_field_natural_key` UNIQUE | *refuses two declarations of one field* | **`42P10`** — see below |
| 4 | `value_type` CHECK (no `MONEY`) | *has no MONEY value type* | `'MONEY'` accepted — expected `23514` |
| 5 | `document_type_field_version_is_ordered` | *closes before it opens* | accepted — expected `23514` |
| 6 | `document_validity_is_ordered` | *ends before it starts* | accepted — expected `23514` |
| 7 | `document_is_immutable` trigger | *keeps file_hash and storage_uri immutable* | `UPDATE` succeeded — expected `23001` |
| 8 | `document_link.entity_type` CHECK | *not one of the workbook's eight* | `'INVOICE'` accepted — expected `23514` |
| 9 | `document.file_hash` UNIQUE | *one document with two links* | **`42P10`** — see below |

**Rows 3 and 9 failed differently, and the difference is worth recording.** Both are unique keys the
module's upserts name as their `ON CONFLICT` target, so removing the key does not produce a silent
duplicate — it produces `42P10`, *"there is no unique or exclusion constraint matching the ON CONFLICT
specification"*, and the statement cannot be expressed at all. That is a **stronger** red than the
one the case was written for: the key is not an optimisation the commands happen to benefit from, it
is the thing they are written in terms of.

The probe script is not committed. It removed one constraint at a time and restored it, and the
schema was verified intact afterwards (`\d document` shows the FK, the unique constraint, the CHECK
and the trigger). What is committed is this table.

## Guard three fired zero times, and three `not-pii` sentences were written anyway

Week 2 owed this slice a note: *a document row is not person-shaped, but `DocumentTypeField` will
describe fields that are, and `scripts/guards.ts` fires on the column, not the intent.*

```
guard no-current-tenant-column:        ok — 11 files scanned
guard isolation-join-lives-in-src-scope: ok — 117 files scanned
guard pii-columns-are-commented:       ok — 11 files scanned
```

**No column in the four tables is person-shaped by name**, so the guard is silent and correctly so.
The interesting case is the one it cannot see: `document_type_field.field_key` is `tenant_name`,
`label_he` is `שם השוכר`, and `extraction_hint` is the phrasing printed beside the name on the form.
Those three columns **name** personal data without ever holding any — the value itself lands in
`ExtractedField` at 4.2, under its own marking — and that is exactly the question a reviewer will
ask. So all three carry `-- not-pii: names a field, never holds a value`, which is the guard's escape
used where the guard has no reach. **Guard three fired zero times; three escape sentences written
deliberately.**

Guard two also stayed silent on `document_validity_is_ordered`, and it was checked rather than
assumed: `valid_to IS NULL OR valid_to >= valid_from` rides the same-row-ordering exception 2.1 wrote,
because comparing `valid_to` against the other column of the same row is true of every well-formed
row and therefore cannot express "valid on day D". `document_type_field`'s version CHECK uses
`effective_from`/`effective_to` and does not touch either pattern.

## What the module refuses

`src/evidence/contract.ts` exports six catalogue and document commands and **no query that returns a
person**, which is 2.6's owed item and the same sentence `src/tenancy/` and `src/parties/` already
carry. Documents bind to parties — `entity_type = 'PARTY'` is one of R13's eight — and who those
parties are is `src/scope/`'s answer and nobody else's. A document panel shows what is filed, not who
signed it, until week 5 puts a session behind the screens.

There is also **no delete on the contract**, anywhere. `document_type` is deactivated
(`is_active = false`), and the foreign key refuses the delete regardless — but an absent function is
what stops anyone asking.

`entity_id` on `document_link` carries **no foreign key**, and that is R13's price stated in the
migration rather than left to be noticed: it points at eight different tables. The alternative — six
nullable columns on `document` with a CHECK that exactly one is set — buys integrity for the entities
we thought of and refuses the eighth, which is R13's own argument against it.
