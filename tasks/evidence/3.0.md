# Slice 3.0 — Workbook pass: the document-type catalogue

**Closed 2026-09-07.** Week 3's first slice and the only one in the week that writes no code. The
workbook in [docs/model/](../../docs/model/) is the specification for month one's tables, and it had
`Document` carrying a fixed enum of nine type keys with no catalogue behind it. This pass adds the
catalogue — **E15 `DocumentType`**, **E16 `DocumentTypeField`**, **R17**, **R18**, and **A8** on the
DECISIONS sheet — so that 3.1 writes DDL against a specification rather than against a chat
description.

It is first in the week deliberately. A migration written ahead of the workbook is the anti-pattern
this project has already named once, and 3.1 is the migration.

---

## Append-only, measured rather than asserted

R1–R16 are cited in the frozen Hebrew workbook and across this repository. Renumbering or rewording
one silently invalidates every citation, and the failure is invisible: nothing breaks, the citations
just stop meaning what they meant. So the claim had to be checked, not stated.

The check is stronger than a re-run diff, because of one fact established first:

```
$ python docs/model/build_model.py
$ diff <dump of committed .xlsx>  <dump of freshly generated .xlsx>
REGEN MATCHES COMMITTED ARTIFACT — generator is the source of the committed file
```

The `.xlsx` committed on 3 Sep regenerates **cell for cell** from `build_model.py` as it stood before
this slice. The workbook in the repo is genuinely a build output and has not been hand-edited since
it was generated, which is what `docs/model/README.md` claims and what nothing had ever confirmed.
That makes the committed artifact a legitimate baseline, so the after-diff is against **the file the
project has been reading for four days**, not against a re-run of my own that could have drifted with
the script.

Against that baseline:

```
R1-R16 unchanged, cell for cell: YES  (16 -> 18 rows)   appended: ['R17', 'R18']
E1-E14 unchanged:                YES  (14 -> 16 rows)   appended: ['E15', 'E16']
D1-D6  unchanged:                YES  ( 6 ->  7 rows)   appended: ['A8']

FIELDS rows 115 -> 134
```

**Exactly three pre-existing FIELDS rows changed, all three on E12**, and both substantive changes
were forced by the catalogue rather than chosen (below). Every other row in every other sheet is
byte-identical. The acceptance bar — *the FIELDS sheet specifies every column of both new entities* —
is asserted by count in the same script rather than read off the screen, because a column omitted
from a specification is exactly the kind of thing a reading eye supplies for itself.

The Hebrew workbook (`build_model_he.py`, `dona-building-unit-model-draft-HE.xlsx`) was **not
touched**. It is frozen at an older state on purpose and regenerating it is the director's decision,
not a chore.

## What the two entities carry

**E15 · DocumentType** — six columns. `document_type_id` · `type_key` (unique, nine seed rows) ·
`label_he` · `label_en` · `verification_terms` · `is_active`.

**E16 · DocumentTypeField** — nine columns. `document_type_field_id` · `document_type_id` ·
`field_key` · `label_he` · `value_type` · `is_required` · `extraction_hint` · `effective_from` ·
`effective_to`. Unique on `(document_type_id, field_key, effective_from)`, so redeclaring a field is a
new row and never an edit.

Both also carry a `—` row in the FIELDS sheet naming what is deliberately absent, which is the
convention E1 `Project` and E7 `Tenancy` already use for the same purpose: an absent column that was
decided reads differently from one that was forgotten.

## Three decisions this slice made that the acceptance bar did not ask for

### 1. There is no `promotes_to` column, anywhere

The published Data Model's `DocumentSchema` card lists `promotes_to · target entity`. It is not in
E15 and not in E16, and that is the sharpest thing in this pass.

A8 is two halves: capture is open, promotion is governed. A `promotes_to` column on a catalogue row
makes promotion **a row** — an admin adds a field on Tuesday, names a target column, and an extracted
value starts writing to something the isolation join reads. That is precisely the failure the
workbook already ruled out when it made `asset_type` guarded rather than admin-editable, and A8 says
so in as many words. The mapping from a captured field to a typed column is `FieldPromotion`, it is
its own entity, and it costs a migration — which is 4.3's slice and is unaffected by this decision
except that it is now the only place the mapping can live.

Recorded on the E15 `—` row and in the A8 decision text, so the next person reading the sheet against
the Data Model finds the answer rather than the discrepancy.

### 2. `DocumentType.verification_terms` — 3.3's guard reads the type row

3.3 ships the cheap guard for the real ingestion error: right slot, wrong file. Nothing in the plan
said where the guard's knowledge lives, and the default answer — a `Record<TypeKey, string[]>` in
TypeScript — is quietly fatal to A8. A new document type would then be a seed row *and a release*,
because until the release it ships with no guard at all. A8 would be true of the catalogue and false
of the first thing that consumes it.

So the marker terms live on the type row. A type added as a seed row arrives with its own guard.
Carried into 3.3 in both `todo.md` and `roadmap.md`.

The column is nullable: a type with no terms is unguarded rather than unfileable, which is the right
failure direction for a guard whose whole justification is that it is cheap.

### 3. A8 keeps its own number in a sheet numbered D1–D6

The DECISIONS sheet holds workbook-local shaping decisions, D1–D6, cited from the FIELDS sheet as
"SETTLED BY D3", "LOCKED BY D4". A8 is `tasks/plan.md`'s, settled 4 Sep, and it shapes these tables.

Renumbering it to D7 would give one decision two names in two files, which is the drift the whole
citation convention exists to prevent — and the workbook is the file more likely to be read by
someone who has never opened `plan.md`. So the sheet now carries two namespaces, and both the READ ME
sheet and `docs/model/README.md` say which is which: a **D**-number is decided in the workbook, an
**A**-number is a repository architecture decision reproduced here because it shapes these tables.

## The two forced changes to E12

Neither is scope creep; both are consequences of adding the catalogue that 3.1 would otherwise have
had to decide arbitrarily and alone.

**`type_key` (enum of nine) → `document_type_id` (FK → DocumentType).** This is R17. The enum *is*
the thing the catalogue replaces; leaving it would have left the workbook specifying both mechanisms.

**`sha256` → `file_hash`.** [SPEC-flows.md](../../SPEC-flows.md) flow A1, written 6 Sep, already calls
it `file_hash`, and `tasks/todo.md`'s 3.1 entry does too. The workbook said `sha256`. Two
specification files disagreeing on a column name is a defect 3.1 inherits and resolves by coin-flip,
and it costs one word here. `file_hash` is also the better of the two names: it says what the column
is for rather than which algorithm this year uses.

`storage_uri` is the third changed row and only gained a note — the path convention from 3.2, that it
carries the place and never the people.

## Raised here, and where each is owned

Nothing below is unowned ([docs/pipeline.md](../../docs/pipeline.md) §8 step 7). All four are in
`tasks/todo.md` and `tasks/roadmap.md`, inside the entry of the slice that closes them.

1. **The seed is nine document types, not eight — so 3.1's acceptance bar is the *tenth*.** → **3.1**.
   The Data Model names eight; the workbook has carried `inspection_certificate` as a ninth since
   3 Sep because SAFETY assets and the compliance tab need it, and **3.5 needs it this week**. Holding
   back a type the system already requires, so that a demonstration can land on the number nine, is a
   knowingly incomplete seed dressed as a proof. Seed nine; prove the mechanism on a tenth added in a
   test; say which in the evidence.

2. **E12 is narrower than the published Data Model, and a column is either in the first DDL or it
   costs a migration later.** → **3.1**. `docs/data-model.html`'s `Document` carries `state`,
   `superseded_by`, `tenant_visible` and `uploaded_by`; E12 carries none. With 3.4 deferred and the
   type declared rather than detected, figure 5's review-queue states collapse to nearly nothing — but
   supersession is real the moment an addendum lands (flow A3, week 4) and `tenant_visible` is real
   the moment a tenant can see a document (week 9). Deliberately **not** decided here: this pass was
   scoped to the catalogue, and widening it to re-litigate E12 against a published document is a
   different slice's argument. Decided at 3.1, with a reason per column.

3. **4.2's `type_field_id` and `schema_version_id` are one column, not two.** → **4.2**. E16 is
   versioned by `effective_from` on the field row itself, so the row *is* the version and an
   `ExtractedField` pointing at `document_type_field_id` already says which declaration governed it.
   There is no separate schema-version entity for a `schema_version_id` to point at. Two names for one
   fact is a pair that can disagree, and the day they disagree is the day a value stops being
   explicable — which is the entire reason `effective_from` exists.

4. **`value_type` has no MONEY member, and no money field is seeded.** Already owned, so no new owner
   is created: READ ME rule 3 (*no money, not one amount, anywhere in this model*) binds hardest at
   promotion, where no amount is ever a column on a business record; and *no tenant-facing price and
   no balance, ever* is already a standing refusal case in the golden set
   ([pipeline.md](../../docs/pipeline.md) §7). Capture being open means an amount on a page is
   *capturable*; it never becomes business truth and it is never quoted. Stated on the E16
   `value_type` row so nobody adds the member helpfully.

## Also closed in this slice — the demo-day carry, which had already been fixed

This slice edits `docs/model/`, so it inherited week 2's item: *"[pipeline.md](../../docs/pipeline.md)
§7 says the demo kind is declared **Monday**; the cadence and roadmap.md say **Sunday**"*, owed to the
first week-3 slice touching `docs/`.

**The claim is not true of the file, and §7 has never said it.** §7 is the golden set. The line was in
**§8**, and **slice 2.1 corrected it on 2026-09-06** — it now reads that the Cadence's "Monday" means
the first working day of the week, that the working week here is Sun–Thu, and that the day is
therefore Sunday. `tasks/evidence/2.1.md` records the close under "Also closed in this slice".

So week 1 raised it, 2.1 closed it, and weeks 1 and 2 both re-carried it afterwards — from a note,
not from the file. That is the carry rule's own failure mode and it is worth naming: **an item can
outlive its fix.** The rule stops things being forgotten; it does nothing to stop them being carried
after they are done, and the only defence is re-reading the thing an item points at before copying it
forward. It cost two weeks of a line in two documents here, which is cheap — but the same habit
applied to a constraint would mean re-fixing something already fixed, or worse, trusting a description
of the code over the code.

**Nothing is owed in this repository.** What remains literally true is that two *published* documents
say the demo kind is declared on Monday — `rollout-cadence.html` ("Declare the demo type on Monday")
and `platform-brief.html`. 2.1's ruling covers them and no republish was made: the Cadence is the
authority on the schedule and is never renegotiated in the repo, so "Monday" reads as its first
working day, and the correction is a reading recorded rather than a schedule changed. Changing
client-facing wording is a promise to the client and therefore the director's call, not a slice's. It
is flagged, not owned.

## Definition of Done

- `SPEC-<module>.md` — **no edit, deliberately.** `SPEC-evidence.md` is a stub whose content arrives
  in its build week, and it already names E15 and E16 and carries A8 with the `effective_from`
  versioning rule. This slice changed the workbook, which is the specification for the *tables*; the
  module's own contract — what `src/evidence/` exports and what it refuses — is 3.1's, in the same
  change as its code, per the standing rule. Filling the stub now would put a specification in front
  of a decision that has not been made.
- No code changed, and the suite was measured anyway rather than assumed: **347 tests** green
  (306 code + 41 hooks), zero skipped, with the local Postgres up.
  **That is one more than week 2's closing number, and week 2's number was the stale one.** 346 was
  measured at 2.6's own commit (`2f89955`) and is correct there — re-run at that commit today it is
  still 305 + 41. The 347th arrived at `e6c4375`, *"Record slice 2.6's staging verification"*, which
  despite its title also changed `src/estate/internal/views.ts` and added a case to
  `tests/ui/tokens.test.ts` — *"counts days in Hebrew, which does not count in two"*, found on
  staging. Identified by diffing the test **names** between the two commits, not by reasoning about
  the counts. `tasks/evidence/week-2.md` is not edited: evidence files are written once and reopened
  never, and the correct number is recorded here instead. The lesson is small and repeats one already
  in this repo — a commit whose message says *record* can still change code, so a summary number is
  only true of the commit it was taken at.
- The `.xlsx` is regenerated and committed, because it is a build output that is handed over as a
  file rather than built by anything downstream.
- `openpyxl` is **not** installed anywhere in this repo and must not be: a Python package for the
  build output of a document has no business in a Node service's dependency tree. It is run from a
  throwaway virtualenv, and `docs/model/README.md` now says so with the command, because that fact
  cost this slice five minutes of rediscovery.
