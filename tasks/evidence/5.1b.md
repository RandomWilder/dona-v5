# 5.1b — the credential is Google's, and the TOTP machinery goes

**Claimed:** 5.1's admin edge — our password form, our TOTP form, an invite URL, an enrolment screen,
a base32 secret hand-typed because `tests/ui/tokens.test.ts` forbids the JavaScript a QR needs — was
more machinery than the job needs to carry a credential this system had already decided not to own.

**Proved.** One link → Google → our session: authorization-code flow, server-side, no client JS, no
new runtime dependency (`google-auth-library@11.0.2` was already here).

`npm test` · `test:policy` · `guards` (3/3) · `typecheck` · `lint` green; CI's `evals` gate green.

**Red first, committed that way.** Both suites failed to load before the implementation existed
(`does not provide an export named 'OAUTH_COOKIE'`), then eight refusals went green: unknown email ·
`email_verified` false · no role · disabled · a `sub` differing from the one on file · nonce · state ·
no state cookie. One test drives all eight and asserts the bodies are byte identical — a refusal that
says which one it is, is an oracle.

**A real sign-in, not a fake** (§8 step 5). Boot line `identity: google:681282581055-2koouc…`;
`/staff` → 303 → `/staff/login`; `/staff/auth/start` → 303 to `accounts.google.com`,
`scope=openid+email`, `access_type=online`, `prompt=select_account`, `set-cookie: dona_oauth=…;
HttpOnly; SameSite=Lax; Max-Age=600` — no `Secure`, correct over http locally. The director signed in
with their own Google account against a `staff_account` holding one row from `npm run staff:add`, and
landed on `/staff` as ADMIN. After: `idp_local_id` holds the 21-digit Google `sub`; the one
`staff_session` row holds a 64-character sha256 hex, so the bearer value is in the cookie and nowhere
in the database. No screenshot attached — no evidence file here has ever carried an image.

**Two corrections to the re-plan, made before starting.** (1) "Squash `staff_invite` out of `0021_`"
reaches nothing — the ledger is by filename with no checksum (`kernel/migrate.ts:34`) and staging ran
`0021_` at the 5.1 deploy, so the edit would have left staging with `idp_local_id NOT NULL` and the
first sign-in failing on an INSERT. Forward migration `0022_staff_google.sql` instead, dropping
`outbox` and `idempotency_keys` where they still stand: **5.0-cut's opened item, closed without the
schema reset the bash guard refuses.** (2) "25 tables → 24" was 27 → 26.

**Two claims in the approved plan were wrong.** The policy suite was not untouched: one case's
expectation changed, because `staff_invite.token_hash` was one of the two hashes
`tests/policy/staff-session.test.ts` excludes and that table is gone — subject unchanged, count still
50. And `grep -rn "totp\|mfa\|otpauth" src/` returns 2, not 0: both comments recording the change,
one in a frozen migration that must not be edited.
