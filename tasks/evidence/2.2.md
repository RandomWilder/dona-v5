The probe below proves a rejection red by rebuilding the DDL without the constraint. Case 3 was


`actual: undefined` is the whole finding — no error was raised, so the row **was accepted and
stored**. The constraint was restored with the identical definition and `pg_get_constraintdef` was
read back to confirm the schema matches the migration file.

The case asserts three things, and the second and third are why the first is worth having:

1. `role = 'GUARANTOR'` with `is_service_contact = true` is rejected — **23514**.
2. A guarantor is still *representable*: the ערב is on the lease, with a phone number of their own,
   and the isolation join returns **nothing** for that number while the tenant's number returns their
   unit. The constraint is **spent** at the front door rather than merely stored, because a flag
   nothing reads protects nobody.
3. The other three roles may be service contacts. A rule that quietly refused an occupant would be a
   different bug wearing this one's clothes.

`src/tenancy/schema.test.ts` adds the half a module test owns: **an `UPDATE` cannot flip it either.**
That is the difference between a CHECK and a form default — there is no later moment at which it
stops applying, so a co-tenant promoted to guarantor takes the rule with them.

## Two calls made in the DDL, and what decided each

**The overlap constraint is partial on `ACTIVE`.** The workbook's own note on `end_date` is *"Together
with start_date this is the isolation window. No overlap allowed on one unit."* Declared as a
statement about overlap, exactly as 2.1's was:

```sql
CONSTRAINT one_active_tenancy_per_unit EXCLUDE USING gist (
  unit_id WITH =, daterange(start_date, end_date, '[]') WITH &&
) WHERE (status = 'ACTIVE')
```

Blanket would have been wrong, and the case that decides it is ordinary: a `TERMINATED_EARLY` tenancy
keeps its **contractual** `end_date` while `actual_move_out` records reality, so a tenant who leaves
in June on a lease running to December, with the next tenancy starting in August, is correct history
that a blanket constraint rejects. `ACTIVE` is exactly the set the isolation join reads — the
constraint covers exactly the rows that can produce the defect and no others. Asserted in both
directions: the overlap is refused, the history is accepted.

**`terms_profile` exists so that `terms_profile_id` can be NOT NULL.** The workbook makes it a
required foreign key and `TermsProfile` is modelled nowhere, which left two options. The column could
have become nullable — and 2.1's own argument for a nullable `national_id` (*"a required identifier
is one that gets typed as `000000000` within a week"*) is the argument for it. It was rejected here
because the two columns answer different kinds of question: `national_id` is a fact about the world we
may not have, while `terms_profile_id` is what **Q4, the responsibility decision, keys on**. A null
there is not a missing fact, it is a week-6 matrix with no input.

So the table lands with identity and a name, which is E1 `project`'s move at 1.9 — *"it exists so
Shoham can grow into it; fields are added when we know what it must carry."* The cost is real and is
carried, not absorbed: the importer has to say which profile each lease is on, and open question 2 —
how many profiles are in force — is week 5's. **2.4** and **2.5** own it in `tasks/todo.md` and
`tasks/roadmap.md`.

**The natural key `(unit_id, start_date)` moved up from 2.4.** It was already stated as decided in
both planning files, and 1.9 shipping the estate spine keyless is what 1.11 had to measure — the same
fixture applied twice produced two buildings, 368 spaces and 144 units. It covers every status where
the exclusion constraint covers only `ACTIVE`, so a re-run cannot duplicate a draft or an ended lease
either. 2.4 keeps the decision that is genuinely open: `party`'s key, against the real export.

**No index on `end_date`.** Q5 — leases ending in the next 60 days across 1,500 units — is 2.6's
*Done when*, and 2.1's carry already says an index is decided at full row count with a timing in front
of it. `tenancy_unit` and `tenancy_party (party_id)` do exist, the latter because the composite
primary key `(tenancy_id, party_id)` does not serve the isolation join's third hop.

## The pending branch was masking a broken fixture

The most useful thing the slice found, and it is not about tenancy at all.

The first run of the policy suite after the migration failed:

```
error: duplicate key value violates unique constraint "building_address_unique"
detail: 'Key (address_key)=(shoham|rakefet 12) already exists.'
```

`seedUnit` inserted a **new building at the same address** on every call, and 1.11's
`building_address_unique` has rejected that since week 1. It was invisible for five weeks because the
first `seedOccupancy` raised 42P01 on `tenancy` and aborted the transaction before a second building
was ever attempted — so a case that seeds two occupancies never reached its own second seed. The
pending branch was hiding a defect in the fixtures that create the rows the cases assert on.

The fix makes the building shared — `ON CONFLICT (address_key) DO NOTHING`, then read the id back
rather than composing the generated key by hand — which is also the truer model: the neighbour in the
isolation case now lives next door rather than in a second building at the same address.

**This is the argument for `tests/policy/relations.test.ts` in one paragraph.** A branch that
disarms itself is only as good as somebody noticing it has, and five weeks is long enough for a
fixture to rot underneath it.
