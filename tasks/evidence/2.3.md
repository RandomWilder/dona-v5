## The structural call: the view is the shape, the resolver is the rule

`occupancy` carries no temporal predicate, no status filter and no `CURRENT_DATE`. Three things force
that and each is sufficient on its own:

1. **A view cannot take a parameter.** The only way to put `today` inside one is `CURRENT_DATE`,
   which is `SPEC.md`'s clock rule broken — a temporal predicate the tests cannot control is a test
   that fails on a Tuesday.
2. **Guard two scans the migrations directory.** `src/kernel/migrations/` is not `src/scope/`, so a
   view holding the tenancy-active predicate fails the build. Measured rather than assumed — the
   probe is below. The alternative was to add the directory to the guard's exclusion list, and
   `scripts/guards.ts` says why not: an exclusion list that grows is how a guard dies.
3. **It is the truer line.** What guard two protects is not the join's text, it is the decision about
   *when* a contact or a tenancy counts. That decision now has exactly one home, and a question that
   is not about today — the unit screen's tenancy history, Panel 6 — reads the same view without a
   second one being written.

The consequence is deliberate: **anything wanting occupancy asks `src/scope/` for it.** A screen
reading the view directly would have to write the day predicate, which puts it in a second file and
fails the guard. Slice 2.6's occupancy chip calls `resolvePartiesInUnit`.

## The finding: the view very nearly defanged guard two, and the guard's own test caught it

Written first with the columns aliased — `tenancy_start`, `tenancy_end`, `tenancy_status`,
`contact_valid_from`, `contact_valid_to` — which reads better and is what a view of two tables
naturally does. Guard two's patterns are written against `start_date`/`end_date` and
`valid_from`/`valid_to`, so with the aliases in place **the canonical join in `src/scope/` matched
neither pattern.** The guard was still green, and it would have stayed green over every later copy of
the join anybody made.

It was caught mechanically, and by the one test that could catch it:
`tests/policy/guards.test.ts` builds its violating fixture out of `ISOLATION_JOIN_SQL` itself rather
than out of hand-written SQL — a decision made at 1.7 for a different reason.

```
✖ trips on a second copy of the real join anywhere else
✖ trips on a reformatted copy — the predicate, not the layout
✖ still trips when valid_to is compared to anything else
ℹ tests 19 · pass 16 · fail 3
```

The fix is not a wider guard. The view keeps the base tables' column names for those four columns,
which costs nothing — `tenancy` and `party_contact` name disjoint columns — and the reason is
written in the migration and beside the predicates, because the next person to alias them will be
doing it for the same good reason.

## Probe 1 — the resolver reads the view, and not the base tables

A join that had quietly kept reading `party_contact JOIN party JOIN …` would pass every test in the
repository. So the view was renamed out from under it:

```
ALTER VIEW occupancy RENAME TO occupancy_probe;
```

```
✔ resolves a current tenant to their own unit, and to no other
  ℹ pending — relation "occupancy" does not exist yet
✔ drops a contact whose validity has closed — temporal predicate one
  ℹ pending — relation "occupancy" does not exist yet
…
✖ has every relation its cases declare
  AssertionError: still pending on: occupancy — the cases that touch these are reporting a
  diagnostic, not asserting
```

Both halves of 2.2's mechanism working at once: the cases fall back to pending on the *view*, which
is what proves the read goes through it, and `relations.test.ts` turns that pending into a build
failure rather than a diagnostic somebody has to read.

## Probe 1 also found a defect, and it was not in the view

On the first run of that probe the cases did not report pending. They failed with this:

```
error: current transaction is aborted, commands ignored until end of transaction block
    at async Object.write (src/kernel/audit.ts:40:5)
```

The audit line was written in a `finally`, which is the reflex. The read raised `42P01`, the
transaction was poisoned, the audit `INSERT` then failed with `25P02` — **and that was the error the
caller saw.** An audit line that can replace the error it was meant to describe is worse than an
absent one: it would have turned every pending policy case in weeks 5 and 6 into an unrelated
failure, and the pending machinery 2.2 built would have silently stopped working.

The line is now written after the read succeeds. A read that raised returned no tenant data, so
there is no access to record; a read that legitimately resolved nobody is `matched: 0` and **is**
logged, which is the case an access review actually asks about.

## Probe 2 — the audit line, red first, both ways

Removing the write:

```
✖ writes one line naming the party reached and the row count
✖ logs the read that resolved nobody, which is the one worth having
✖ logs Q1 too — a unit screen is a scoped read of tenant data
✖ carries neither the number that was asked nor the name that was found
ℹ tests 10 · pass 6 · fail 4
```

And putting the number in the line, which is what anyone writing this by reflex would do:

```
✖ carries neither the number that was asked nor the name that was found
  AssertionError: the audit line leaks +972521234567: (01a0765b-…,system,,,scope.resolve_by_phone,
  01a0765b-…,"{""phone"": ""+972521234567"", ""matched"": 1}",ok,,)
```

Worth reading closely: the number reached the log **normalised**, `+972521234567`, when the caller
had asked with `052-123-4567`. Converting at the edge and then logging the input means logging the
canonical value — the one that joins to everything else in the system.

`SPEC.md` requires every scoped read to be logged *and* PII never to be in logs, and the two are
only reconcilable one way. An Israeli mobile number carries around seven digits of entropy, so a
bare hash of one is reversible by anybody willing to run a loop, and an HMAC needs a secret this
module would have to own and rotate. **So the line records what was reached and never what was
asked**: actor, action, the resolved `party_id` as subject, and the row count. The number that was
asked is not lost — it belongs to the channel module's message log, where an inbound message
legitimately lives with its sender, and it arrives at week 9. Carried below.

## Probe 3 — E.164 at the edge is load-bearing, not decorative

`normalisePhone` removed from the resolver, everything else unchanged:

```
✖ resolves a national number against the E.164 row it belongs to
  AssertionError: 052-123-4567
✖ refuses a number it cannot place rather than resolving to nobody
  AssertionError: Missing expected rejection (KernelError).
```

This is the failure the workbook warns about and the reason it is tested harder than its size
suggests: a number stored as `+972521234567` and asked for as `052-123-4567` resolves to nobody, and
**a scope of nothing is exactly what correct isolation looks like.** Nothing on any screen is wrong.
2.1's `phone_is_e164` CHECK is the storage half and this is the conversion half; `phone.test.ts`
asserts the two are validated against the same expression, by reading it out of `0006_parties.sql`,
so they cannot drift apart quietly.

One decision inside it: a bare `521234567` is **refused**, not assumed Israeli. Nine digits pass
E.164's shape as `+521234567`, which is a Mexican subscriber, and a register row silently becoming a
different country's number is worse than a row rejected with its line number — which is what 2.4's
importer will do with it. `+9720521234567` is refused for the same reason: it is the most common way
a phone column is wrongly internationalised, it satisfies the shape, and it matches nothing ever.

## A second defect the tests found: the audit assertion was reading the whole table

`src/scope/scope.test.ts` first cleared `audit_log` at the top of its transaction so that "exactly
one line" would be a claim about this read. `src/kernel/audit.test.ts` writes its rows on a **pool**,
not in a transaction, so they are committed and concurrent with this suite — which made the clear a
table-wide lock held for the length of the transaction, and made the assertion a claim about the
container rather than about the read. It surfaced as an eight-case failure in one full run and green
in the next.

Every case now names its own actor and reads back `WHERE actor_id = $1`. Race-free, lock-free, and
the default-actor path is covered by the one case that filters on its own freshly-generated
`party_id` instead.

## Q1 and Q2, one query each

The workbook's ADMIN VIEWS sheet ends with a test: *if the model is right, these are all one query
each.* Two of the seven are this module's, and they are the same spine read from opposite ends.

- **Q1** — `resolvePartiesInUnit`. `DISTINCT`, because the view fans a party out over their contact
  rows and this question is about people. It deliberately does **not** filter `is_service_contact`:
  the unit screen shows a guarantor as a guarantor, greyed and marked unreachable (Panel 1), where Q2
  must not resolve one at all. Two questions, one view, opposite readings of one column — and both
  readings are asserted.
- **Q2** — `resolveUnitsByPhone`. The isolation join. Unchanged in behaviour, which is what the
  thirty unedited policy cases say.

The contact hop is a `LEFT JOIN` so a tenant whose number we do not have still appears on the unit
screen. An inner join would drop them, which is a filing failure disguised as an empty panel; Q2
supplies a channel and a value, so the null rows fall away on their own and isolation is unaffected.

**`national_id` is not a column of the view**, and its absence is asserted against
`information_schema.columns` rather than intended. The whole column list is compared to
`OCCUPANCY_VIEW_COLUMNS`, so a column added to the view without being considered fails here instead
of arriving in a response shape unnoticed.

## Carried out of this slice

- **2.4 — the importer normalises before it inserts.** A register formatted for a spreadsheet is
  rejected row by row by `phone_is_e164` otherwise. `normalisePhone` is on the scope contract for
  exactly this caller.
- **2.6 — the occupancy chip calls `src/scope/`.** Reading `occupancy` from `src/estate/` means
  writing the day predicate there, which is a second copy and fails guard two.
- **Week 9 — the channel module logs the inbound number.** The scope audit line deliberately does
  not carry it, and an inbound message is where it legitimately belongs.
- **The view's dated columns keep the base tables' names.** Recorded in the migration and beside the
  predicates, because the next person to alias them will have the same good reason this slice did.
