> **Done when:** `rm -rf /`, force push, raw `psql` against prod and `DROP DATABASE` are each blocked

## What was proved

### Red first, then green

`.claude/hooks/hooks.test.mjs` was written **before any hook existed** and run against the empty
directory. The hooks are tested the way Claude Code actually calls them — spawned as a process, fed
the tool payload as JSON on stdin, judged on exit code and stderr — because asserting the regexes
directly would prove the regexes match, not that the guard blocks.

```
$ node --test --test-reporter=tap .claude/hooks/hooks.test.mjs     # before the hooks existed
# tests 29
# pass 0
# fail 29

$ node --test --test-reporter=tap .claude/hooks/hooks.test.mjs     # after
# tests 32
# pass 32
# fail 0
```

The three extra cases are the ones the implementation itself produced: two defects in the lifted v3
code and one whole class of behaviour v3 never had (below).

### The four blocks, live through the Bash tool

Not simulated. The hook loaded in this session, and these are its verbatim refusals. Each payload was
prefixed with `echo` **on purpose**: the guard matches the command string, so an `echo`-neutered
payload exercises the identical code path while being inert if the hook had *not* been loaded. A
verification that destroys the machine when it fails is not a verification.

```
$ echo rm -rf /
PreToolUse:Bash hook error: Blocked by guard-bash hook: rm -rf on filesystem root.
  Run it manually if truly intended.

$ echo git push --force origin main
PreToolUse:Bash hook error: Blocked by guard-bash hook: force push (use --force-with-lease
  deliberately, outside hooks). Run it manually if truly intended.

$ echo psql "$DATABASE_URL_PROD" -c 'select 1'
PreToolUse:Bash hook error: Blocked by guard-bash hook: raw psql against a prod database.
  Run it manually if truly intended.

$ echo 'DROP DATABASE dona'
PreToolUse:Bash hook error: Blocked by guard-bash hook: DROP DATABASE/SCHEMA.
  Run it manually if truly intended.

$ echo gcloud sql instances delete dona-v5-prod            # the fifth, not in the slice's bar
PreToolUse:Bash hook error: Blocked by guard-bash hook: destructive gcloud command.
  Run it manually if truly intended.
```

Exit 2 is the only code Claude Code reads as *blocked*; 1 is an error the model is shown and may
route around. The suite asserts the code, not just the message.

## Three defects in the lift, found by verifying rather than by reading

`docs/from-v3.md` files these hooks under Tier 1, "take verbatim". **Two of the three would have been
silently broken in v5, and one of them was already silently broken in v3.** This is the slice's most
useful output.

**1. `node --test src/<module>` does not discover tests under Node 24.** A positional argument is a
file or a glob, not a directory to walk:

```
$ node --test src/estate
Error: Cannot find module '.../src/estate'   [MODULE_NOT_FOUND]     exit 1
```

v3's hook read that non-zero exit as "the module's tests failed" and would have printed
`Focused tests failing in src/estate` after **every single edit**, whatever the tests actually did. A
guardrail that fires constantly is a guardrail you learn to scroll past. v5 collects the test files
with `fs.globSync` and runs them explicitly, which also makes *"this module has no tests yet"* — the
ordinary state of a module in week 1 — a silent no-op instead of an error.

**2. A `PostToolUse` hook that exits 0 has its stderr hidden from the agent.** v3's `after-write.mjs`
wrote its failing-test report to `console.error` and then `process.exit(0)`. **Nothing ever read it.**
The feedback loop the file's own header describes — "feedback in seconds, not at push time" — did not
exist. Exit 2 is the code that puts stderr in front of the model; it does not undo the write, because
`PostToolUse` fires after the tool has already run. This is the change that gives the slice its title,
and it is why the second half of the bar is demonstrated with a transcript paste rather than a claim.

**3. `rm -rf /*` was not matched.** v3's `\/(\s|$)` requires the slash to end the argument, so the
canonical `rm -rf /` was blocked and the equally terminal `rm -rf /*` was not. The pattern now also
accepts `*` and `--no-preserve-root`.

## What the guard deliberately does not do

Pinned as passing tests under *accepted false positives*, so the next person meets them as a recorded
decision rather than as a surprise at 2am:

| Command | Why it is blocked anyway |
|---|---|
| `grep -rn "DROP DATABASE" migrations/` | The guard matches the string, not the intent |
| `git push --force-with-lease origin <branch>` | `--force` is a prefix of it; the safe form goes with the unsafe one |
| `psql -h 127.0.0.1 dona_dev -f seed-production-catalogue.sql` | "prod" anywhere on the line |

The trade is deliberate and asymmetric: a false positive costs one rephrase, a false negative costs a
database.

**Known gaps, stated rather than discovered.** `git push origin +main` is a force push by refspec and
is not caught. `rm --force -r /` spells the flags in a way the pattern misses. And the whole class is
bypassable by construction — the guard sees one command string, so `bash -c`, a shell script, a
base64 payload or a here-doc all walk past it. **This is a net against accidents and momentum, not
against an adversary**, and no line in `SPEC.md` should ever be defended by it alone. The constraints
that must hold against intent live in `tests/policy/` (1.7) and in database constraints.

## The allowlist

`.claude/settings.json` is now tracked (`.gitignore` excludes only `settings.local.json`). Seventeen
routine commands are allowlisted so flow is uninterrupted — tests, both gates, `measure`, typecheck,
lint, format, `node --test`, `npx biome`, `git status`/`diff`/`log`/`add`, `db:up`, docker compose
up/ps/logs. **Eight of them are `npm run` scripts and there is no `package.json` yet** — none of them
exist until 1.3, 1.7 and 1.8. An allowlist entry for a missing script is inert, and writing them now
means the toolchain slice does not have to remember to.

Deliberately **not** allowlisted, and each stays behind a prompt: `git commit`, `git push`, `gh api`
and `gh pr` (they write), anything `gcloud`, and the deploy and rollback scripts. Pipeline §4: the
routine is allowlisted, deploys and destructive commands are not.

## Raised, not silently handled

1. **The hooks' tests are not in any suite yet.** They run with
   `node --test .claude/hooks/hooks.test.mjs` and nothing else runs them. **Slice 1.3 owes it:** the
   `npm test` script must include `.claude/hooks/`, or these 32 cases rot the first time a Node
   release changes the test runner's argument handling — which is exactly the defect that produced
   finding 1 above.
2. **`AGENTS.md` is now 40 lines against pipeline §3's "20–30 lines MAX".** It was already 38 at 1.1
   and this slice added two. The pipeline's reason for the cap is real (duplicated context measurably
   degrades agent performance), so this is over budget, not merely over a number. Raised for a
   deliberate trim rather than trimmed inside a slice about hooks.
3. **A hook is only as loaded as the session that loaded it.** `.claude/settings.json` is new, so the
   next session prompts for approval before these hooks run, and a session that declines them has no
   guardrails at all while looking identical. Nothing in the repo detects that state.
4. **The guard covers the Bash tool only.** Write, Edit and every MCP tool reach the filesystem
   without passing it. The `-- pii` and corpus rules in `SPEC.md` are enforced by `.gitignore` and by
   review, not by this hook, and slice 1.12 should not assume otherwise.

## Raised and settled

- **A harness artefact, not a hook defect.** The first green run was a lie: `NODE_TEST_CONTEXT=child-v8`
  is inherited from the test runner into the spawned hook and on into the hook's own `node --test`
  grandchild, which then reported over *this* runner's IPC channel and exited 0 — so a failing module
  test looked green to the hook. The child environment is scrubbed in the test helper, with the reason
  written beside it. Claude Code never spawns a hook from inside a test runner, so the hook itself
  needs no defence; the suite that tests it does.
- **No `SPEC-<module>.md` was touched.** This slice changes no module behaviour. The Definition of
  Done's spec-before-code bullet is not applicable rather than skipped.
- **Most of the standing Definition of Done cannot be run yet, by sequence and not by omission:**
  `typecheck` / `lint` / `npm test` land in 1.3, `tests/policy/` in 1.7, `npm run evals` in 1.8, and
  staging plus `infra/smoke.sh` in 1.6. What was available — red-first proof, the diff read, an
  evidence file, no new runtime dependency — was done.
