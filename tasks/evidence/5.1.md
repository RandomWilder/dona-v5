## The acceptance bar, line by line

**Done when: a named operator signs in with a second factor and holds a session.**
`src/staff/routes.test.ts` — *invites an operator, enrols a second factor, and signs them in* —
drives the whole path through `app.inject` with the same `application/x-www-form-urlencoded` bodies
the HTML forms post: invite → set password → TOTP enrolment → password step → second-factor step →
`Set-Cookie` → `/staff` renders the role. The password step alone returns **no cookie**, which is
the half that matters.

**Done when: an account with no role is refused with `not_allowed` and no other detail.**
*answers every role-less shape with the same bytes* signs in three accounts — one the provider knows
and this system does not, one whose `role` is null, one that is disabled — and asserts
`unknown.body === roleless.body === disabled.body`, 403 on all three, `Set-Cookie` on none, and zero
session rows written. A refusal that distinguished them would be an account-enumeration oracle on
the login screen of a system holding 1,500 households.

**Verify: a role-less account is refused on every route with the same message.**
*refuses a role-less holder of a live session on every guarded route, with one message* mints a
session for an `ADMIN`, confirms `/staff` answers 200, sets `role = NULL`, and then asserts `GET
/staff` and `POST /staff/invites` both return exactly `{"code":"not_allowed","message":"not_allowed"}`
— and that the two bodies are identical to each other. A withdrawal takes effect on the next
request, not the next sign-in, which is why `resolveSession` joins the account rather than trusting
mint time.

**Done when: no token value exists anywhere in the database.** Two suites, from two directions.
`src/staff/sessions.test.ts` — *stores a hash and never the token* — mints a session and asserts the
cookie value appears in **no column of the row**, iterating every column rather than checking
`token_hash` alone, because the narrower assertion would pass a later migration that added a
convenience copy somewhere else. It then asserts `token_hash === sha256(cookie)` and that presenting
the hash as a cookie resolves to nothing. `tests/policy/staff-session.test.ts` is the other
direction and is the standing rule.

**Verify: sign in on staging with MFA *enforced*, not offered.** **Performed against the live
Identity Platform on `dona-v5`.** See the next two sections.

## The policy case, red before green

`tests/policy/staff-session.test.ts` — **no column in this database whose name contains `token` may
be anything but a `_hash`.** Written before `0021_staff.sql` existed, and proved red twice.

**Red once against a schema with the constraint missing.** `0021_staff.sql` was applied with
`token_hash` renamed to `token` throughout, deliberately, and the case failed on all three
assertions:

```
✖ finds none in the schema this application deploys
  AssertionError: a column holds a token in plaintext: staff_invite.token, staff_session.token
  actual: [ { table_name: 'staff_invite', column_name: 'token' },
            { table_name: 'staff_session', column_name: 'token' } ]
  expected: []
✖ accepts the hashes the mechanism does keep
  actual: []   expected: [ 'staff_invite', 'staff_session' ]
ℹ pass 0   ℹ fail 3
```

The migration was then written correctly, the tables dropped and re-applied, and the same three
cases went green — `ℹ pass 3  ℹ fail 0`.

**And red permanently inside the case, which is the part that survives.** A case that only asserts
*the real schema is clean* is green the day it is written and green again the day somebody removes
the constraint. So the case builds its own violation, the way `tests/policy/guards.test.ts` does: a
real `CREATE TABLE session_token_fixture (token text)` inside a transaction that is rolled back,
asserted to be caught — and a second fixture named `session_token`, asserted to be caught too, so
the suffix is the only way past the check and a column cannot rename itself around it. The fixture
is created in `public` deliberately: a `TEMP` table lands in `pg_temp_N` and would slip past a check
scoped to the schema the application actually deploys into, which would make that half a
decoration.

## Decisions this slice made, and why

**1. Identity Platform holds the credential and the second factor; the session is ours.** Settled by
Stack Map §3.1 and `docs/from-v3.md` Tier 2 gap 1, not reopened. There is no password hash and no
TOTP secret in this schema. The session is minted here rather than the ID token being handed to the
browser, because an ID token is an hour of authority this application cannot revoke: an operator
dismissed at 09:00 would hold it until 10:00.

**2. The second factor is TOTP, and that is a consequence of a rule rather than a preference.**
Identity Platform's SMS second factor requires a reCAPTCHA token minted in the browser by Google's
JavaScript SDK. `SPEC.md` says the UI is self-contained HTML plus `/ui/tokens.css` and nothing else,
and `tests/ui/tokens.test.ts` fails the build on a `<script>` in any screen. SMS would therefore
have bought this system its first client-side dependency **on the screens that guard everything
else**. TOTP's REST endpoints need no reCAPTCHA, so sign-in, the second factor and enrolment are all
plain server-rendered forms — and it costs nothing per sign-in, where SMS costs a message. The trade
taken with open eyes: TOTP is a genuine second factor and is not phishing-resistant. Open question
12 (is Dona Dom on Google Workspace?) would move the second factor to Google's own at no cost, and
reopens this.

**3. "Enforced, not offered" is claimed twice, and only one of the two has a test.**
`infra/bootstrap.sh` sets `mfa.state = MANDATORY` with the TOTP provider and
`client.permissions.disabledUserSignup` — and reads it back, for the reason below. And `src/staff/` refuses any ID token with no
`firebase.sign_in_second_factor` claim — a password sign-in that returns a token directly means the
account has no second factor, and `refuses an account with no second factor, however good its
password is` asserts 403, no cookie, and zero session rows. A `PATCH` in a shell script no test runs
is a configuration this repository cannot assert; the refusal is the claim.

**4. The ID token's signature is not verified, deliberately.** A signature check answers *did Google
mint this?*, and it is indispensable wherever a token arrives from a client. This one never does: it
is a field in the JSON body of an outbound HTTPS call this process made, read once and discarded in
the same request, and no browser ever holds it. TLS already answers who sent it. The `aud` check is
kept anyway, because it is free and catches the one thing TLS does not — an API key pointed at the
wrong project — and `refuses a token minted for another project` asserts it.

**5. No pepper on the session hash.** A pepper defends a secret whose preimage space can be
searched. The token is 32 bytes of CSPRNG output, so an attacker holding the hash has nothing to
search; a pepper would buy a secret to rotate, a rotation path to own, and a way to lock every
operator out of a running system, in exchange for nothing. Recorded in `SPEC-staff.md` so it is a
decision and not an omission.

**6. The invite is a printed one-time URL and never an email.** This system has no mail transport,
and acquiring one is an external dependency with its own DPA, its own deliverability problem and its
own ADR-0004 naming — not something a slice about sessions adds quietly. **Carried to week 8**, the
week the console has to be usable on its own with Dona Dom's staff on it.

**7. The role lands only when the second factor is enrolled.** The `staff_account` row is created
with `role` null when the password is set, and receives its role when `mfaEnrollment:finalize`
succeeds. That is decision 3 read from the other end: an account that never enrolled never acquires
a role, so the refusal path and the enrolment path cannot disagree. The test asserts `role IS NULL`
between the two steps and `role = 'ADMIN'` after.

**8. `bootstrap.sh` creates one API key and no operator.** Slice 1.5 wrote that a generated
credential nothing reads and no rotation flow owns is worse than an absent one, and refused to seed
v3's four staff secrets. This slice discharges that comment without contradicting it: the first
operator comes from `npm run staff:invite <email> <role>`, run by a human who can already reach the
database, and the invite expires on its own if nobody uses it. The key is created and read in one
pipeline into Secret Manager — never an argv, never a file, never a log (ADR-0003) — and is
restricted to `identitytoolkit.googleapis.com`, so a leak is a key that can call one API.

## One structural move that was not in the plan

**The urlencoded form parser moved from `src/estate/` to `src/kernel/ui/forms.ts`.** Estate has
registered it at root scope since 2.6, and registering a second one in an encapsulated staff scope
threw `FST_ERR_CTP_ALREADY_PRESENT` — which is Fastify saying out loud what a copy would have said
quietly. This is the same move the page shell made at 3.3 and for the same reason: a copied parser
is a copy that drifts, one of them starts trimming and the other does not, and two screens end up
disagreeing about what an empty field means. It costs no dependency, because `URLSearchParams` is in
the standard library — unlike the multipart body at 3.3, which genuinely needed one.

`--size-form-max: 28rem` was added to `src/kernel/ui/tokens.css` in the same spirit: the staff
screens are the first pages in this system that are one narrow card rather than a portfolio, and a
measure typed into a view is how a design system stops being one.

## Provisioning, and the silent failure it hid

`./infra/bootstrap.sh staging` now enables `identitytoolkit.googleapis.com` and
`apikeys.googleapis.com`, initialises Identity Platform, configures MFA, and creates a restricted
API key into `staging-identity-api-key` with `secretAccessor` bound per secret to `app-staging`.

**The first run printed nothing but success and left MFA `DISABLED`.** The state name is
`MANDATORY`, not `ENFORCED`; the provider answered `400 INVALID_ARGUMENT`; `curl` exited 0 because
an HTTP error is not a transport error; and the block sent its output to `/dev/null`. Reading the
config back is what caught it:

```
mfa      : { "state": "DISABLED" }
client   : {}
signIn.email: null
```

That is **slice 1.2's lesson in a different costume** — a step that cannot fail the run is
decoration, exactly as a `PostToolUse` hook that exits 0 is. The block now uses
`curl --fail-with-body` **and reads the config back and exits 1 if it did not take**, because the
application half of "enforced, not offered" has a test behind it and this half has only that line,
so that line has to be an assertion rather than a hope. Proved by putting `ENFORCED` back and
re-running: the script stops on `curl: (22) The requested URL returned error: 400` and never reaches
the service-account section. Restored and re-run idempotently:

```
▸ Identity Platform — enforced MFA, TOTP, no public sign-up
  mfa: MANDATORY (TOTP) · public sign-up: disabled
  staging-identity-api-key already exists — leaving the key untouched
```

Read back from the provider afterwards:

```
mfa      : {"state": "MANDATORY", "providerConfigs": [{"totpProviderConfig": {"adjacentIntervals": 1}, "state": "ENABLED"}]}
client   : {"disabledUserSignup": true}
signIn.email: {"enabled": true, "passwordRequired": true}
```

## Proved against Google, not against the fake

The port makes the whole flow testable with no network, which is right — and it is also exactly the
kind of seam that hides a provider's real requirements. So the flow was run once against the live
Identity Platform on `dona-v5`, with a synthetic operator and a TOTP code computed from the shared
secret (RFC 6238, the same arithmetic an authenticator app does):

```
1. account created through the admin endpoint: TxfX1KIn7CQ4UhLsU7d6Kph7nwZ2
2. before enrolment, the password step returns: signed_in, secondFactor=null
   -> src/staff/ refuses exactly this shape. "Enforced, not offered".
3. TOTP enrolment started, shared secret length 32 (base32, provider-encoded)
4. enrolment finalised with a computed code
   (waited 19s for the next TOTP window -- codes are single-use)
5. after enrolment, the same password returns: mfa_required
6. second factor accepted: localId=TxfX1KIn7CQ4UhLsU7d6Kph7nwZ2 secondFactor=totp
7. a wrong code is refused: true

PASS — MFA is enforced by the provider and the token names the factor.
8. fixture account deleted: true
```

**Line 5 is the acceptance line.** The same password that signed in at step 2 cannot sign in at step
5: once a second factor is enrolled, the provider will not mint a token for a password alone. And
line 2 is the case our own code exists for — a token with `secondFactor=null` is what an
unenrolled account produces, and `src/staff/` refuses it whatever the provider's configuration says.

**Two defects the fake could never have surfaced, both now pinned as tests:**

1. **The admin account-creation endpoint needs `x-goog-user-project`.** Under user ADC the bare call
   answers `403 — requires a quota project, which is not set by default`. A Cloud Run service
   account would not have shown it, so without the header this would have been found by whoever
   first ran the invite flow on a laptop, which is the worst place to find it.
2. **`mfaEnrollment:finalize` requires a `displayName`** — `400 MISSING_DISPLAY_NAME`. It names the
   *factor*, not the person, so it is the constant `TOTP_FACTOR_NAME`: this system offers one kind
   of second factor and never asks an operator to name it.

`src/staff/identity.test.ts` now asserts both against the recorded request, under a comment saying
where they came from. The Identity Platform tenant was left with **zero accounts** — every fixture
created during verification was deleted, and `accounts:query` confirms `recordsCount: 0`.

## What is not closed

**The sign-in performed on the staging *URL*, by the director, as themselves.** The mechanism is
proved end to end against the real provider, and the routes are proved end to end in
`src/staff/routes.test.ts` — what has not happened is a human opening
`https://dona-staging-r44j24yuaa-zf.a.run.app/staff/login` and signing in as a named operator,
because **creating a person's account and typing their password is theirs to do and not this
agent's**. What remains, once this merges and staging deploys itself:

1. Confirm the boot line reads `identity: identity-platform:dona-v5` and not `unconfigured`.
2. `STAFF_BASE_URL=https://dona-staging-… npm run staff:invite -- <your address> ADMIN`, against the
   staging database.
3. Open the printed URL, set a password, add the printed secret to an authenticator app, confirm
   with the first code — and then sign in.

Everything that decides whether step 3 works has been executed once already, against the same
provider, on the same project.

## Carried out of this slice, each with the entry that closes it

Written into `tasks/todo.md` **and** `tasks/roadmap.md`, inside the slice that closes each — never
only here (`docs/pipeline.md` §8, and the reason: an evidence file is written once and reopened
never).

- **The CSRF token's scope is every write route, the six staff POSTs included → 5.2.** 5.1 built no
  half of a token on purpose; `SameSite=Lax` on the session cookie is what stands in for one until
  then, and it is stated as the defence it is rather than left to look like protection.
- **The guard is `requireStaff` from `src/staff/contract.ts`, called once per route → 5.2.** Never
  re-implemented — the rule the `SCREENS` registry carries, for the same reason.
- **`party.national_id.read` exists in the matrix with no reader → 5.3.** The admin-only half of
  `SPEC.md`'s security default given a vocabulary before the unreachable half is enforced. A
  permission still unread when 5.3 closes is a permission to delete.
- **The settings screen never grows a card for the role matrix → 5.8.** Two catalogues, and who may
  do what stays code.
- **Staging and prod share one Identity Platform tenant → week 12.** They share one GCP project, so
  a staging operator is a prod operator. Prod answers 503 by design until then, so this is a known
  window and not an open one; it is decided once, beside the prod restart and the F7 organisation
  move, as either a tenant per environment or a second project. `release.yml` mounts no
  `prod-identity-api-key` today and gains one in the same pass.
- **An invite is a printed URL because there is no mail transport → week 8**, and it is an ADR-0004
  naming before it is an integration.
