## The order is the point

`tasks/plan.md` **R4** says the controls are built before the data lands. A slice that landed both
would have satisfied its own acceptance bar and proved nothing about the order, so **tier 2 did not
land here.** The bucket exists, its lifecycle rule exists, the deletion path has been run in anger,
and the corpus itself is still the director's to accept — after **F6**'s other half, which is a DPA
with each processor and disclosure to data subjects, and which no engineering change can produce.

## Tier 1, and the correction it forced

`SPEC.md` and `plan.md` A7 both said the specimen corpus was **the published documents**, committed.
What is committed is Hebrew text **authored to those forms' structure** — clause numbering, headings,
legal register — with each file naming the form it follows and where that form is published. Both
documents were corrected in this slice rather than left disagreeing with the repository.

Two reasons, and the second decided it:

1. **The gate needs text it can chunk, embed and rank.** The path that turns a PDF into text is week
   3's ingestion work. A PDF committed today would sit in the repository being unusable by the one
   thing tier 1 exists for.
2. **Republishing a third party's document wholesale is a licensing decision**, and it belongs to the
   director rather than to an engineer.

A7's actual worry — *no gate is ever green because it was measured against a document we authored to
pass it* — binds at the **week-4 accuracy number**, and A7 itself already assigns that to tier 2:
real documents measure accuracy, they do not do development. The published PDFs are carried to
**3.4**, where F4 and an ingestion path exist, and they land **beside** the authored text rather than
over it: swapping the substrate under a ranking ratchet silently re-baselines it.

Six files, 71 clauses:

```
lease-standard.md          חוזה שכירות אחיד — דירה להשכיר      30   lease
handover-protocol.md       פרוטוקול מסירה                       9   lease
bank-guarantee.md          ערבות בנקאית אוטונומית               7   lease
arnona-bill.md             הודעת חיוב ארנונה                    7   lease
insurance-certificate.md   אישור קיום ביטוחים                   7   lease
service-policy.md          the operator's own — follows none   11   policy
```

**Two properties stopped being comments.** The old fixture's header claimed no sum of money anywhere
and no real person; `evals/fixtures/specimen-clauses.test.ts` now asserts both over the raw files —
the raw files and not the parsed clauses, because a phone number in front matter would never be
indexed and would still be in the repository. Proved red before they passed, by appending one clause
that violates both:

```
✖ holds no sum of money anywhere
  docs/corpus/arnona-bill.md: … 1,250 ש"ח … שמספרו 039456712 בטלפון 0521234567 …
✖ holds nothing shaped like a person
  docs/corpus/arnona-bill.md contains a long run of digits: 039456712
```

**The fixture stopped being a parallel invention.** `evals/fixtures/specimen-clauses.ts` held the
nine passages and a header saying 1.12 would swap them in. It is now a loader over `docs/corpus/`,
so the corpus and the golden set cannot hold two copies of a clause and drift; a clause renamed in a
specimen breaks the import, at parse, in `npm test` — not the gate at 2am. It also refuses a
duplicate ref across the corpus and refuses a `specimenRefs` entry naming a clause nobody wrote.

## Tier 2 — the controls, and the deletion that failed on purpose

`gs://dona-v5-corpus-2026-09-06`, created by `infra/corpus-bucket.sh`. It is the **opposite shape**
to `gs://dona-v5-<env>-docs`, and that is the decision rather than an oversight: the docs bucket is
versioned so an overwrite of a signed contract is recoverable, and this one must not be, because a
corpus with a removal date whose objects survive deletion has no removal date.

```
name               dona-v5-corpus-2026-09-06
location           ME-WEST1
uniform access     True
public prevention  enforced
versioning         False
soft delete        {'retentionDurationSeconds': '0'}
lifecycle          {"rule":[{"action":{"type":"Delete"},"condition":{"age":90}}]}
IAM                no service account granted anything on it
```

No service account is bound at all. The application never reads this bucket, which is stronger than
binding a role per bucket and is why nothing in `src/` knows the name.

**Access logging.** `storage.googleapis.com` `DATA_READ` + `DATA_WRITE` on the project's audit
config, applied read-modify-write by the same script:

```json
[{"service":"storage.googleapis.com",
  "auditLogConfigs":[{"logType":"DATA_READ"},{"logType":"DATA_WRITE"}]}]
```

This is the access logging the slice can honestly deliver. The **application-level** line over every
scoped read is `SPEC-scope.md`'s and slice **2.3**'s, and it cannot be honest before `party` exists —
a scoped read returns nothing to log until 2.2. Re-confirmed in 2.3's roadmap entry rather than left
in this file. Cost: data-access log volume is billed past the free tier, small at this project's
size, named here rather than found on a bill.

**Idempotent, proved by diff and not by assertion.** The second run creates nothing, and the audit
config is written back only when it would change something — a `set-iam-policy` that rewrites an
identical policy still bumps the etag and still writes an admin audit entry:

```
  storage audit config: already present
etag before: BwZayk9lWrU=
etag after : BwZayk9lWrU=
UNCHANGED — the re-run wrote no policy
```

### The deletion path, proved both ways

The red half is the useful one. A second bucket, `dona-v5-corpus-softdelete-probe`, was created with
**Cloud Storage's defaults** — which include a seven-day soft-delete window:

```
soft delete policy: effectiveTime=…;retentionDurationSeconds=604800
```

A throwaway object was uploaded and the deletion path run against it:

```
▸ Deleting gs://dona-v5-corpus-softdelete-probe/throwaway-1.12.txt
▸ Verifying
  STILL RECOVERABLE (soft-deleted, not deleted):
gs://dona-v5-corpus-softdelete-probe/throwaway-1.12.txt#1788674861670766
  fix the bucket first: ./infra/corpus-bucket.sh
✖ … was NOT permanently removed
exit=1
```

**The object was gone from `gcloud storage ls`.** Every listing a person would look at said it had
been deleted, and Cloud Storage would have restored it on request for a week. That is the failure
this slice's acceptance bar is one sentence away from — "permanently removed by a documented command"
— and it is on by default.

Then the same script that provisions the real bucket was pointed at the probe, which set its window
to zero and purged what it held, and the deletion path was run again:

```
▸ Deleting the whole corpus in gs://dona-v5-corpus-softdelete-probe
✔ … is permanently removed — absent from the live and the soft-deleted listings
exit=0
```

The control is the difference, and it is now visible as one. The probe bucket was then deleted.

**The green, on the real bucket** — the acceptance bar:

```
gs://dona-v5-corpus-2026-09-06/throwaway-1.12.txt          ← present
▸ Deleting gs://dona-v5-corpus-2026-09-06/throwaway-1.12.txt
▸ Verifying
✔ … is permanently removed — absent from the live and the soft-deleted listings
exit=0

independently, not the script's own check:
  live:         ERROR: One or more URLs matched no objects.
  soft-deleted: ERROR: HTTPError 400: Soft delete policy is required to list soft-deleted versions
```

**A defect found in the script by running it, and fixed before it merged.** That second error is the
control working — a bucket that keeps nothing cannot be asked what it kept — but the first version of
the script swallowed *every* listing error with `|| true`, so an expired credential or a typo in a
bucket name would have printed `✔ permanently removed`. The two benign messages are now named
explicitly and anything else fails closed:

```
CORPUS_BUCKET=dona-v5-corpus-does-not-exist-9x ./infra/corpus-delete.sh throwaway.txt
  could not verify the listing -- refusing to report a deletion:
  ERROR: gs://dona-v5-corpus-does-not-exist-9x not found: 404.
exit=1
```

And the refusal that runs before anything else:

```
CORPUS_BUCKET=dona-v5-staging-docs ./infra/corpus-delete.sh --all
refusing: dona-v5-staging-docs is not a corpus bucket. This script deletes permanently.
exit=2
```

## Guard three — `-- pii` stops being a sentence

`SPEC.md` has said "PII columns are commented `-- pii`" since slice 1.1 and nothing enforced it,
which is precisely the standing the `current_tenant` rule had before guard one existed. In a slice
whose whole thesis is *controls before data*, that was the cheapest control available and the one
that outlives the slice.

A column named `national_id`, `phone`, `email`, a name, a birth date or a bank detail must carry
`-- pii` on its line or in the comment block directly above it. The one escape is `-- not-pii: <why>`
— a sentence somebody has to write and a reviewer can read; silence is not one of the options. Names
rather than patterns over names, because `like '%phone%'` would fire on `telephone_policy` and teach
people to work around the guard.

```
guard no-current-tenant-column:        ok — 5 files scanned
guard isolation-join-lives-in-src-scope: ok — 79 files scanned
guard pii-columns-are-commented:       ok — 5 files scanned
```

**Zero violations, by design.** `party` and `party_contact` arrive at **2.1** and are the first
tables in this system with a person in them, so this guard is written against a repository that
cannot trip it and fires on `0006_` the day it lands. Carried into 2.1's entry in both plan files.

**Its own test caught it before a migration could.** The first version anchored the pattern at the
start of the line, which matches a column inside `CREATE TABLE` and misses
`ALTER TABLE party ADD COLUMN IF NOT EXISTS birth_date date` entirely — the exact form 2.1 is most
likely to use for a column added after the fact. Six cases in `tests/policy/guards.test.ts`, one of
which is the zero-files case every guard in this repository has.

## F6 and F7 — one lit, one decided

**F6 is lit and half discharged.** ADR-0004 decision 4 — *every third party that sees tenant text is
named before it is called* — is now a table in `SPEC.md`'s Security defaults: OpenAI, Google Cloud,
Meta/WhatsApp, Twilio, and **Anthropic**. The last row is the one nobody had written down: Claude
Code reads this repository as it is built, and the reason it never sees tenant text is not an
assurance but a mechanism — tier 2 never enters the repo, and `.gitignore`, the corpus bucket and the
tier-1 tests are what hold it there.

Decision 3 — a DPA with each processor and disclosure to data subjects — is **the owner's**, is still
owed, and is why ADR-0004 keeps its `proposed` status. An engineering change cannot close it, and
this slice deliberately did not take delivery of the corpus that would overtake it.

**F7 is decided rather than deferred.** The GCP project is org-less and the move must not happen
while real tenant data sits in it. Creating an organisation is a Cloud Identity signup on a domain —
the director's, not a script's — so the move does **not** go first. The corpus gets a dated bucket
with a proved deletion path instead, and the constraint becomes: *the move happens before tier 2
lands, or after it is removed.* The second branch is one `corpus-delete.sh --all` and a bucket
deletion, rather than a search of a project. Recorded on `fuses.md` as a decision with its reasoning.
